# 04. 선택적 AI 사건 연출·보조 제안 시스템 상세 설계

## 문서 상태

- 상태: 1차 구현 완료 (2026-09-01)
- 선행 조건: 03 Story Event Engine과 fallback presentation 완성
- 대상 모듈: 공개 계약은 `mythictrpg-main`, AI 구현은 `mythai-ai-response`
- 권위 주체: 사건·지식·Hook은 서버, AI는 표현만 담당

## 구현 결과 요약

- `mythictrpg-main`에 Presentation 정책 스키마, 안전 Snapshot, 공개 검사, fallback/AI 라우터를 구현했다.
- `mythai-ai-response`에 프로필·동적 관계·허용 Story 의미를 조합하는 Ollama 연출기를 구현했다.
- 실시간 AI 대화에도 화자 Knowledge만 최대 8개까지 주입하며, Hook은 최대 3개의 opaque alias만 제공한다.
- `story_event_hook`은 기존 확인 UI를 사용하고 플레이어·세션·화자·TTL·대상 사건 revision·Hook 조건을 재검증한다.
- 샘플 루브라스 이탈/귀환/전말 공개 Presentation을 새 정책 데이터로 전환했다.
- 전체 186개 GameTest와 두 모듈 컴파일을 통과했다.

남은 운영 검증은 실제 Ollama/Gemma가 실행되는 전용 서버에서의 대사 품질·timeout 스모크 테스트다.
별도 영구 사건 저널 UI가 없으므로 `JOURNAL_IMMEDIATELY`의 오프라인 기록은 현재 pending 보존으로
대체된다. 세부 사용법은 `mythictrpg-main/docs/STORY_AI_PRESENTATION_GUIDE.md`를 따른다.

## 1. 목표

03이 이미 확정한 사건을 신의 프로필, 현재 관계, 감정과 지식 수준에 맞는 자연스러운 대사로
표현한다. 대화 중 플레이어가 할 수 있는 조사·SIDE 활동을 제안할 때도 AI가 새 사건을 만드는 대신
서버가 현재 허용한 등록 Hook 중 하나만 고르게 한다.

04가 없어도 다음은 모두 동일하게 동작해야 한다.

- 사건 발생 조건과 범위
- 확정 outcome과 확률 결과
- 신·존재의 상태와 위치
- Runtime Fact와 각 holder의 Knowledge
- 지연 후속 사건
- 퀘스트·관계·보상·엔딩 분기
- 플레이어에게 필요한 canonical 기록과 fallback 문구

## 2. 보장할 수 있는 것과 없는 것

### 서버 구조로 보장하는 것

- AI가 world fact, outcome, 확률, 관계 수치 또는 보상을 변경하지 못한다.
- AI가 받지 않은 숨은 사실은 프롬프트를 통해 유출되지 않는다.
- AI가 출력한 임의 ID·명령·좌표·아이템은 실행되지 않는다.
- 등록 Hook도 세션, 플레이어, 화자, 사건 revision과 조건을 재검증한다.
- AI 실패·지연·중복이 사건 결과를 바꾸지 않는다.
- 사실 전달이 필요한 장면에는 작성된 canonical 문구가 별도로 남는다.

### 완전히 보장할 수 없는 것

생성 모델이 허용된 정보를 말투에 맞게 표현하는 과정에서 어색한 문장, 사실 누락 또는 근거 없는
장식 표현을 만들 가능성을 0으로 만들 수는 없다. 프롬프트와 출력 검증은 의미 단위의 완전한 사실
검증기가 아니다.

따라서 MAIN/ENDING의 핵심 사실은 AI 문장 하나에만 의존하지 않는다. 서버가 퀘스트 기록, 사건
저널 또는 작성된 자막으로 canonical 내용을 확정해 보여주고, AI 대사는 그 주변의 캐릭터 연출로
사용한다. 정확성이 가장 중요한 장면은 `SCRIPTED_ONLY`로 설정한다.

## 3. 하지 않는 것

- 플레이어가 없는 곳에서 신 대 신 장시간 대화 생성
- AI 대화 결과를 읽어 사건 승패나 50% 결과 판정
- 화자의 성격·강함만 보고 새 사건을 정사로 추가
- 잠긴 outcome, 실제 weight, 다른 신의 비공개 지식 전달
- 모델이 만든 자유 텍스트를 명령어나 데이터팩 JSON으로 실행
- AI가 새 hook/event/quest/actor/fact ID 생성
- 자동 진행되어야 하는 숨은 사건을 AI 응답 완료까지 대기
- AI 대사가 있었다는 이유만으로 플레이어 Knowledge를 임의 상승

## 4. 03과 04의 경계

~~~text
03 Story Event Engine
├─ 사건 판단과 결과 저장
├─ 화자 지식·공개 정책 검사
├─ canonical 문구와 허용 Hook 결정
├─ player별 PresentationOpportunity 생성
└─ AI가 없어도 fallback 전달 가능
                ↓ 공개 Snapshot
04 AI Presentation
├─ 프로필·관계·허용 의미를 조합
├─ 자연스러운 한국어 대사 생성
├─ 허용된 opaque Hook alias만 제안
└─ 결과를 서버 validator로 반환
                ↓
03/기존 서버 Gateway
├─ revision·세션·화자 재검증
├─ canonical 전달 receipt 기록
└─ 수락된 등록 Hook만 StorySignal로 변환
~~~

03은 `mythai-ai-response`를 참조하지 않는다. AI 모듈은 공개 Snapshot을 소비할 뿐
`StoryRuntimeState`에 직접 접근하지 않는다.

## 5. Presentation 종류

~~~text
DIRECT_DIALOGUE
└─ 사건 직후 신이 플레이어에게 직접 말함

CONVERSATION_CONTEXT
└─ 플레이어가 신과 대화하거나 질문할 때 관련 사건 지식을 추가함

OBSERVABLE_CLUE
└─ 소리, 흔적, HUD 문구 등 화자가 없는 관찰 결과

INVESTIGATION_RESULT
└─ 조사 완료 후 작성된 사실과 신의 설명을 함께 전달

JOURNAL_ONLY
└─ AI 없이 사건 기록 또는 퀘스트 저널에만 남김
~~~

`OBSERVABLE_CLUE`, `JOURNAL_ONLY`는 기본적으로 AI를 사용하지 않는다. 화자가 존재하고 실제
플레이어에게 대사가 필요한 경우에만 AI generation을 고려한다.

## 6. 생성 정책과 중요도

~~~text
GenerationPolicy
- SCRIPTED_ONLY
  작성된 대사만 사용. 엔딩, 계약, 정확한 규칙 설명에 권장.

- AI_PARAPHRASE
  허용된 canonical 의미를 말투에 맞게 바꿈. 실패 시 scripted fallback.

- AI_FLAVOR
  중요한 사실 없이 감정·반응 연출만 생성. 정사 정보원으로 사용 금지.
~~~

~~~text
CanonicalDeliveryPolicy
- FLAVOR_ONLY
  별도 저널 기록 불필요. fallback 대사는 반드시 있음.

- FACT_BEARING
  플레이어에게 전달할 canonical fact level을 서버 기록/자막으로 함께 전달.

- CRITICAL
  SCRIPTED_ONLY 강제. MAIN/ENDING의 필수 선택과 규칙 설명에 사용.
~~~

검증 규칙:

- `CRITICAL + AI_*` 조합은 reload 거부
- `FACT_BEARING`은 최소 하나의 canonical fact와 fallback key 필요
- `AI_PARAPHRASE`도 모델 실패 시 의미가 보존되는 fallback 필요
- `AI_FLAVOR`에는 비공개 fact 공개 요청을 넣을 수 없음

## 7. StoryPresentationDefinition

정의는 03과 함께 `mythictrpg-main`이 로드한다.

~~~java
record StoryPresentationDefinition(
    ResourceLocation id,
    PresentationKind kind,
    GenerationPolicy generationPolicy,
    CanonicalDeliveryPolicy canonicalDeliveryPolicy,
    Optional<ResourceLocation> speakerActorId,
    List<FactDisclosureRequest> factRequests,
    List<String> fallbackTranslationKeys,
    Set<ResourceLocation> performanceTags,
    List<ResourceLocation> offeredHookIds,
    OfflineDeliveryPolicy offlineDeliveryPolicy,
    int maximumAiTurns
) {}
~~~

~~~java
record FactDisclosureRequest(
    ResourceLocation factId,
    int maximumLevel,
    boolean required
) {}
~~~

`required=true`인데 화자의 지식·공개 정책으로 어떤 단계도 공개할 수 없다면 AI에게 빈 정보를 주지
않고 Presentation을 `BLOCKED_DISCLOSURE`로 남긴다. 작성 오류 또는 사건 순서 오류이므로 관리자
health에서 확인한다. 숨겨야 하는 장면은 required가 아닌 모호한 fallback을 사용한다.

### 7.1 예시

~~~json
{
  "schemaVersion": 1,
  "kind": "DIRECT_DIALOGUE",
  "generationPolicy": "AI_PARAPHRASE",
  "canonicalDeliveryPolicy": "FLAVOR_ONLY",
  "speakerActorId": "mythictrpg:lubras",
  "factRequests": [],
  "fallbackTranslationKeys": [
    "story.mythictrpg.lubras.intruder_found.fallback"
  ],
  "performanceTags": [
    "mythictrpg:amused",
    "mythictrpg:evasive"
  ],
  "offeredHookIds": [],
  "offlineDeliveryPolicy": "ON_NEXT_LOGIN",
  "maximumAiTurns": 1
}
~~~

이 장면의 AI에는 “침입자가 누구인지”를 주지 않는다. 루브라스가 흥미를 느끼고 무언가를 확인하러
떠나는 태도만 작성된 performance directive로 준다.

## 8. PresentationOpportunity 저장

03의 `emit_story_presentation` 효과는 player별 opportunity를 만든다.

~~~java
record StoryPresentationOpportunity(
    UUID opportunityId,
    StoryEventInstanceId eventInstanceId,
    long eventRevision,
    ResourceLocation presentationId,
    UUID audiencePlayerId,
    Optional<ResourceLocation> speakerActorId,
    PresentationOpportunityStatus status,
    long createdAtGameTime,
    OptionalLong expiresAtGameTime,
    int deliveryAttempts,
    Optional<UUID> activeRequestId
) {}
~~~

~~~text
PENDING
├─ Snapshot 생성 불가 → BLOCKED_DISCLOSURE 또는 FALLBACK_READY
├─ SCRIPTED_ONLY/AI 없음 → DELIVERING_FALLBACK
└─ AI 가능 → GENERATING

GENERATING
├─ 유효 응답 + revision 일치 → DELIVERING_AI
├─ timeout/JSON 오류/낡은 revision → DELIVERING_FALLBACK
└─ 플레이어 이탈 → PENDING 또는 JOURNALED

DELIVERING_AI / DELIVERING_FALLBACK
├─ 클라이언트/저널 전달 성공 → DELIVERED
└─ 일시 실패 → PENDING

DELIVERED
└─ receipt를 근거로 player Knowledge 상승
~~~

`DELIVERED` key는 `eventInstanceId + eventRevision + presentationId + playerId`로 멱등 처리한다. 같은
장면을 다시 대화할 수는 있지만 canonical Knowledge grant는 중복 적용되지 않는다.

## 9. 공개 Snapshot 계약

### 9.1 Query

~~~java
record StoryPresentationQuery(
    UUID audiencePlayerId,
    ResourceLocation speakerActorId,
    Set<ResourceLocation> presentActorIds,
    Optional<UUID> opportunityId,
    Optional<String> playerTopic,
    int maximumFacts,
    int maximumHooks

~~~

`maximumFacts` 기본 8, 상한 16, `maximumHooks` 기본 3, 상한 5로 제한한다.

### 9.2 Snapshot

~~~java
record StoryPresentationSnapshot(
    UUID snapshotId,
    Optional<UUID> opportunityId,
    Optional<StoryEventInstanceId> eventInstanceId,
    long eventRevision,
    UUID audiencePlayerId,
    ResourceLocation speakerActorId,
    Set<ResourceLocation> presentActorIds,
    GenerationPolicy generationPolicy,
    CanonicalDeliveryPolicy canonicalDeliveryPolicy,
    List<AllowedStoryStatement> allowedStatements,
    List<String> performanceDirectives,
    List<StoryHookOffer> allowedHooks,
    List<Component> canonicalPlayerEntries,
    List<Component> fallbackDialogue,
    long expiresAtGameTime
) {}
~~~

~~~java
record AllowedStoryStatement(
    UUID opaqueStatementToken,
    String semanticText,
    StatementKind kind                 // TRUE_FACT, AUTHORED_COVER_STORY, OBSERVATION
) {}
~~~

Snapshot에는 다음을 넣지 않는다.

- forbidden fact ID 목록
- 화자가 아는 사실 중 현재 공개하면 안 되는 내용
- 다른 행위자의 Knowledge
- 선택되지 않은 outcome과 후보 목록
- 확률과 RNG roll
- admin summary와 전체 사건 이력
- 숨은 사실을 유추할 수 있는 semantic한 내부 ID

코드 내부에서 fact ID를 사용하더라도 prompt builder에는 `semanticText`와 opaque token만 전달한다.
`mythictrpg:unknown_entity_occupies_lubras_base` 같은 ID 자체가 비밀을 누설할 수 있기 때문이다.

## 10. 대화용 Context 선택

현재 `AiInteractionContentProvider`는 프로필, 정적 Lore와 관계 Context를 만든다. 여기에
`StoryPresentationContextProvider` 결과를 병합한다.

대화마다 전체 사건 이력을 넣지 않고 다음 우선순위로 최대 8개만 고른다.

1. 활성 opportunity가 요구한 fact
2. 플레이어가 현재 질문에서 언급한 작성 keyword와 일치하는 fact
3. 현재 화자 또는 함께 있는 행위자가 참여한 최근 사건
4. 현재 열린 조사 Hook의 prerequisite와 연결된 공개 가능 fact
5. 이미 플레이어도 알고 있어 대화 연속성에 필요한 최근 fact

동점은 `relevance → learnedGameTime 최신 → fact 정의 ID 안정 정렬` 순으로 결정한다. 모델 임베딩
검색은 v1에 필요하지 않다. 작성 keyword와 역색인을 먼저 사용한다.

플레이어가 “루브라스는 왜 사라졌어?”라고 다른 신에게 물었을 때의 처리:

~~~text
질문 keyword 추출
→ 다른 신의 actor Knowledge 조회
→ disclosure policy 평가
→ 모르면 allowedStatements 비어 있음
→ AI에게 "알지 못함/추측을 사실처럼 말하지 말 것" directive 제공
→ 안다면 허용 level의 semanticText만 전달
~~~

프로필에 “고대의 신”이라고 적혀 있다는 이유로 Runtime Fact를 안다고 추론하지 않는다.

## 11. 작성된 거짓말과 은폐

서버가 `COVER_STORY`를 선택한 경우 AI에는 원래 진실을 함께 주지 않는다.

~~~text
원래 진실: 미지 존재가 루브라스의 거점을 차지했다.
화자의 현재 정책: COVER_STORY
AI 입력: "루브라스는 개인적인 용무 때문에 자리를 비웠다고 설명한다."
StatementKind: AUTHORED_COVER_STORY
~~~

AI는 위장 설명의 말투만 바꾼다. 진실과 거짓을 동시에 주고 “알아서 숨겨라”라고 지시하지 않는다.
정책이 바뀐 뒤 진실을 공개할 때는 새 Snapshot에 실제 fact 단계가 들어간다.

## 12. Prompt 계약

### 12.1 System 규칙

~~~text
- 한국어 신 NPC 대사를 생성한다.
- ALLOWED_SPEAKERS 외 speaker를 사용하지 않는다.
- ALLOWED_STORY_STATEMENTS의 의미만 사실로 말한다.
- AUTHORED_COVER_STORY는 화자가 현재 주장할 작성된 설명이다.
- 목록에 없는 원인, 결과, 장소, 존재, 보상, 관계 변화를 만들지 않는다.
- world state가 변경됐다고 선언하지 않는다.
- HOOK_ALIAS는 제안만 가능하며 실행됐다고 말하지 않는다.
- JSON 하나만 반환한다.
~~~

### 12.2 허용 출력 스키마

~~~json
{
  "speech": [
    {
      "speakerId": "mythictrpg:lubras",
      "text": "대사",
      "audienceParticipantIds": ["player"]
    }
  ],
  "currentTopic": "짧은 주제",
  "proposals": [
    {
      "type": "story_event_hook",
      "hookAlias": "hook_1",
      "title": "조사 제안",
      "summary": "루브라스의 거점을 확인한다"
    }
  ]
}
~~~

- 대사 최대 4개, 각 1,024자 이하
- primary speaker 대사 최소 1개
- proposal 최대 1개
- title 80자, summary 240자 이하
- 자유 parameters, command, coordinates 필드 거부
- 알 수 없는 최상위·중첩 필드는 거부

현재 `AiInteractionContentProvider`의 `proposals: []` 고정 계약을 위 스키마로 확장하되, story
Snapshot이 없으면 지금처럼 빈 목록만 허용한다.

## 13. 응답 검증과 전달

1. requestId와 활성 generation이 일치해야 한다.
2. opportunityId, eventRevision, conversation session이 현재 값과 일치해야 한다.
3. 모든 speaker가 현재 InteractionPlan 참가자인지 검사한다.
4. 대사 길이, 개수와 Component sanitizer를 통과시킨다.
5. hookAlias가 Snapshot의 opaque allowlist에 있어야 한다.
6. 알 수 없는 proposal, ID, extra field가 있으면 proposal만 또는 전체 응답을 정책대로 거부한다.
7. 늦은 응답은 화면·Knowledge·사건 상태를 변경하지 않고 폐기한다.
8. 유효 대사가 없으면 작성된 fallback으로 전환한다.

AI 문장 안에 `/give`, NBT, 좌표가 있어도 단순 문자열일 뿐 실행되지 않는다. 자유 텍스트를 다시
파싱하여 effect로 바꾸는 코드 경로를 만들지 않는다.

## 14. Canonical 전달과 Knowledge receipt

`FACT_BEARING` 장면은 다음 두 층을 사용한다.

~~~text
1. Canonical layer
   작성된 fact 문구를 사건 저널/HUD에 기록

2. Character layer
   AI 또는 fallback으로 신의 말투와 감정 표현
~~~

AI가 사실을 빼먹더라도 1번으로 플레이어가 필요한 내용을 얻는다. 반대로 AI가 불필요한 장식을
붙여도 그 문장은 새 Runtime Fact가 되지 않는다.

Knowledge 상승은 `StoryPresentationDeliveryReceipt`가 성공한 뒤 서버가 미리 계산한 grant plan을
적용한다. AI가 실제로 특정 단어를 썼는지 문자열 검색하지 않는다. identity 공개에 쓰는 기존
`SpokenIdentityReveal`과 Runtime Story Knowledge는 별도 체계로 유지한다.

## 15. 등록 Story Hook

### 15.1 정의 권한

Hook 정의는 03 데이터팩에 있으며 다음 정보를 가진다.

~~~java
record StoryHookDefinition(
    ResourceLocation id,
    ResourceLocation targetEventId,
    Set<ResourceLocation> allowedSpeakerActorIds,
    ConditionNode availabilityConditions,
    StoryScopeType targetScope,
    String titleTranslationKey,
    String summaryTranslationKey,
    int cooldownTicks,
    int maximumAcceptances,
    boolean confirmationRequired
) {}
~~~

04는 현재 조건에 맞아 Snapshot에 포함된 Hook만 보여준다. MAIN/WORLD 상태를 바꿀 수 있는 Hook은
`confirmationRequired=true`를 강제한다. 첫 구현에서는 모든 AI 제안 Hook에 확인을 요구한다.

### 15.2 Opaque token

AI에게 실제 event ID와 내부 revision을 직접 넘기지 않는다.

~~~java
record StoryHookTokenState(
    UUID token,
    ResourceLocation hookId,
    UUID playerId,
    ResourceLocation speakerActorId,
    UUID conversationSessionId,
    Optional<StoryEventInstanceId> sourceInstanceId,
    long expectedEventRevision,
    long expiresAtGameTime
) {}
~~~

prompt에는 `hook_1` 같은 alias만 들어가고 서버 메모리에서 token으로 매핑한다. token은 기본 1,200
tick 후 만료하며 서버 재시작 시 폐기해도 된다. 수락하지 않은 제안은 정사가 아니므로 영구 저장할
필요가 없다.

### 15.3 AiActionGateway 연동

기존 `AiActionGateway`에 등록 action type `mythictrpg:story_event_hook`을 추가한다.

~~~text
AI가 hookAlias 제안
→ 서버가 alias를 opaque token으로 해석
→ AiActionGateway가 활성 대화·행동 신·플레이어 검증
→ 확인 UI 전송
→ 플레이어 수락
→ 현재 세션·token 만료·event revision 재검사
→ StoryHookService가 정의·조건·scope·횟수·cooldown 재검사
→ story_hook_accepted StorySignal 발행
→ 03이 등록 target event만 평가
~~~

Hook 수락은 outcome 선택이 아니다. target event가 신호를 받은 뒤 03의 조건과 resolution policy로
판정한다. 수락 순간 조건이 바뀌었다면 거부하고 아무 사건도 만들지 않는다.

## 16. 현재 코드와 구체적 접점

### mythictrpg-main

- `MythicTrpg`: Story definition reload listener와 runtime event handler 등록
- `GameplayIngressService` production sink: Story observation adapter 추가
- `ConditionContext`: `StoryStateView` 추가, 기존 overload 호환
- `AiActionRegistry`: `story_event_hook` action definition 등록
- `AiConversationRuntimeService`: 현재 session ID와 speaker scope 검증 재사용
- `DialoguePresentationService`: scripted/AI 결과의 클라이언트 전달 재사용
- `InteractionSignal`: 실제 플레이어가 있는 DIRECT_DIALOGUE를 시작할 때만 새 payload 타입 추가
- `StoryPresentationContextProvider`: AI 모듈에 허용 Snapshot 제공

### mythai-ai-response

- `AiInteractionContentProvider.messages`: Story Snapshot의 허용 의미·연출·Hook alias 병합
- `AiInteractionContentProvider.toPreparationResult`: speech와 proposal strict 검증 분리
- `GodAiDialogueService`: 대화 turn마다 관련 Story Context shortlist 요청
- `MythAiConversationEngine`: 대화 시작/종료에 Snapshot token 수명 연결
- `LocalOllamaClient`: 기존 timeout·server thread callback 규칙 재사용

### mythai-ai-content-registry

정적 Lore와 프로필의 원본 역할을 계속 맡는다. Runtime Story Fact를 이 모듈의 `LoreEntry`에 동적으로
삽입하거나 JSON 파일로 덮어쓰지 않는다. AI response가 정적 Lore와 서버 Snapshot을 최종 prompt에서
합친다.

## 17. Offline, timeout과 중복 정책

~~~text
OfflineDeliveryPolicy
- DROP_FLAVOR: flavor 장면은 버리고 감사 receipt만 남김
- ON_NEXT_LOGIN: 다음 로그인 때 조건/revision 재검증 후 전달
- JOURNAL_IMMEDIATELY: 저널에 canonical 내용 기록, 대사는 생략
~~~

- MAIN/ENDING fact-bearing 장면은 `DROP_FLAVOR` 사용 금지
- 로그인 뒤 화자 상태가 바뀌어 대화가 부적절하면 canonical 저널만 전달
- AI timeout 기본값은 기존 설정을 따르되 사건 엔진은 기다리지 않음
- 같은 opportunity의 generation은 동시에 하나만 허용
- timeout 뒤 도착한 응답은 requestId 불일치로 폐기
- 재로그인 때 outcome을 읽어 새로 추첨하지 않고 pending presentation만 복구

## 18. 루브라스 사례의 AI 사용 지점

### 18.1 거점 점유

플레이어가 없는 서버 사건이다. AI 호출 없음.

~~~text
wanderer ACTIVE
→ location=lubras_hell_base
→ occupied fact=true
→ 후속 signal
~~~

### 18.2 루브라스의 갑작스러운 이탈

03이 먼저 `lubras availability=ABSENT`와 사건 결과를 확정한다. 플레이어가 현장에 있으면 04가
`amused + evasive` directive로 짧은 대사를 만들 수 있다. 실패하면 “재밌는 게 생겼군.”이라는
작성 fallback을 표시한다. 실종 이유는 Snapshot에 넣지 않는다.

### 18.3 다른 신에게 질문

그 신이 level 1만 알면 “지옥 쪽에서 이상한 기운이 움직였다” 정도만 Snapshot에 들어간다. level
0이면 모른다는 directive만 준다. 화자가 교활하고 작성된 cover story 정책이 있으면 그 문구만 준다.

### 18.4 루브라스 귀환

귀환 사건이 루브라스의 공개 정책을 level 3까지 연 뒤 새 Snapshot을 만든다. `FACT_BEARING`이므로
사건 저널에 canonical 전말을 기록하고 AI는 루브라스다운 상세 설명을 덧붙인다. AI 실패 시 level 3
fallback 대사로 대체한다.

## 19. 성능과 요청량

- 플레이어가 없는 사건에는 AI 요청 0회
- PresentationOpportunity 하나당 동시 요청 1회
- 한 대화 turn당 Story fact 최대 8개, Hook 최대 3개
- 전체 사건 이력이나 전체 Lorebook을 prompt에 넣지 않음
- keyword/actor/event 역색인으로 shortlist 후 disclosure 검사
- 같은 Snapshot revision은 content hash cache 사용 가능
- 캐시는 정답 저장소가 아니며 event/knowledge/relation revision이 바뀌면 폐기
- 모델 요청 queue가 가득 차면 기다리지 않고 fallback을 사용

## 20. 실패 처리

| 실패 | 처리 | 사건 영향 |
|---|---|---|
| AI 모듈 미설치 | scripted fallback | 없음 |
| Ollama 중지/timeout | fallback | 없음 |
| 잘못된 JSON | 응답 거부 후 fallback | 없음 |
| 허용되지 않은 speaker | 해당 응답 거부 | 없음 |
| 잘못된 hook alias | proposal 거부, 대사는 별도 검증 | 없음 |
| 낡은 revision | 전체 응답 폐기 또는 새 fallback | 없음 |
| disclosure required 불충족 | BLOCKED_DISCLOSURE + 관리자 진단 | 사건 결과 유지 |
| 클라이언트 전달 실패 | pending 재시도/저널 | 사건 결과 유지 |
| Hook 재검증 실패 | 수락 거부 안내 | 새 사건 없음 |

## 22. 테스트 매트릭스

### 비밀과 입력

1. 화자가 모르는 fact가 Snapshot에 없다.
2. WITHHOLD된 fact ID와 의미가 prompt에 없다.
3. 다른 신의 Knowledge와 속마음이 prompt에 없다.
4. 선택되지 않은 outcome, weight와 roll이 prompt에 없다.
5. COVER_STORY에서 원래 진실을 모델에 함께 주지 않는다.
6. level 1 화자와 level 3 화자의 허용 문구가 다르다.

### 출력과 권한

7. outsider speaker와 5번째 대사를 거부한다.
8. 알 수 없는 JSON field와 proposal type을 거부한다.
9. 명령·좌표 문자열이 실행되지 않는다.
10. 허용되지 않은 hookAlias와 위조 token을 거부한다.
11. 다른 player/session/speaker의 token을 거부한다.
12. 확인 뒤 revision이 변하면 Hook 실행을 거부한다.
13. Hook 수락이 직접 outcome을 정하지 않고 StorySignal만 발행한다.

### 실패와 중복

14. AI 미설치, timeout, 빈 응답, 잘못된 JSON에서 fallback이 보인다.
15. 늦은 응답이 이미 표시된 fallback을 덮어쓰지 않는다.
16. 같은 opportunity 재시도가 canonical Knowledge를 두 번 올리지 않는다.
17. 재접속이 outcome을 재추첨하지 않고 pending presentation만 처리한다.
18. playerless 사건에서 Ollama 요청 수가 0이다.

### 정사 전달

19. FACT_BEARING에서 AI가 사실 문장을 생략해도 canonical 저널은 남는다.
20. CRITICAL presentation에 AI 정책을 작성하면 reload가 실패한다.
21. 실제 전달 receipt 전에는 플레이어 Knowledge가 오르지 않는다.
22. 작성된 cover story 외의 거짓 정보는 서버 fact가 되지 않는다.

## 23. 완료 기준

- 03은 04와 Ollama 없이 동일한 사건 결과와 fallback 전달을 완료한다.
- AI 대사는 화자의 프로필, 방향성 관계, 허용된 Runtime Story Knowledge를 함께 반영한다.
- 서로 다른 지식 수준의 신이 같은 질문에 서로 다른 범위로 답한다.
- 은폐와 거짓말은 작성된 disclosure/cover story 범위에서만 표현된다.
- MAIN/ENDING 필수 사실은 canonical 기록으로 보장된다.
- AI 제안은 현재 Snapshot의 등록 Hook 하나만 선택할 수 있다.
- Hook은 플레이어 확인 후에도 서버가 조건·세션·revision을 다시 검사한다.
- AI 실패·지연·중복·환각이 world fact, outcome, 관계, 보상 또는 엔딩을 바꾸지 않는다.
- 실제 Gemma 계열 모델 대사 스모크 테스트와 전용 서버 fallback 테스트가 통과한다.

## 24. 구현 시 금지 사항

- 숨은 fact를 prompt에 넣고 “말하지 말라”고만 지시하지 않는다.
- semantic한 내부 fact/event ID를 그대로 모델에게 노출하지 않는다.
- AI가 말한 내용을 사실 전달 여부 판정의 유일한 근거로 사용하지 않는다.
- 핵심 정보를 fallback 없는 AI 대사에만 맡기지 않는다.
- Hook alias를 실제 command, event ID 또는 effect parameters로 직접 해석하지 않는다.
- AI 모듈에서 StoryRuntimeState를 직접 수정하지 않는다.
- 모델 품질이 좋아져도 03의 결과 결정 권한을 04로 옮기지 않는다.

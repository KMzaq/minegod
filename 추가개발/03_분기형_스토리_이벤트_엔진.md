# 03. 조건 기반 인과·분기형 스토리 사건 엔진 상세 설계

## 문서 상태

- 상태: 1차 서버 권위 엔진 구현 완료 (전용 PLAYER_CHOICE GUI와 04 AI 연동은 후속)
- 대상 모듈: `mythictrpg-main`
- 정적 데이터 위치: 데이터팩 `data/<namespace>/mythictrpg/...`
- 권위 주체: Minecraft 서버
- 04 의존성: 없음. 03은 AI 모듈 없이 완전히 동작해야 한다.

## 1. 목표

플레이어의 행동, 퀘스트, 신들의 방향성 관계, 신·존재의 상태, 장소 점유와 과거 사건 결과가 이후의
사건을 일으키게 한다. 서버는 작성자가 등록한 결과 중 하나만 확정하여 저장하고, 실제로 일어난
사실과 각 인물이 알고 있는 사실을 분리한다.

이 엔진으로 다음 흐름을 구현할 수 있어야 한다.

~~~text
플레이어의 작은 행동
→ 즉시 눈에 보이지 않는 실제 세계 변화
→ 조건이 갖춰진 뒤 플레이어 부재 중 후속 사건 발생
→ 이상 징후만 관찰
→ 다른 신에게서 일부 정보 습득
→ 당사자 귀환 후 전말 공개
→ 퀘스트·관계·엔딩 분기로 연결
~~~

## 2. 확정 정책

1. 메인 스토리와 세계 변화는 기본적으로 서버 전역에서 한 번 발생한다.
2. 플레이어별 목격·정보·개인 분기는 별도로 저장한다.
3. 팀 범위는 사건이 명시한 경우에만 사용하며, 사건 발생 당시 구성원을 고정한다.
4. 신, 미지의 존재, 세력은 모두 범용 `StoryActor`로 취급한다.
5. 행위자의 봉인·해방·패배·소멸, 대화 가능 여부와 논리적 위치를 서버가 저장한다.
6. 지연은 서버가 실행 중일 때 흐르는 게임 시간만 사용한다. 오프라인 시간은 흐르지 않는다.
7. 메인·엔딩은 조건 또는 플레이어 선택이 기본이다. 명시적으로 허용된 사건만 확률을 사용한다.
8. 확률 결과는 인스턴스당 한 번만 뽑고 저장한다.
9. 플레이어와 신은 각자 별도의 지식을 가진다. 팀 자동 공유는 하지 않는다.
10. AI가 즉석에서 만든 거짓말은 정사로 취급하지 않는다. 거짓말은 작성된 위장 정보만 사용한다.
11. 신들끼리 장시간 자율 대화하지 않는다. 플레이어가 없는 곳의 사건은 상태 전이만 계산한다.

## 3. 범위 밖

- LLM을 이용한 승패, 확률, 참가자 또는 정사 결정
- 모든 신과 사건을 매 tick 순회하는 자율 시뮬레이션
- 자연어를 Minecraft 명령이나 자유로운 월드 변경으로 실행
- 미등록 몹·아이템·보상·좌표 생성
- 서버가 꺼져 있는 동안의 현실 시간 진행
- 작성자 승인 없이 AI가 MAIN/WORLD/ENDING 사건을 추가
- 1차 구현에서의 실제 NPC 경로 탐색과 신들 사이 물리 전투 시뮬레이션

## 4. 용어와 진실의 계층

| 개념 | 의미 | 저장 위치 |
|---|---|---|
| Canonical Lore | 시작 전부터 참인 과거사·세계 법칙 | 기존 Lorebook |
| Story Definition | 사건·행위자·장소·사실·공개 규칙의 정적 정의 | 데이터팩 |
| Runtime Fact | 플레이 중 실제로 참/거짓이 바뀌는 등록 사실 | StoryRuntimeState |
| Actor State | 봉인·활동·패배·부재·논리적 위치 | StoryRuntimeState |
| Event Instance | 실제 발생한 사건 한 건과 확정 결과 | StoryRuntimeState |
| Knowledge | 플레이어·행위자가 알고 있는 Runtime Fact의 단계 | StoryRuntimeState |
| Presentation | 알려도 되는 내용을 플레이어에게 전달하는 행위 | 03 fallback + 선택적 04 AI |

Runtime Fact가 참이라고 해서 플레이어가 그 사실을 아는 것은 아니다. 행위자가 사실을 안다고 해서
플레이어에게 말할 수 있는 것도 아니다. 이 두 경계를 각각 `KnowledgeRecord`와
`DisclosurePolicy`로 검사한다.

## 6. 정적 데이터 레지스트리

### 6.1 폴더

~~~text
data/<namespace>/mythictrpg/story_actors/*.json
data/<namespace>/mythictrpg/story_locations/*.json
data/<namespace>/mythictrpg/story_facts/*.json
data/<namespace>/mythictrpg/story_cover_stories/*.json
data/<namespace>/mythictrpg/story_disclosure_policies/*.json
data/<namespace>/mythictrpg/story_events/*.json
data/<namespace>/mythictrpg/story_hooks/*.json
data/<namespace>/mythictrpg/story_presentations/*.json
~~~

모든 파일은 `schemaVersion: 1`, 알 수 없는 필드 거부, namespaced ID 강제, 중복 거부 정책을 쓴다.
각 Manager는 기존 `GodDefinitionManager`, `GodRelationTransitionManager`와 같은 준비-검증-원자 교체
reload 패턴을 사용한다. 하나라도 잘못되면 새 세트를 전부 거부하고 직전 정상 세트를 유지한다.

### 6.2 StoryActorDefinition

~~~java
record StoryActorDefinition(
    ResourceLocation id,
    StoryActorType type,                  // GOD, ENTITY, FACTION
    Optional<ResourceLocation> godId,     // GOD일 때 기존 GodDefinition 연결
    ExistenceState initialExistence,
    AvailabilityState initialAvailability,
    Optional<ResourceLocation> initialLocationId,
    Set<ResourceLocation> tags
) {}
~~~

- `GOD`는 반드시 존재하는 `GodDefinition`을 참조한다.
- `ENTITY`, `FACTION`은 완전한 신 프로필 없이도 사건 행위자로 먼저 등록할 수 있다.
- ID가 없는 임시 존재를 런타임에 자유 생성하지 않는다.
- `SEALED`, `DEFEATED`, `DESTROYED` 상태의 기본 대화 가능 여부는 `ABSENT`여야 한다.

~~~text
ExistenceState: SEALED, ACTIVE, DEFEATED, DESTROYED
AvailabilityState: AVAILABLE, ABSENT
~~~

`ACTIVE + ABSENT`는 살아 있고 어딘가에서 활동하지만 일반 조우·대화에는 나타나지 않는 상태다.
루브라스가 갑자기 사라진 기간이 이에 해당한다.

### 6.3 StoryLocationDefinition

논리적 장소는 실제 좌표가 아니다.

~~~java
record StoryLocationDefinition(
    ResourceLocation id,
    String titleTranslationKey,
    Optional<ResourceLocation> dimensionId,
    Set<ResourceLocation> tags
) {}
~~~

`mythictrpg:lubras_hell_base`처럼 사건에서 안정적으로 참조할 ID를 제공한다. 행위자의 현재 장소를
변경하면 런타임이 `actorsByLocation` 역색인을 함께 다시 만든다. 한 장소에 여러 존재가 있을 수
있으며, 빈 장소 조건은 이 역색인으로 검사한다.

### 6.4 StoryFactDefinition

Runtime Fact v1은 등록된 Boolean 사실만 지원한다. 숫자 누적은 퀘스트 진행 트랙이나 별도 카운터를
사용하며, 문자열 값을 자유 저장하지 않는다.

~~~java
record StoryFactDefinition(
    ResourceLocation id,
    Set<StoryScopeType> allowedScopes,    // SERVER, PLAYER, TEAM
    boolean defaultValue,
    String adminSummary,
    List<FactKnowledgeLevel> levels,      // 1부터 연속
    Set<ResourceLocation> keywords
) {}

record FactKnowledgeLevel(
    int level,
    String canonicalTranslationKey
) {}
~~~

`canonicalTranslationKey`는 그 단계에서 확실히 알 수 있는 작성된 의미다. AI 프롬프트에는 ID가 아닌
번역된 의미만 전달한다. 단계 예시는 다음과 같다.

~~~text
level 1: 지옥의 오래된 봉인 주변에서 이상 징후가 생겼다.
level 2: 누군가의 봉인이 풀렸고 루브라스의 빈 거점으로 향했다.
level 3: 플레이어의 접촉으로 풀려난 존재가 그 거점을 차지했다.
~~~

### 6.5 StoryDisclosurePolicy

~~~java
record StoryDisclosurePolicy(
    ResourceLocation id,
    DisclosureMode mode,                 // FULL, PARTIAL, WITHHOLD, CONDITIONAL, COVER_STORY
    OptionalInt maximumDisclosedLevel,
    Optional<ConditionNode> condition,
    Optional<ResourceLocation> lockedPolicyId,
    Optional<ResourceLocation> coverStoryId
) {}
~~~

- `CONDITIONAL`은 서버가 조건을 검사한 뒤 열린 정책 또는 `lockedPolicyId`를 선택한다.
- `COVER_STORY`는 미리 등록된 `StoryCoverStoryDefinition`의 작성 문구만 사용한다.
- 원래 진실과 위장 정보의 연결은 서버에만 존재한다.
- 정책 누락·순환·조건 UNKNOWN은 `WITHHOLD`로 닫힌다.
- AI가 임의로 거짓 원인이나 새 인물을 만드는 경로는 없다.

Cover Story는 거짓인 정사 fact가 아니라 화자가 주장하도록 허용된 문장 묶음이다.

~~~java
record StoryCoverStoryDefinition(
    ResourceLocation id,
    List<String> canonicalTranslationKeys,
    Set<ResourceLocation> allowedSpeakerActorIds
) {}
~~~

이를 Runtime Fact로 등록하지 않으며 플레이어가 들었다고 세계의 진실이 바뀌지도 않는다. 플레이어
기록에는 “해당 화자가 이 설명을 주장했다”는 공개 receipt만 선택적으로 남길 수 있다.

### 6.6 StoryEventDefinition

~~~java
record StoryEventDefinition(
    ResourceLocation id,
    NarrativeRole narrativeRole,         // SIDE, MAIN_ENTRY, MAIN, WORLD, ENDING
    StoryScopeType scopeType,             // SERVER, PLAYER, TEAM
    List<StoryTriggerDefinition> triggers,
    ConditionNode prerequisites,
    List<StoryActorBinding> actors,
    RepeatPolicy repeatPolicy,
    ResolutionPolicy resolutionPolicy,
    boolean randomNarrativeExplicitlyAllowed,
    List<StoryOutcomeDefinition> outcomes,
    Optional<ChoicePolicy> choicePolicy,
    EventFailurePolicy failurePolicy
) {}
~~~

~~~text
ResolutionPolicy:
- FIXED: 유효한 단일 결과
- FIRST_MATCH: 작성 순서상 처음 일치하는 결과
- WEIGHTED_ONCE: 유효 후보 중 1회 가중 추첨
- PLAYER_CHOICE: 서버 UI/검증된 선택으로 결과 확정
~~~

`MAIN`, `ENDING`에서 `WEIGHTED_ONCE`를 쓰려면
`randomNarrativeExplicitlyAllowed: true`가 반드시 있어야 한다. 없으면 reload를 거부한다.

플레이어 선택은 기본적으로 만료되지 않는다. 선택 시간 제한을 작성하려면 게임 tick 기준
`timeoutTicks`와 `defaultOutcomeId`를 둘 다 지정해야 한다. AI 자유 텍스트로 선택을 확정하지 않는다.

### 6.7 StoryHookDefinition

Hook은 AI가 만드는 사건이 아니라 작성자가 등록한 사건 진입점이다.

~~~java
record StoryHookDefinition(
    ResourceLocation id,
    ResourceLocation targetEventId,
    Set<ResourceLocation> allowedSpeakerActorIds,
    ConditionNode availabilityConditions,
    StoryScopeType targetScope,
    String titleTranslationKey,
    String summaryTranslationKey,
    int cooldownTicks,
    int maximumAcceptances,
    boolean confirmationRequired
) {}
~~~

Hook이 수락되면 `story_hook_accepted` 신호만 발행한다. target event는 다시 trigger, prerequisite,
scope와 반복 제한을 검사하며 Hook 자체가 outcome을 직접 지정하지 않는다. AI에서 제안되는 Hook은
v1에서 모두 `confirmationRequired=true`여야 한다.

## 7. 사건 Trigger와 Signal

### 7.1 StorySignal

~~~java
record StorySignal(
    UUID signalId,
    ResourceLocation typeId,
    Optional<UUID> initiatingPlayerId,
    Optional<ResourceLocation> subjectId,
    Optional<ResourceLocation> logicalLocationId,
    Optional<StoryEventInstanceId> sourceEventInstanceId,
    long gameTime,
    StorySignalPayload payload
) {}
~~~

`payload`는 등록된 타입별 Java record다. 자유 `Map<String, Object>`는 금지한다. 최소 내장 신호는
다음과 같다.

~~~text
mythictrpg:gameplay_observed
mythictrpg:quest_completed
mythictrpg:god_unlocked
mythictrpg:god_identified
mythictrpg:relation_transitioned
mythictrpg:fact_changed
mythictrpg:actor_state_changed
mythictrpg:event_resolved
mythictrpg:scheduled_due
mythictrpg:story_hook_accepted
mythictrpg:admin_triggered
~~~

기존 `GameplayIngressService`의 production sink lambda에
`StoryGameplayObservationAdapter.INSTANCE.accept(server, observation)`를 네 번째 소비자로 추가한다.
현재 `InteractionSignal`은 반드시 플레이어를 요구하므로 플레이어가 없는 세계 사건에 재사용하지
않는다.

### 7.2 Trigger 모드

~~~text
IMMEDIATE
└─ 신호가 들어온 순간 조건이 맞을 때만 인스턴스를 만든다.

LATCHED
└─ 신호를 저장한 뒤 조건 의존성이 변할 때 재평가한다.
   expiresAfterTicks가 지나면 취소된다.
~~~

`LATCHED`는 “플레이어가 먼저 봉인을 건드렸고 나중에 거점이 비게 됨” 같은 순서 차이를 허용한다.
무기한 대기는 명시적으로 `expiresAfterTicks: -1`을 작성한 경우에만 허용한다. 대기 레코드는
event/scope/trigger discriminator당 하나로 중복 제거한다.

### 7.3 Dependency Index

`StoryEventDefinitionManager`는 reload 때 다음 역색인을 만든다.

~~~text
signal type + optional subject → event IDs
story fact ID                → latched event IDs
actor ID                     → latched event IDs
location ID                  → latched event IDs
condition dependency         → latched event IDs
scheduled event ID           → event ID
~~~

신호가 오면 관련 후보만 평가한다. 조건 트리는 기존 `ConditionEngine`을 재사용하고 Story 전용 조건
타입을 등록한다.

## 8. 추가 Condition 타입

`ConditionContext`에 `StoryStateView story`를 추가하되 기존 생성자의 호환 overload에는
`StoryStateView.unavailable()`을 넣는다. 다음 타입을 v1에 추가한다.

| type | 주요 필드 | 의존성 |
|---|---|---|
| `mythictrpg:story_fact` | fact, scope, expected | fact ID |
| `mythictrpg:story_event` | event, status/outcome, scope | event ID |
| `mythictrpg:story_actor_state` | actor, existence, availability | actor ID |
| `mythictrpg:story_actor_location` | actor, location | actor/location ID |
| `mythictrpg:story_location_empty` | location, optional excludedActors | location ID |
| `mythictrpg:story_knowledge` | holder/target player, fact, minimumLevel | fact/holder |

`ConditionResult.UNKNOWN`은 일치로 간주하지 않는다. MAIN/ENDING 사건에서 UNKNOWN이 발생하면
`BLOCKED_UNKNOWN_CONDITION` 진단을 남기고 관리자 조회가 가능해야 한다.

## 9. Scope와 멀티플레이

~~~java
sealed interface StoryScopeKey {
    record Server() implements StoryScopeKey {}
    record Player(UUID playerId) implements StoryScopeKey {}
    record Team(String stableTeamId) implements StoryScopeKey {}
}
~~~

- `SERVER`: 최초 유효 신호 하나만 승리하며 유발 플레이어는 원인으로 기록된다.
- `PLAYER`: 같은 사건도 플레이어별로 별도 인스턴스를 가진다.
- `TEAM`: FTB 팀 stable ID를 사용하고 사건 발생 시 구성원 UUID를 인스턴스에 고정한다.
- 팀이 없는 플레이어는 `solo:<uuid>` 팀으로 해석한다.
- 사건 도중 가입한 구성원은 자동으로 과거 지식을 얻지 않는다.
- 탈퇴한 구성원이 이미 얻은 지식은 삭제하지 않는다.

같은 tick에 여러 플레이어가 서버 공용 ONCE 사건을 유발하면 서버 신호 큐에서 먼저 처리된 유효
신호가 원인이 된다. 나머지는 `ALREADY_RESOLVED`로 감사 로그에만 남긴다.

## 10. 런타임 저장 모델

새 SavedData 파일 `mythictrpg_story`를 만든다.

~~~java
final class StoryRuntimeState extends SavedData implements StoryStateView {
    int dataVersion;
    long globalRevision;
    Map<ScopedFactKey, FactValueRecord> facts;
    Map<ResourceLocation, StoryActorState> actorStates;
    Map<StoryEventInstanceId, StoryEventInstance> eventInstances;
    Map<LatchedTriggerKey, LatchedStoryTrigger> latchedTriggers;
    Map<UUID, ScheduledStorySignal> schedules;
    Map<KnowledgeKey, StoryKnowledgeRecord> knowledge;
    Map<PublicKnowledgeKey, Integer> publicPlayerKnowledge;
    Map<StoryEventInstanceId, List<ExternalEffectReceipt>> externalOutbox;
    List<StoryAuditEntry> boundedAudit;
}
~~~

모든 자료는 sparse하게 저장한다. 기본값과 같은 fact, 초기값과 같은 actor 상태는 저장하지 않아도
되지만 조회 시 정의의 기본값과 합성한다. `actorsByLocation`, signal index, due-time priority queue는
저장하지 않고 load 후 검증하여 재구성한다.

NBT는 다음 원칙을 따른다.

- `CURRENT_DATA_VERSION = 1`
- 알 수 없는 미래 버전은 원본 NBT를 보존하고 read-only로 전환
- 중복 키, 잘못된 enum/ID, 음수 revision, 존재하지 않는 참조를 거부
- 거부된 상태를 빈 정상 상태로 덮어쓰지 않음
- 모든 변경은 서버 스레드에서만 실행
- 감사 기록은 전체 2,048개, 인스턴스당 상세 32개를 기본 상한으로 둠

### 10.2 Event Instance 상태 머신

~~~text
TRIGGERED
├─ 조건 불일치 → CANCELLED 또는 LATCHED로 복귀
├─ PLAYER_CHOICE → WAITING_FOR_CHOICE
└─ 결과 확정 → DECIDED

WAITING_FOR_CHOICE
├─ 유효 선택 → DECIDED
└─ 작성된 timeout → DECIDED(default outcome)

DECIDED
└─ canonical commit 성공 → COMMITTED

COMMITTED
├─ 외부 효과 전부 성공/불필요 → RESOLVED
├─ 재시도 가능 실패 → EXTERNAL_EFFECT_PENDING
└─ 영구/정의 불일치 → RECOVERY_REQUIRED

EXTERNAL_EFFECT_PENDING
├─ idempotent 재시도 성공 → RESOLVED
└─ 재시도 한도 초과 → RECOVERY_REQUIRED
~~~

`AVAILABLE`, `ACTIVE` 같은 정의 상태는 저장하지 않는다. 인스턴스가 없고 반복 정책이 허용하면 후보일

## 11. 결과 결정

### 11.1 유효 후보

1. event prerequisite가 `MATCH`인지 검사한다.
2. 반복 제한과 scope를 검사한다.
3. 각 outcome의 `additionalConditions`를 검사한다.
4. 결과별 모든 효과 참조와 현재 실행 가능성을 사전 검증한다.
5. 유효 후보가 없으면 추첨하지 않고 `BLOCKED_NO_VALID_OUTCOME`을 기록한다.

### 11.2 WEIGHTED_ONCE

- weight는 `1..1_000_000` 양의 정수다.
- 합계는 `long`으로 더하고 overflow를 거부한다.
- seed는 `world seed + event ID + scope key + repeat sequence + definition fingerprint`의 안정적 hash로 만든다.
- roll과 `selectedOutcomeId`를 인스턴스에 기록한다.
- resource reload, 대화 재시도, 재접속, AI 실패로 다시 뽑지 않는다.
- 운영 preview는 후보와 가중치만 보여주며 RNG 상태를 소비하지 않는다.
- 일반 관리자 trigger도 기존 결과를 덮어쓰지 않는다. 테스트 전용 force는 별도 권한과 감사 기록을 쓴다.

### 11.3 PLAYER_CHOICE

클라이언트는 `instanceId`, `eventRevision`, `choiceId`만 보낸다. 서버는 참가자, 현재 상태, 선택 허용
목록, 조건과 revision을 다시 검사한다. 같은 선택 packet이 재전송돼도 최초 결정만 적용한다.

## 12. Outcome과 Effect

~~~java
record StoryOutcomeDefinition(
    ResourceLocation id,
    int weight,
    Optional<ConditionNode> additionalConditions,
    List<StoryEffectDefinition> effects
) {}
~~~

각 effect는 outcome 안에서 고유한 `effectId`를 반드시 가진다.

### 12.1 Canonical Effect

하나의 `StoryRuntimeState` copy-on-write 커밋 계획에 포함된다.

~~~text
set_fact
set_actor_state
move_actor
grant_knowledge
set_disclosure_policy
schedule_story_signal
cancel_schedule
emit_story_presentation
~~~

전체 계획을 먼저 검증한 뒤 새 Map/Set 복사본에 적용하고 마지막에 한 번 교체한다. 중간 검증 실패 시
아무 canonical 변경도 적용하지 않는다. 커밋 뒤 발생한 `fact_changed`, `actor_state_changed`,
`event_resolved` 신호는 현재 실행 스택에서 재귀 실행하지 않고 다음 큐 단계로 보낸다.

### 12.2 External Effect

다른 SavedData나 Minecraft 월드를 바꾸므로 outbox를 거친다.

~~~text
registered_quest_offer_or_start
registered_quest_completion
quest_progress_change
god_unlock
god_relation_transition
registered_reward
registered_sound_particle
future: validated_spawn / validated_region_mutation
~~~

각 executor는 `StoryEffectExecutionKey(instanceId, effectId)`를 받아야 하며 다음 중 하나만 허용한다.

1. 대상 시스템이 같은 key의 `ALREADY_APPLIED`를 판별하는 멱등 API를 제공한다.
2. 원래부터 quest 완료처럼 한 번만 적용되는 등록 동작이다.
3. 실패해도 canonical 정사를 바꾸지 않는 표현 효과다.

멱등성이 없는 자유 명령 executor는 등록하지 않는다. 외부 효과 실패로 outcome을 바꾸거나 재추첨하지
않고 outbox에서 제한 재시도 후 `RECOVERY_REQUIRED`로 보낸다.

### 12.3 저장 한계에 대한 명시

Minecraft `SavedData`는 매 사건마다 디스크 동기 flush를 보장하지 않는다. 따라서 프로세스가 저장
tick 사이에 강제 종료되면 마지막 월드 저장 이후의 변화가 함께 롤백될 수 있다. 정상 저장·재시작에서는
결정과 효과 receipt가 유지된다. 강제 종료에도 단 한 건도 잃지 않는 보장이 필요해지면 별도의
write-ahead journal이 추가로 필요하며 v1 완료 범위에는 포함하지 않는다.

## 13. 예약과 연쇄 처리

~~~java
record ScheduledStorySignal(
    UUID scheduleId,
    ResourceLocation targetEventId,
    StoryScopeKey scopeKey,
    Optional<UUID> initiatingPlayerId,
    long dueGameTime,
    StoryEventInstanceId causeInstanceId,
    ResourceLocation causeEffectId
) {}
~~~

- `dueGameTime = overworld.getGameTime() + delayTicks`
- 현실 시각은 저장하지 않는다.
- 서버 시작 시 dueTime priority queue를 재구성한다.
- tick마다 가장 이른 항목만 확인하고 한 tick 최대 64개를 처리한다.
- 한 tick StorySignal 최대 256개, 사건 연쇄 깊이 최대 32를 기본 상한으로 둔다.
- 상한을 넘은 신호는 버리지 않고 다음 tick으로 넘기며 반복 순환은 진단 로그로 차단한다.

## 14. Knowledge와 공개

~~~java
record StoryKnowledgeRecord(
    StoryKnowledgeHolder holder,          // PLAYER 또는 ACTOR
    ResourceLocation factId,
    int knownLevel,
    ResourceLocation disclosurePolicyId,
    StoryEventInstanceId sourceInstanceId,
    long learnedAtGameTime,
    long revision
) {}
~~~

- 같은 fact를 다시 배우면 낮아지지 않고 `max(old, new)`를 쓴다.
- 플레이어 지식은 다른 플레이어에게 자동 복사하지 않는다.
- `TRIGGER_TEAM` grant는 인스턴스에 고정된 구성원 각각에게 기록한다.
- `ALL_PLAYERS_CURRENT_AND_FUTURE`는 public player knowledge projection에 기록한다.
- 행위자 지식은 `ACTOR` holder로 저장한다. 세력도 행위자이므로 동일하다.
- 한 신의 지식은 같은 신화·세력이라는 이유만으로 다른 신에게 자동 공유되지 않는다.
- 대화로 정보가 전달되면 서버가 `transfer_knowledge`를 검증하고 플레이어 record를 올린다.

`StoryDisclosureService`의 순서는 다음과 같다.

~~~text
화자가 fact를 아는가?
→ 현재 정책 조건을 서버가 만족하는가?
→ 허용 최대 level 계산
→ WITHHOLD면 아무 의미 정보도 반환하지 않음
→ COVER_STORY면 작성된 위장 정보만 반환
→ 허용된 canonical 문구를 플레이어에게 전달
→ 실제 전달 성공 후 플레이어 knowledge를 해당 단계까지 상승
~~~

AI가 말한 자유 문장을 분석해서 지식 단계가 올랐다고 판정하지 않는다. 전달할 canonical 항목을 서버가
미리 정하고, fallback 또는 AI 연출이 실제 표시된 뒤 receipt로 커밋한다.

## 16. Data reload와 기존 인스턴스

- Definition에는 정규화 JSON SHA-256 fingerprint를 부여한다.
- 아직 결정되지 않은 latched trigger는 reload 후 새 정의로 다시 검사한다.
- `DECIDED` 이후 인스턴스는 저장된 outcome ID와 fingerprint를 유지한다.
- 처리 중인 인스턴스와 현재 정의 fingerprint가 다르면 새 정의로 효과를 재해석하지 않고
  `RECOVERY_REQUIRED`로 닫는다.
- RESOLVED 인스턴스는 정의가 삭제되어도 compact ledger로 남는다.
- 예약 대상 event가 사라지면 schedule을 버리지 않고 `ORPHANED_DEFINITION`으로 관리자에게 노출한다.
- MAIN/ENDING 참조 삭제는 reload 경고가 아니라 오류로 취급할 수 있도록 strict pack 모드를 제공한다.

## 20. 테스트 매트릭스

### 정의 검증

1. 알 수 없는 필드·버전·enum·ID를 거부한다.
2. 없는 actor/location/fact/event/outcome/effect 참조를 거부한다.
3. disclosure 순환과 cover story 누락을 거부한다.
4. MAIN/ENDING의 암묵적 WEIGHTED_ONCE를 거부한다.
5. effectId와 trigger discriminator 중복을 거부한다.
6. reload 한 파일 실패 시 이전 전체 snapshot을 유지한다.

### 상태와 결정

7. 서버/플레이어/팀 scope 인스턴스가 서로 오염되지 않는다.
8. 팀 구성원 snapshot이 사건 뒤 가입·탈퇴로 바뀌지 않는다.
9. 동일 신호 중복이 ONCE 사건을 두 번 만들지 않는다.
10. 가중 결과가 재접속·reload·재시작 뒤 동일하다.
11. 선택 packet 재전송과 낡은 revision을 거부한다.
12. definition fingerprint 불일치 중간 인스턴스가 recovery로 이동한다.

### 효과와 복구

13. canonical effect 하나의 검증 실패가 전체 canonical 변경을 막는다.
14. external effect 재시도가 멱등이고 보상·관계 변화가 중복되지 않는다.
15. outbox 실패가 outcome을 바꾸지 않는다.
16. due schedule이 정확히 한 번 실행되고 오프라인 시간은 더하지 않는다.
17. 연쇄 상한 초과가 서버를 멈추지 않고 다음 tick 또는 recovery로 이동한다.

### 비밀과 공개

18. 사실이 참이어도 지식 없는 플레이어·신 Snapshot에는 들어가지 않는다.
19. 같은 사건을 본 팀원만 명시된 grant를 받는다.
20. WITHHOLD와 조건 미충족은 닫힌다.
21. COVER_STORY는 작성된 위장 문구만 반환한다.
22. 실제 전달되지 않은 지식은 플레이어 record에 올라가지 않는다.

### 성능

23. 신호 하나가 전체 actor/event를 순회하지 않고 역색인 후보만 평가한다.
24. 800 actor, 5,000 event 정의에서 무관 신호 평가 건수가 0에 가깝다.
25. priority queue가 아직 먼 schedule 전체를 tick마다 순회하지 않는다.

## 21. 완료 기준

- 루브라스 예시의 7단계가 AI 없이 처음부터 끝까지 진행된다.
- 플레이어 부재 중 3~5단계가 LLM 호출 없이 서버 상태로 확정된다.
- 실제 사실, 플레이어 지식, 각 행위자 지식과 공개 정책이 분리된다.
- 메인/엔딩은 작성된 조건·선택으로, 명시적 사건만 1회 확률로 결정된다.
- 재접속·정상 재시작·reload가 이미 결정된 outcome을 바꾸지 않는다.
- 새로운 actor/fact/event/presentation을 Java 재컴파일 없이 데이터팩으로 추가할 수 있다.
- 04가 설치되지 않거나 Ollama가 꺼져 있어도 작성된 정식 문구와 사건 진행이 정상이다.
- GameTest, 빌드, 전용 서버 부팅과 실제 멀티플레이 scope 점검이 통과한다.

## 22. 구현 시 금지 사항

- `InteractionSignal`을 플레이어 없는 세계 사건 버스로 억지 재사용하지 않는다.
- Runtime Fact를 정적 Lorebook에 현재 사실처럼 덮어쓰지 않는다.
- AI 문장을 파싱해 fact, outcome, 보상 또는 관계 수치로 실행하지 않는다.
- 대화할 때마다 확률을 다시 뽑지 않는다.
- actor 위치와 별도 `location_occupied` fact를 수동으로 이중 관리하지 않는다.
- 처리 중 definition이 바뀌었을 때 새 효과를 조용히 적용하지 않는다.
- 핵심 분기가 콘텐츠를 영구 제거한다면 대체·복구 사건 없이 배포하지 않는다.

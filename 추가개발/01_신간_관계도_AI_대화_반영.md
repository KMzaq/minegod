# 신 간 고정 관계도를 AI 대화에 반영

## 구현 결과 (2026-09-01)

- AI 대화의 일반 발화·관계 발화·즉석 상호작용 경로에 정적 `social_relations` 조회를 연결했다.
- 서버가 허용한 현재 참가자(현재 최대 두 신) 사이에서만 `화자 → 상대` 방향 태그를 전달한다.
- 정적 관계와 동적 현재 관계를 별도 구역으로 전달하며, 태그를 대사에 그대로 노출하거나 관계
  주제를 억지로 꺼내지 않도록 프롬프트에 제한을 추가했다.
- 다중 신 대화 서비스는 한 플레이어와 1~2명의 명시된 신을 허용한다.
- 관계 정보를 근거로 AI가 Secondary God을 자동 선정하거나 참가자를 추가하는 기능은 넣지 않았다.
- 관계 데이터가 없으면 기존처럼 빈 관계 Context로 정상 대화한다.

실제 `social_relations` 운영 데이터와 Gemma4 실응답 검증은 사용자가 신 프로필·관계도를 전달한 뒤
진행한다. 메인 모듈·AI 응답 모듈·Content Registry 전체 빌드와 183개 필수 GameTest를 통과했다.

## 목적

`MythAI Content Registry`가 이미 로드하는 정적 신 간 관계 정보를 실제 AI 대화 Context에 포함한다.
두 신이 같은 대화나 사건에 참여했을 때 부모·자식·연인·숙적·주종 등의 관계가 말투와 태도에
자연스럽게 반영되도록 하는 것이 목표다.

이 기능은 **변하지 않는 신화적 관계**를 다룬다. 플레이 중 변화하는 신 간 관계는
`02_동적_신간_관계_시스템.md`의 별도 범위다.

## 작업 전 상태

- 콘텐츠 레지스트리에 `social_relations` JSON 로더와 검증기가 구현되어 있다.
- 관계는 `participantA`, `participantB`, `aToBTags`, `bToATags`로 방향을 구분한다.
- `AiContentRegistry.socialRelationTagsFor(sourceGodId, targetGodId)` 조회 API가 존재한다.
- 동일한 신 쌍의 중복 정의와 존재하지 않는 God ID는 reload 과정에서 거부된다.
- 현재 콘텐츠 폴더에는 실제 `social_relations` 데이터가 없다.
- 현재 AI 응답 모드에는 위 조회 API를 호출해 프롬프트에 넣는 소비 경로가 없다.
- 자동 다중 신 참가자 선정도 아직 완성된 기능이 아니다.

## 콘텐츠 형식

경로:

```text
mythai-ai-content-registry/src/main/resources/data/<namespace>/mythai_ai/social_relations/*.json
```

예시:

```json
{
  "schemaVersion": 2,
  "participantA": "mythictrpg:greek_olympian_zeus",
  "participantB": "mythictrpg:greek_olympian_athena",
  "aToBTags": ["RT_FATHER", "RT_BLOOD_RELATION"],
  "bToATags": ["RT_CHILD", "RT_BLOOD_RELATION"]
}
```

## 구현 범위

### 1. 관계 데이터 작성

- 전달받은 관계도를 God ID 기준의 방향성 쌍으로 정규화한다.
- 한 방향에 복수 관계 태그를 허용한다.
- 관계 태그로 표현하기 어려운 구체적인 사연은 Lore에 작성한다.
- 관계 사실을 각 신 프로필에 중복 기록하지 않는다.
- 관계도에 존재하지만 God Definition 또는 AI 프로필이 없는 신을 별도로 보고한다.

### 2. AI Content Bridge 확장

- AI 응답 모드가 Content Registry의 관계 조회 API를 사용할 수 있도록 반사 경계 또는 공개
  호환 API를 추가한다.
- 현재 Interaction에 실제로 포함된 신 쌍만 조회한다.
- 방향을 지켜 `화자 → 상대` 관계 태그만 해당 화자의 Context에 넣는다.
- 참가자가 한 명이면 신 간 관계 Context를 생성하지 않는다.
- 관계 데이터 조회 실패가 전체 대화를 실패시키지 않도록 빈 관계로 안전하게 fallback한다.

### 3. 프롬프트 구성

권장 Context 예시:

```text
[STATIC RELATIONSHIPS]
- speaker=mythictrpg:zeus, target=mythictrpg:athena
  tags=RT_FATHER, RT_BLOOD_RELATION
- speaker=mythictrpg:athena, target=mythictrpg:zeus
  tags=RT_CHILD, RT_BLOOD_RELATION
```

- 태그를 기계적으로 대사에 반복하지 말고 태도 결정에만 사용하도록 지시한다.
- 고정 관계는 현재 감정이나 동맹 상태를 의미하지 않는다고 명시한다.
- Lore의 구체적 사건과 관계 태그가 충돌하면 콘텐츠 오류로 처리하고 임의로 해석하지 않는다.
- 전체 관계도를 넣지 않고 현재 참가자 사이의 관계만 넣는다.

### 4. 다중 참가자 경계

- 첫 단계에서는 관리자 명령이나 명시적으로 지정된 참가자 대화에서 검증한다.
- 자동 Secondary God 선택은 별도 기능으로 유지한다.
- AI가 관계도를 근거로 허용되지 않은 참가자를 새로 추가하지 못하게 한다.
- 최종 참가자 목록은 계속 MythicTRPG 서버가 결정한다.

## 예상 수정 위치

- `mythai-ai-content-registry/.../mythai_ai/social_relations/`
- `mythai-ai-content-registry`의 공개 조회/호환 계약
- `mythai-ai-response`의 Content Registry bridge
- `mythai-ai-response`의 Context 조립 및 프롬프트 생성부
- 필요 시 `mythictrpg-main`의 bounded Conversation Snapshot 계약

## 테스트 계획

1. 양방향 관계 태그가 방향에 맞게 조회되는지 검증한다.
2. 동일 신 쌍 중복 파일과 존재하지 않는 God ID가 reload에서 거부되는지 검증한다.
3. 단일 신 대화에는 관계 Context가 포함되지 않는지 검증한다.
4. 두 신 대화에는 두 방향 관계가 뒤바뀌지 않고 포함되는지 검증한다.
5. 관계가 없는 신 쌍도 정상 대화할 수 있는지 검증한다.
6. 관계 데이터만으로 AI가 새 참가자나 게임 상태 변경을 제안하지 못하는지 검증한다.
7. 실제 Gemma4 응답에서 관계가 자연스럽게 반영되되 태그 문자열이 노출되지 않는지 확인한다.

## 완료 기준

- 실제 `social_relations` 데이터가 reload 검증을 통과한다.
- 현재 대화 참가자 사이의 방향성 관계만 bounded Context에 들어간다.
- 관계 정보가 없는 경우 기존 단일 신 대화 동작이 변하지 않는다.
- AI가 관계 정보를 참가자 선정이나 authoritative 상태 변경에 사용하지 못한다.
- 자동 테스트, 두 모드 빌드, 전용 서버 reload와 대화 스모크 테스트가 통과한다.

## 주의점

- `R_*`는 플레이어와 신의 현재 관계 단계이며, `RT_*`는 신 간 고정 관계 태그다. 혼용하지 않는다.
- 혈연이면서 숙적인 것처럼 복수 태그가 동시에 존재할 수 있다.
- 모든 신의 전체 관계도를 매 요청에 넣으면 Prompt가 폭증하므로 절대 사용하지 않는다.
- 고정 관계 태그는 현재 우호·적대 수치를 대신하지 않는다.

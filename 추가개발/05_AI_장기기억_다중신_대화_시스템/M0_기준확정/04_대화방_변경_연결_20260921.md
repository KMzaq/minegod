# 대화방 변경 반영 — M0 후속 연결 기준

2026-09-21 / 개발 게임 1.0.13·AI 0.1.14 / 기존 방 연결 보완 완료, 신규 M1 저장소 미착수·미배포.

후속 상태: 사용자 요청으로 같은 버전 JAR의 [서버 적용](../../../docs/ROOM_RECORDING_RELEASE_20260921.md)을 완료했다. 서버 부팅/실제 플레이는 검증하지 않았으며 신규 M1~M7 완료를 의미하지 않는다. 아래는 연결 설계/구현 시점의 경계를 보존한다.

이 문서는 2026-09-20 M0 이후 달라진 채팅 연결점을 정리한다. 기존 M0의 조사·보존 CSV는 역사적 기준으로 유지한다. 현재 게임 동작은 [대화방 가이드](../../../docs/CONVERSATION_ROOMS.md), 이번 코드·검증은 [연결 보완 결과](../../../docs/ROOM_RECORDING_INTEGRATION_20260921.md), 최종 신규 저장 계약은 [02 공통 계약](../02_공통계약과_데이터모델.md)을 따른다.

## 1. 기존 기준에서 바뀐 점

| 항목 | 현재 연결 기준 |
|---|---|
| 대화의 단위 | `ConversationRoomLedger`가 발급한 room UUID·long revision·turn lease. 플레이어/신 쌍이나 UI 선택값으로 하나의 세션을 추정하지 않음 |
| 병행·규모 | 같은 플레이어/신의 공개방 1곳 + 여러 비밀방. 방당 최대 64플레이어·16신, 플레이어당 64방·서버 256방. 기존 개인 journal 청중은 여전히 16명 제한 |
| 입력 | 공개 일반 채팅, 비밀 `/s`, H 선택 화면. G는 HUD 숨김이며 종료/기록 off가 아님 |
| 출력 | 게임이 확정한 대사를 공개 전체 온라인/비밀 참가자에게 전송. 신 HUD는 참가자에게 페이지별 전송 |
| 기록 정책 | STANDARD/TEST_RECORDING은 허용 경로, TEST_EPHEMERAL은 새 영속 대화/진단/기억 금지. 기존 자료 읽기와 현재 RAM history는 유지 |
| 장기 기억 | 기존 journal/ExperienceAccess를 명시적 방 context로 호출. 공개/다중 신으로 관찰·소문 읽기 권한을 확대하지 않음 |
| 그룹 생성 | 현재 한 턴 한 신. M6는 기존 방 위에 순차 Primary/Secondary를 추가하는 단계이며 방 원장을 새로 만들지 않음 |

기록 off는 후속 채팅 변경에서 확정된 예외다. 최초의 “우선 전체 기록”을 이유로 이를 우회하지 않는다. 일반 플레이어 행동 원장·주시 기록은 기존 게임 정책대로 별도 유지한다.

## 2. 이번에 구현한 수집 연결

`ConversationRooms.publishPlayer/publishGod → RoomDialoguePublisher → RoomDialogueEvent → RoomConversationEngine.dialoguePublished → RoomDialogueLog.published`

- 모델 요청이 아니라 게임이 수락/출력한 발화를 기준으로 통지한다. 초기 Encounter의 신 대사와 LLM 없이 처리한 플레이어 동의 발언도 같은 경로를 쓴다.
- 논리 발화마다 message UUID 하나를 발급하고 같은 대사의 참가자/HUD 복제에서 재발급하지 않는다. room UUID/revision, optional turn UUID, 시각, 화자, 원문, 참가자/신, 실제 서버 전송 결과를 불변 snapshot으로 넘긴다.
- 온라인 수신자별 chat 전송/HUD 성공 페이지 수를 구분한다. 실패·오프라인·모든 표시 차단은 성공 receipt로 꾸미지 않는다. 플레이어 본인의 수락 입력은 본인 채팅을 숨겨도 기록할 수 있다.
- AI의 기존 respond/delivered에서 참가자 TXT를 다시 쓰던 경로는 제거했다. 진단과 기존 개인 기억 후처리 자체는 유지하되 on/off와 게임 현재성을 다시 검사한다.
- observer/디스크 쓰기 실패가 이미 일어난 게임 발화나 보상을 되돌리지 않는다. 실패는 서버 경고에 남는다. 영속 멱등 transaction/누락 coverage는 아직 M1~M2 대상이다.

이 단계의 TXT는 관리용 참가자별 사본이다. 공개 관전자에게 새 TXT를 복제하지 않는다. 이벤트에는 공개 전송 결과가 있지만 이 정보를 전체 RAW/신의 청취 권한으로 저장하는 새 DB는 아직 없다. 일반 `/msg`, 바닐라/FTB 팀, 방 밖 스토리, 시스템이 직접 보내는 동의 안내 등 모든 출력에 hook를 달았다는 뜻도 아니다.

## 3. 방 이동과 근거 철회

- `HistoryLine.sourceRoomId`를 원래 방으로 유지한다. 병합·분리 시 내용의 컨테이너만 바뀌며 이전 청중/참가 신 제약도 그대로 남는다.
- 일반 응답과 분리 판단 모두 원래 방의 관찰·소문 근거를 검사한다. 새 방에 provenance가 없다는 이유로 이전 대사를 무조건 안전한 일반 대화로 취급하지 않는다.
- 비동기 생성 전에 근거 reference를 동결하고 최종 적용 시 다시 확인한다. 분리 판단 중 근거가 철회돼도 무리 선택 결과를 적용하지 않는다. 과도한 근거 수는 보수적으로 거부한다.
- 방 무효화는 기존 provenance를 즉시 삭제하지 않는다. 복사된 과거 대사가 살아 있을 수 있어 종료 시점까지 철회 검사가 필요하다. 장기 source/message 계보의 영속 저장은 M3에서 확장한다.
- 응답 bundle은 현재 room/revision/turn, 선택된 신, 비어 있지 않은 대사를 게임이 검증한 뒤 전달한다. 다른 신 대사 일부만 건너뛰고 전체 bundle을 전달 완료로 처리하지 않는다.

## 4. M1~M3에서 이어받을 경계

1. **M1:** 월드/dataset/epoch·SQLite·합산 100GB·재시작/손상·quota 예약을 구현한다. 현재 TXT에는 world/dataset 연결이 없으므로 임의로 새 DB 원본으로 import하지 않는다. 구 시험 데이터는 보존·제외하고 새 dataset 시작 경계를 둔다.
2. **M2:** 새 방 이벤트를 입력 adapter로 재사용한다. 수신자별 실제 표시 view와 성공한 HUD part의 내용/순서, 영속 멱등 message/receipt, 모든 지원 채널 및 coverage를 완성한다. 현재 페이지 수만으로 받은 내용을 추정하지 않는다. 신규 관리 로그를 유지한다면 world/dataset별 파일 registry에 연결해 quota에 합산하고, 전환 뒤 무제한 이중 writer를 남기지 않는다.
3. **M3:** 플레이어별 행동 원본은 게임 원장에 유지한다. 신에게는 주시 증명/허용 소문 참조만 제공한다. `SocialRuntime`의 생성/설득 회복을 방별 lease·실제 신·청중·off 정책으로 옮기고, 게임발 퀘스트 완료/평가의 자동 AI 연출은 명시적 목적지로 연결한다. 플레이어 단일 세션이나 선택된 UI 방으로 fallback하지 않는다.

현재 TXT의 길이/queue 한도, 개인 journal의 1,200자·청중 16인 등 기존 제한이 모두 해제된 것은 아니다. 새 RAW의 무기한·100GB 목표와 구 저장소 제한을 구분한다. 서버 전송 성공은 클라이언트 열람/인지 확인도 아니다.

## 5. M6와 검증 원칙

새 순차 생성의 초기 1플레이어·2신 시험 범위 밖에서는 기존 한 턴 한 신 응답을 유지한다. 이미 있는 N플레이어·M신 참가/초대/병합/분리를 거절하거나 축소하지 않는다. 다른 방의 같은 신/플레이어, 선택 변경, 동의 처리, 근거 철회, stale 응답, 기록 on/off를 각각 회귀 검사한다.

이번 오프라인 검사는 [결과 문서](../../../docs/ROOM_RECORDING_INTEGRATION_20260921.md)에 기록했다. 실제 다인 서버·Ollama·HUD·서버 재접속 검증과 배포는 하지 않았다. 다음 설계 단계는 M1이며, 이번 연결 보완을 M1~M7 완료로 세지 않는다.

# 07. Primary/Secondary와 다인·다신 대화

## 1. 기존 기능 보존과 초기 범위

2026-09-23 개발판은 공개/비밀 병행방의 최대64플레이어·16신 참가를 유지하면서 1플레이어·2신에서 제한된 순차 반응을 선행 연결했다. 기존 journal 기반 호환 구현이며 아래 신규 RAW/KnowledgeReceipt/M5 검색까지 구현한 것은 아니다. [재통합 기록](../../docs/ORIGINAL_GOALS_REINTEGRATION_20260923.md), [현재 대화방](../../docs/CONVERSATION_ROOMS.md), [기존 다인 퀘스트 계약](../../mythictrpg-main/docs/QUEST_PARTICIPATION_GUIDE.md)을 따른다.

새 **Primary/Secondary 순차 생성 기능**만 먼저 플레이어 1명·신 최대 2명으로 검증한다. 신규 방 원장이나 병행 세션 엔진을 만들지 않고 기존 roomId/revision/turn lease와 기록·검색 adapter에 붙인다. 이는 초기 시험 규모이지 기존 방의 참가 상한이 아니다.

초기 시험 범위를 벗어난 방은 기존 한 턴 한 신 경로를 유지하고 새 Secondary 생성만 활성화하지 않는다. 참가를 막거나 기존 플레이어/신을 자동 퇴장시키지 않는다. 새 순차 생성의 N플레이어·M신 적용은 별도 수용 시험 뒤 확장한다.

## 2. 발언권과 권한

| 역할 | 발언 | 초기 새 경로의 게임 Proposal |
|---|---|---|
| Primary | 현재 턴의 주 응답, 한 명 | 기존 서버 action scope로만 가능 |
| Secondary | 필요할 때 짧은 보조 반응, 최대 한 명 | 불가. 다른 신의 보상/퀘스트를 대행하지 않음 |
| LISTENER | 게임이 허용한 청취 | 없음 |
| OUTSIDE | 대화 참가/청취 근거 없음 | 없음 |

Primary는 신의 위계/전투력/관계 우열이 아니라 **대화 진행 역할**이다. 같은 신이 계속 Primary일 필요는 없다. 다만 모델이 자기 마음대로 참가자를 추가하거나 currentGod/action scope를 바꾸지는 못한다.

Secondary가 자신의 퀘스트 등 실제 행동을 맡아야 한다면 게임이 다음 턴의 Primary/action owner를 변경한 후 수행한다. 발언 문자열의 이름만 바꾸거나 Primary의 action scope로 실행하지 않는다. 이 제한은 신규 경로에 한정하며 기존 지원 액션을 무관하게 삭제하지 않는다.

## 3. 발언 계획

게임은 eligible gods와 현재 대화 목적을 제공한다. 선택 우선순위는 플레이어가 명시적으로 부른 유효 참가 신 → 현재 처리 중인 게임 상호작용 소유 신 → 현재 Primary 유지다. 중의적인 호칭/유효하지 않은 대상이면 임의 신을 호출하지 않는다.

Secondary는 모든 턴에 의무 발언하지 않는다. 직접 지목, 자신이 관련된 공개 주제, 성격/관계상 실제로 의미 있는 짧은 반응이 있을 때만 선택한다. 모델이 제안한 발언 계획은 game allowlist로 검증한다. 새 참가자 소환이나 자율 무한 신끼리 대화는 없다.

초기 한 사용자 턴의 상한은 Primary 한 번 + 선택적 Secondary 한 번이다. 이는 한 문장 제한이 아니며 화자별 실제 대사는 기존 HUD 순차 출력 정책을 따른다. 반복 끼어들기/대답 가로채기 방지 cooldown은 기능 시험값으로 관리하고 신별 정식 성격 수치로 확정하지 않는다.

## 4. 순차 생성과 실제 출력

1. 입력을 수락하고 turn/participants/audience snapshot을 동결한다.
2. 게임이 Primary를 승인하고 해당 신의 기억·공개 지식으로 context를 구성한다.
3. Primary를 생성하고 게임이 세션·근거·권한을 재검증한다.
4. 기존 Gateway가 제안의 확인 대기/실행/거절을 처리한다. 대사는 실제 결과 이상을 실행 성공으로 말하지 않게 기존 정규화/피드백을 유지한다.
5. 승인된 Primary 대사만 전달·기록한다.
6. Secondary가 여전히 필요한 경우 **이미 전달된 공용 대사**와 자신의 허용 기억으로 새 context를 만든다.
7. Secondary 생성·재검증·전달. Primary의 미출력 초안·비밀 생각·비공개 constraints는 전달하지 않는다.
8. 실제 수신자에게만 KnowledgeReceipt를 만들고, 모델 실패/미출력 발언은 기억으로 편입하지 않는다.

처음부터 둘을 병렬 생성하면 Secondary가 실제 Primary 응답/게임 결과를 못 보는 문제가 생기므로 초기 설계는 순차다. 지연이 길어지면 Secondary를 생략한다. Primary 생성 실패 시 계획된 Secondary를 주 화자처럼 자동 실행하지 않고 턴을 종료하거나 게임이 새 턴으로 재계획한다.

## 5. 한 대화의 턴 직렬화

공유 세션에는 단일 turn arbiter를 둔다. 여러 플레이어가 동시에 보내면 서버 수락 순서로 발언을 기록한다. 응답 중 새 입력은 bounded 대기 또는 명시 중단 규칙으로 처리하고, 어느 경우인지 출력/기록에 남긴다. 무제한 큐를 만들지 않는다.

새 입력이 현재 턴을 supersede하면 늦은 Primary/Secondary·소문 설득 결과를 적용하지 않는다. 다음 턴으로 넘길 입력과 이미 처리한 입력의 cursor를 분리한다. 큐가 가득 차 응답 요청은 거절해도 실제 전달된 채팅 원문은 RAW에 남길 수 있다.

퀘스트 동의 버튼/명령은 기존 offerId·participant 검증을 먼저 따른다. 일반 대화 순서를 바꿔 네/아니요를 다른 제안에 적용하지 않는다. 확정된 퀘스트 roster는 대화 참가자 변경과 별개다.

## 6. 청중·화자 변경과 비동기 격리

join/leave, 로그아웃, 명시 대화 종료, 신 교체, 정책 reload, 관련 근거 철회에 따른 generation/revision 검사를 유지한다. 새 공유 세션에 합류 전 사적 히스토리를 붙이지 않는다.

출력 직전 검증 키는 world/dataset/runtimeEpoch/conversation/generation/turn/speaker/audienceRevision과 사용한 근거의 관련 revision이다. 플레이어 UUID만으로 진행 턴을 찾거나 같은 God ID라는 이유로 서로 다른 세션을 합치지 않는다.

신마다 해당 플레이어의 affinity와 QuestConstraint/RewardConstraint/validator feedback을 따로 조립한다. 여러 플레이어가 있으면 질문자/게임 대상/전체 청중을 구분한다. A에게 지급할 보상을 B의 프롬프트에서 확정하거나 FTB 팀 공유를 개인 수신권으로 쓰지 않는다.

## 7. N플레이어·M신의 순차 생성 확장

DB와 DTO는 처음부터 actor 목록과 방향 있는 subject 링크를 사용한다. Primary/Secondary는 역할이며 `god1`, `god2` 고정 컬럼을 만들지 않는다. 플레이어별 사적 분기·신별 제안은 별도 scoped request로 분리할 수 있어야 한다.

확장 시 최대 발언 신 수, fairness, 한 턴 총 지연, 공동 퀘스트 대상 선택을 추가 수용 시험한다. 현재 64플레이어·16신 참가 상한이 그 규모의 실제 모델 지연/자연스러움 검증 완료를 뜻하지 않는다.

이 단계에서 기존 신 ID·등장/인식·참가자 감지 시스템을 바꾸지 않는다. 확정된 새 방 연결은 [M0 후속 기준](M0_기준확정/04_대화방_변경_연결_20260921.md)을 적용하고 같은 기록·기억 계약을 유지한다.

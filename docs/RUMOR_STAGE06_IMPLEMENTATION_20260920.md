# 6단계 — 추후 전서구 엔티티를 위한 소문 연결 기반

2026-09-20 / 개발 게임 **1.0.9**, AI **0.1.11** / 기본 OFF·미배포 / 실제 엔티티는 후속 제작

## 1. 요청과 완료 범위

사용자는 전서구 엔티티를 나중에 제작해 넣고, 스폰 이벤트도 별도로 만들며 **자동 스폰·재생성은 우선 OFF**로 하라고 요청했다. 이번에는 임시 동물/가짜 전서구, 엔티티 등록·모델·렌더러, 스폰 명령·타이머·구조물 배치를 만들지 않았다. `CourierRumorService`는 **이미 월드에 추가된 실제 엔티티**를 미래 콘텐츠가 연결하는 게임 측 API다.

[선행 점검](RUMOR_STAGE06_PREFLIGHT_20260920.md)의 소스/오프라인 기반을 재사용했다. 1~5단계의 실제 Minecraft 종단·1/4/6인 품질·부하 수용은 여전히 미완료다. 이번 완료는 **엔티티 후속 제작을 전제로 한 소스 연결·오프라인 검증**이며, 6단계 전체 운영 완료나 다음 7단계 승인이 아니다.

- 전서구→관찰 대상 UUID를 명시적으로 연결한다. A의 전서구를 B가 사냥해도 **A만 차단**한다.
- 이미 수신한 소문은 유지한다. 미전달분은 폐기하고 새 개체 연결 후에도 재전송하지 않는다. 긍정/부정 모두 같은 차단을 적용한다.
- 직접 주시/개인 기억과 소문 경로를 분리한다. 신 간 자동 재전파를 추가하지 않는다.
- 대사 참조까지만 연결하며 관계 수치·퀘스트 조건·보상·영구 칭호를 바꾸지 않는다. 수식어는 전언 속 표현이지 게임 보상 태그가 아니다.
- 실제 서버 설정·mods·client-required-mods·월드·기억·로그는 변경하지 않았다. 서버는 게임1.0.2/AI0.1.3/콘텐츠0.1.0 그대로다.

## 2. 구현된 연결과 권한

| 계층 | 이번 구현 | 하지 않는 일 |
|---|---|---|
| `CourierSettings` | OFF 기본, 명시적 엔티티 타입/이벤트 규칙/수신 신/공개 정책, 크기·범위 제한 | 기본 신화권/반경/발행 기준을 정사로 생성 |
| `CourierRumorService` | 서버 스레드, 기존 개체 연결, 동일 차원·거리·시야·로드된 경로 검사, 사망 후 확인, 제한된 전달 | 스폰/재생성/청크 강제 로드/전체 채팅 감청 |
| `CourierProof` + `RumorLedger` | 실제 게임 생산자 source ID/revision, 관찰 epoch·정책 지문·발췌 hash, 후보/발행/대기/수신 분리 | AI가 목격 사실이나 수신자를 발급 |
| `CourierEngine` | 중복/쿨다운/최대 대기 tick/늦은 결과/대상별 차단, 재시작 후보 조회, 신별 수신 필터 | 모델 호출·무한 작업 큐·다른 신 자동 공유 |
| AI 대화 소비 | 해당 신이 실제 받은 전언만 첫인상/관련 질문에 사용, 관심·유보 메타데이터, 철회 가능한 대화 출처 | 소문을 직접 경험/플레이어 인정/검증된 사실로 저장 |

신별 `IGNORE`는 프롬프트에서 제외, `CAUTIOUS`는 유보적인 전언, `INTERESTED`는 관심 대상이라는 힌트다. 어느 것도 무조건 믿으라는 규칙이 아니다. 신의 성격·현재 관계를 유지하고 수식어를 매 턴 강제로 반복하지 않도록 기존 기억 사용 지침을 보완했다. 실제 말투·오해 해석 품질은 LLM 미호출로 아직 확인하지 않았다.

새 소문을 인용한 NPC 대사는 영구 원문 journal의 독립 사실로 재저장하지 않고 세션 내 출처를 유지한다. 근거 철회·정책 변경·공개 범위 변경 후에는 해당 대사와 그 후속 인용을 다음 프롬프트에서 제외한다. 세션/턴/청중 검사는 기존 경로를 유지한다. 관찰과 소문을 함께 쓰는 경우에도 출처 상한64개 안에 들어가도록 과거 참조는 최대62개다. 이미 저장된 옛 NPC 원문을 임의 삭제/정리하지는 않았다.

## 3. 나중에 엔티티·스폰 이벤트를 붙이는 방법

1. 별도 콘텐츠에서 전서구 `EntityType`과 동작/외형/사망을 구현한다. 엔티티 타입 ID는 실제 등록된 ID를 사용한다. 현재 예제에는 가짜 ID나 바닐라 새를 대신 등록하지 않았다.
2. 별도 허가 후 맞는 게임/AI JAR을 배포하고 시험 월드에서 `RUMOR_TEST`와 `config/mythictrpg/rumor-courier.json`을 명시적으로 켠다. 기본 파일은 [OFF 예제](examples/rumor-courier.example.json)다. 이번에는 서버에 복사하지 않았다. `automaticSpawn`/`automaticRespawn`을 true로 쓰면 지원하지 않는 설정으로 전체 OFF 처리한다.
3. 미래 스폰 이벤트가 개체를 월드에 추가한 **후**, 서버 스레드에서 `CourierRumorService.bindExisting(subject, courier)`를 호출한다. 대상은 실제 접속 중 플레이어, 개체는 살아 있고 로드된 허용 타입이어야 한다. 한 플레이어의 활성 바인딩은 덮어쓰지 않는다. `binding(server, subjectUUID)`로 기존 연결을 읽을 수 있다.
4. 실제 게임 생산자가 사건/발화의 중요성과 공개 가능 범위를 승인한 경우에만 `captureApproved(...)`를 호출한다. 같은 tick의 실제 위치·살아 있는 연결 개체·거리/차원/가림을 검사한다. 숨은 공간/사적 대화 등 **공개 승인 판단은 호출자 책임**이며, 단순 시야 통과만으로 사적 정보를 공개할 수 없다. 물리 벽 검사와 신전/스토리상의 정보 차폐 정책은 같은 것이 아니다.
5. 일반적인 `LivingDeathEvent`는 취소 가능한 시도만 예약하고 tick 종료 시 최종 취소 여부와 실제 사망 상태를 재검사한다. 취소·청크 언로드·로그아웃은 사망으로 처리하지 않는다. 커스텀 엔티티가 표준 생명주기를 우회한다면 실제 사망 후 `confirmDeath(server, courier)` 어댑터를 연결한다. 사망자와 관찰 대상 귀속에 사냥자/FTB 팀을 사용하지 않는다.
6. 재생성은 실행하지 않는다. 후속 명시적 스폰 이벤트가 새 UUID의 개체를 만든 뒤 차단된 대상에 다시 `bindExisting`하면 새 epoch로 재개할 수 있다. 임의로 사라진 개체를 사망/재생성으로 추정하지 않으므로 비표준 삭제·월드 이동 등은 미래 엔티티 제작 때 별도 확인해야 한다.

`captureApproved` 인수는 실제 대상/개체, `sourceId`, `sourceRevision`, 사건 type ID, `GAME_EVENT` 또는 `DISCLOSED_DIALOGUE`, 사건 위치, **승인된 짧은 발췌**, 언급 대상 집합, 공개 가능한 플레이어 청중이다. 복합 대상 발췌는 현 단계에서 거절한다. 전체 로그/통계/사적 대화/시스템 프롬프트를 통째로 입력하지 않는다. 관찰 대상 이외 인물을 인수에서 누락해 개인정보 경계를 우회하지 않도록 게임 생산자가 먼저 분리해야 한다.

실제 중요 전투 원장의 별도 상세 기록을 원하면 미래 개체 타입을 `mythictrpg:detailed_battle_targets`에 작성하거나 기존 제작 전투 API를 호출한다. 이번에 바닐라 몬스터 전체를 네임드로 지정하거나 기존 처치 보상을 변경하지 않았다.

## 4. 규칙·후보·전달 계약

`rules[]`의 항목은 `id`, `eventType`, `source`, `dimension`, `radius`, `cooldownTicks`, `maximumAgeTicks`, `receivers`(기존 God ID→수신 태도), `publication`, `authoredText`, `epithet`다. 실제 값은 콘텐츠 제작 시 정한다. 시험 코드의 반경/기간/등장인물은 운영 설정이 아니다.

- `AUTHORED`는 게임이 확인한 `GAME_EVENT`에 작성자가 정한 제한 문구를 발행한다. 실제 제작 콘텐츠가 source를 공급해야 하며 일반 대화를 특정 낙인으로 자동 분류하는 규칙은 허용하지 않는다.
- `CANDIDATE`는 관측 입력만 돌려준다. `pendingCandidates(server, 1..32)`로 재시작 후 유효 후보를 제한 조회할 수 있다. **새 소문 전용 LLM worker/의미 판단기/자동 발행기는 이번에 만들지 않았다.** 미래 후보 생산자는 기존 모델 입장 관리와 취소를 사용하고, 게임 측 발행 승인 후 `publishCandidate`를 호출해야 한다. 모델 원문을 그대로 승인하는 경로가 아니다.
- 후보는 world/root/epoch/정책 지문/정확한 인용 발췌/유효 기한/현재 개체를 확인한다. 이 검사는 출처·권한 검사이지 **주장 문장의 의미가 맞다는 자동 증명은 아니다**. 자연스러운 해석·문화적 금기·큰 업 기준은 콘텐츠 정책과 실제 모델 비교가 필요하다.
- 원본 사건이 무효화되면 생산자가 반환받은 root ID를 `revoke`한다. 발행 전 취소도 tombstone을 남기므로 늦게 도착한 후보가 되살리지 못한다. 사건 원장의 revision을 몰래 읽어 추정하지 않는다. 호출자가 취소 통지를 연결해야 한다.
- 수신자는 작성된 God ID만, 기본 추가 전파 없음. 존재하지 않는 신/언로드 개체는 전달을 보류한다. 게임 시간 기준 만료·정책 변경 시 미전달분을 버린다. 전달 검사량은 tick당 `deliveriesPerTick`(1..32)이며 순환한다. 기수신 정보는 개체 언로드/사망/나이만으로 삭제하지 않는다.
- 현재 서비스는 **명시적 enabled + 기존 RUMOR_TEST 모드**에서만 열린다. RUMOR_TEST의 게임 Proposal·방문 진척·식별 변경 차단은 유지한다. PERSONAL 운영 대화에 몰래 섞지 않는다.

## 5. 저장·보존·복원

- 기존 `mythictrpg_memory_rumor_v1` SavedData 파일 키를 유지한다. 새 목격 증명은 스냅샷 **v2** 안에 원문/주장/대기/수신과 함께 저장한다. source 사건 저장소와의 별도 트랜잭션을 보장한다는 뜻은 아니다.
- v1을 읽을 수 있으며 증명 없는 기존/빈 상태를 OFF로 조회한 것만으로 v2로 올리지 않는다. v2를 읽은 뒤 임의로 v1로 내리지 않는다. 손상/미지원/버전 불일치는 원본 NBT 그대로 읽기 전용 격리한다.
- 항목별 상한4096과 90% 도달 시 서버 알림·관리자 증설 검토 안내를 유지한다. 이 소문 상한은 현재 코드 상수이며 바이트 설정이 아니다. 자동 삭제/아카이브/상한 증설은 하지 않았다. 꽉 찬 저장소는 새 자료를 거절한다.
- LP 소스298개·이전 기반906개·원본 JAR3의 해시를 검증했다. 이번 직전 **2329개**는 `server/backups/before-memory-stage05-20260920-173428-369/`에 별도 보존했다. 라벨은 기존 백업 도구명이며 실제 내용은 이번6단계 직전 상태다. 전체 지형 백업이 아니라 manifest에 포함된 소스/문서/설정/기억/로그/데이터팩/JAR 범위다.
- [이번 delta](rumor-stage06-changes-20260920.csv)와 `dev-tools/Test-RumorStage06.ps1`로 이 작업 변경을 다른 미커밋 수정과 구분한다. 기존 JAR/LP/FTB/콘텐츠/legacy와 무관한 게임 소스는 보존했다. v2 저장 후 옛 LP JAR만 덮어쓰는 하향 복원은 보장하지 않으며 별도 승인된 복원 시험이 필요하다.

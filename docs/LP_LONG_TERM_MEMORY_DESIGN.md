# LP 기반 장기기억·소문·평판 통합 설계안

2026-09-13 설계 개정 / 2026-09-14 기반 단계 구현·검증 및 PERSONAL 서버 세팅 완료

> 후속 승인으로 백업·공통 계약·개인 기억·소문 시험 기반을 구현했다. 현재 소스와 서버 배치 버전은 회상 개선본인 게임 1.0.2 / AI 응답 0.1.3이며 PERSONAL 시험 설정을 준비했다. 서버를 실행하지는 않았다. 오프라인 회상 검사는 통과했지만 모델 비교는 Ollama 연결 실패로 미완료다. [최신 회상 수정 기록](MEMORY_RECALL_TUNING_20260914.md) 참조. 본문은 전체 목표 설계이며 자동 추출·물리 전서구·전파망·게임 효과까지 구현됐다는 뜻은 아니다. 실제 계약/한계는 [기반 구현 가이드](LP_MEMORY_FOUNDATION_GUIDE.md), 배포/복원은 [서버 시험 안내](LP_PERSONAL_MEMORY_TEST_SETUP.md)를 우선한다. 아래 9월 13일 점검 결과는 구현 전 기준이다.

이 문서는 [2026-09-12 개인 장기기억 설계](archive/LP_LONG_TERM_MEMORY_DESIGN_20260912.md)를 대체한다. 기존 문서는 이력이며 현재 구현 지침으로 병행 적용하지 않는다.

사용자 확인 반영: 여러 신화의 다수의 신이 각자의 인식과 관계를 가지는 RPG다. 헤르메스의 전서구를 사냥하면 **해당 플레이어에 관한 소문만 차단**하며 지역 전체나 다른 플레이어의 소문은 막지 않는다. 평소 4~5명, 최대 6명 접속하며 6명 모두 동시에 AI 대화할 수 있다. 동시 요청에 따른 대기는 허용하지만 불필요한 기억 처리로 더 지연시키지 않는다. 중요한 사건·약속은 오래 유지하고 사소한 잡담은 점차 잊는 것이 목표다.

## 1. 목표와 확인한 기준

목표는 모든 대화를 외우는 챗봇이 아니라, 신이 플레이어와 쌓아 온 경험을 기억하는 RPG다. LP의 말투·분류·출력 형식을 유지하고 회상에 필요한 자료만 보완한다. 기억으로 친밀함이나 적대감을 강제하지 않으며 퀘스트·보상·세계의 사실을 AI가 새로 확정하지 않는다.

2026-09-13 개정 시 재확인:

- `dev-tools/Test-LPBuild.ps1` 통과. AI 응답 265개, 콘텐츠 69개 파일 엔트리 및 두 JAR 전체 SHA-256이 LP 원본과 일치한다.
- `server/backups/LP-source-20260912/file-manifest.csv`의 298개 보존 파일 해시 검증 통과. 이 백업과 `server/backups/LP/`는 수정하지 않는다.
- 현재 게임 모드는 유지한다. 게임 전체 소스는 위 LP 소스 백업에 포함되지 않으므로, 향후 게임 계약 수정 전에는 별도 백업이 필요하다.
- 이번 작업에서는 새 LLM 요청, 빌드, 배포, 서버 실행 또는 기억 데이터 변경을 하지 않았다. 아래 성능 수치·상한은 측정 결과가 아닌 초기 실험안이다.

현재 대화 진입은 `MythAiConversationEngine → GodAiDialogueService → AiTestDialogueAdapter`다. 현재 운영 facade는 플레이어 1명·신 1명을 대상으로 한다. 최근 20개 메시지를 세션 메모리에서 보관하고 종료 시 제거한다. 인사 같은 직접 응답, 분류를 생략하는 잡담, 분류 후 생성하는 일반 경로가 있으며 기존 재시도/수정 생성도 있어 항상 AI 호출 1회인 것은 아니다.

예전 `NpcMemoryEngine`, `MemoryRetriever`, `JsonFileMemoryRepository`는 남아 있지만 현재 운영 대화에서 연결되지 않는다. 키워드·태그·중요도·최근성 검색 개념은 재사용할 수 있다. 다만 저장마다 전체 파일을 동기 재작성하며 출처·월드·공개 범위·정정 이력이 부족해 그대로 활성화하지 않는다.

OPELA 실험본의 출처·청중 격리와 정정 검증 아이디어는 참고할 수 있지만, 오버레이·감정 분석·품질 평가·출력 스키마 튜닝을 통째로 재적용하지 않는다.

## 2. 핵심: 경험·전언·평가를 분리한다

| 층 | 내용 | 관리 방식 |
|---|---|---|
| 최근 문맥 | 방금 한 말, 진행 중 화제·놀이 | LP의 최근 20개 메시지 유지. 재접속 연결이 필요한 경우 짧은 직전 세션 메모를 별도 후보로 저장 |
| 개인적 기억 | 플레이어가 말한 취향·두려움·계획, 서로의 약속, 아직 해결하지 않은 대화 | 발언자·원문 근거·시각을 함께 저장. 주장과 객관적 사실을 구분 |
| 공동 경험 | 해당 신의 퀘스트 완료, 건축 평가, 실제로 전달된 중요한 사건 | 게임이 확정한 결과를 토대로 해당 신에게 허용된 경험만 기록. 현재 상태는 게임에서 다시 조회 |
| 전해 들은 소문 | 다른 곳에서 목격된 행동·업적에 관한 이야기 | 게임이 전달을 확정한 신만 알며, 내용의 진실성과 전달 사실을 구분 |
| 신별 평판·대표 수식어 | 신이 그 플레이어를 어떤 사람으로 보는지 | 직접 경험·받은 소문·출처 신뢰·성격·관계로 결정되는 해석. 게임상 효과가 있으면 MythicTRPG가 소유 |

개인 기억은 “내가 직접 겪은 너”, 소문은 “남에게 전해 들은 너”, 평판은 “그것을 바탕으로 내가 보는 너”다. 사건 자체, 사건을 아는 범위, 그 사건에 대한 평가가 서로 다른 데이터다. 수식어는 사실을 덮어쓰는 단일 전역 태그가 아니다.

신 프로필·정적 로어는 콘텐츠 레지스트리에 그대로 둔다. 현재 호감도·인벤토리·퀘스트 진행·스토리 정사는 MythicTRPG에서 읽는다. 이를 장기기억 DB의 독립적인 현재 사실로 복제하지 않는다.

예시:

- “난 수영을 못해” → `플레이어가 수영을 못한다고 말했다`. 게임 능력으로 확정하지 않는다.
- “밀을 가져다줄게” → 대화상의 약속. 퀘스트 수주·아이템 전달 성공으로 저장하지 않는다.
- 게임의 건축 평가 완료 통지 → 평가받은 경험과 당시 결과. 보상을 다시 지급할 근거가 아니다.
- AI가 “성으로 데려다주겠다”고 말함 → NPC가 한 발언. 실제 이동 기능이나 월드 사실로 승격하지 않는다.
- 모욕 후 사과 → 두 사건과 순서를 유지한다. 새 발언으로 과거 사건을 지우거나 자동 호감도 변경을 하지 않는다.

같은 기억의 해석은 신의 기존 성격과 게임이 제공하는 관계 문맥에 맡긴다. 기억 모듈이 모든 신에게 동일한 감정·답변을 지정하지 않는다. LP의 실제 관계 값 연동 범위도 이번 기억 추가만으로 개선됐다고 주장하지 않는다.

## 3. 저장 모델과 생명주기

### 3.1 최소 메타데이터

`memoryId`, `worldId`, `ownerGodId`, `subjectPlayerId`, 원본 세션/턴 식별자, 발언자, 당시 청중, 허용 공개 범위, 출처 종류, 근거 발췌/원문 참조, 발생 순서, 요약, 검색 태그, 정정 관계, 상태, 최근 사용 기록을 둔다.

출처는 최소한 `PLAYER_STATEMENT`, `NPC_UTTERANCE`, `GAME_CONFIRMED`, `RUMOR_RECEIVED`를 구분한다. 소문 기억에는 게임이 발급한 수신 기록·소문 revision의 불투명 참조와 허용된 요약만 연결한다. AI 저장소가 수신자 명단이나 전파 이력을 독립적으로 결정하지 않는다. “이 발언이 실제로 있었다”와 “발언 내용이 사실이다”는 다른 확실성이다. AI 추출기는 게임 확인 등급이나 공개 권한을 만들 수 없다.

상태는 후보·활성·상충·대체됨·보관·삭제를 구분한다. 중요한 기억의 우선순위도 출처와 분리한다. 반복된 거짓말이 중요해질 수는 있어도 반복만으로 게임 사실이 되지는 않는다.

### 3.2 기록

1. 수락한 플레이어 입력은 짧은 원문 기록으로 남긴다. 실제 현재 신에게 전달된 대화 범위만 대상이며 일반 채팅 전체를 수집하지 않는다.
2. NPC 발언은 실패한 생성 초안이나 수정을 위해 폐기한 응답이 아니라 최종 대사·전달 결과를 기준으로 기록한다. 기존 HUD 전달 함수는 결과를 충분히 반환하지 않으므로, 구현 시 전송 수락/대체 채팅 전달을 확인할 연결이 필요하다. 실제 클라이언트에서 읽었는지까지 보장하지는 않는다.
3. 게임 결과는 확정 후 통지에서만 기록한다. 사용자 발언·Proposal 접수·확인 대기는 실행 성공으로 취급하지 않는다.
4. 중요한 부분을 추출하는 AI 작업은 별도 후처리로 실행한다. 대화 생성 JSON에 추가 기억·평가 필드를 요구하지 않는다.
5. 추출 결과는 원문에 근거가 있는지, 주체·부정·인용·시점이 맞는지 검증한다. 모호하면 사실화하지 않고 원문 후보로 남긴다. 검증으로 모델의 의미 해석 오류를 완전히 없앨 수는 없다.

추출이 아직 안 됐더라도 동일 신·플레이어의 권한이 맞는 최근 원문 후보를 제한적으로 검색할 수 있게 한다. 후처리가 끝날 때까지 재접속 기억이 완전히 비는 것을 피한다. 20개 메시지에서 밀려나기 전에 기록하기 때문에 길게 대화해도 저장 후보가 사라지지 않는다.

### 3.3 정정·망각

- “아까 농담이었어”, “이제는 수영을 배웠어”는 관련 과거 진술과 연결한다. 같은 주제라는 이유만으로 기존 모든 기억을 덮어쓰지 않는다.
- 시간에 따른 변화와 정정은 구분한다. 예전 두려움과 현재 극복을 함께 기억할 수 있다.
- 완료된 약속은 현재 미완료 목록에서 제외하되 함께 겪은 경험으로 남길 수 있다. 게임 관련 약속 완료는 게임 확인이 필요하다.
- 답변 대기 중 정정/삭제가 발생하면 revision을 바꾼다. 늦은 요약·색인 결과가 과거 기억을 다시 살릴 수 없게 한다.
- 사용자 선택은 “중요 사건·약속은 오래 유지, 사소한 잡담은 점차 잊기”다. 미완료 약속·중요 공동 경험은 단순 시간 경과나 오래 접속하지 않았다는 이유로 자동 삭제하지 않는다. 반복 잡담은 중복을 합치고 회상 우선순위를 낮춰 활성 기억에서 보관층으로 이동한다. 정확한 보존 기간과 상한은 사용량을 보고 정한다. 기억을 회상했다고 무조건 중요도를 높이지 않는다.
- 개인 발언 정정이 이미 소문을 들은 모든 신의 기억을 즉시 바꾸지는 않는다. 해명·반증도 실제 전달된 범위에서 반영한다. 반면 구현 오류로 잘못 발급된 소문을 운영자가 취소하는 것은 게임 내 망각과 다른 관리 기능이며 파생 평판까지 무효화해야 한다.
- 원문·활성 기억·보관 이력·백업 보존 기간은 따로 정한다. 무기한 원문 보관을 기본 전제로 삼지 않는다. 삭제 기능은 파생 요약·검색 색인까지 함께 처리하고, 이미 만들어진 백업의 잔존 정책도 명시해야 한다.

## 4. 검색과 프롬프트

```text
현재 발화 + 필요한 직전 문맥
  → 월드·신·플레이어·현재 청중으로 먼저 제한
  → 관련 후보 검색
  → 정정·게임 현재 상태·중복·최근 사용 여부 점검
  → 직접 기억·허용된 소문·평판을 합쳐 참고 항목 0~3개
  → 기존 LP 분류/생성 경로에 짧은 참고 문맥으로 전달
```

- 첫 버전은 외부 호출 없는 로컬 검색이다. 기존 키워드·태그 방식을 개선하고 한국어 표기 정규화, 단어 일부 일치, 명시적 대상 ID, 직전 대화의 주제를 함께 사용한다. 특정 발언의 고정 답변이나 끝말잇기 전용 기억 규칙은 만들지 않는다.
- 관련성이 먼저이고 중요도·최근성은 관련 후보 사이의 순위에만 적용한다. “응”, 인사처럼 검색 근거가 약하면 중요한 기억을 억지로 주입하지 않는다.
- 단순 키워드는 “수영을 못한다 ↔ 깊은 강이 걱정된다” 같은 의미 연결을 놓칠 수 있다. 이를 해결했다고 주장하지 않는다. 의미 검색은 별도 실험 단계로 분리한다.
- 초기 통합 예산 제안은 직접 기억·소문·평판을 합쳐 0~3개, 전체 400~800자 내외다. 소문 항목을 기존 기억 예산 바깥에 별도로 무제한 추가하지 않는다. 토큰 수와 지연도 함께 측정해 조정한다. 관련 기억이 없으면 블록 자체를 생략한다.
- 현재 발화·최근 문맥과 중복되는 기억을 제외한다. 같은 기억을 연속 턴마다 꺼내지 않되, 사용자가 직접 다시 묻는 경우에는 억제하지 않는다.
- 필요한 턴에는 분류와 생성이 동일한 인식 snapshot을 본다. 분류 단계에 기억이 전혀 없으면 “그 약속 말인데”를 잘못 해석할 수 있다. 평범한 직접 인사 응답은 유지한다. 다만 처음 만난 신의 소문 기반 첫인상을 표현해야 하는 턴은 예외다. 현재 LP의 고정 인사 경로로는 개인별 첫인상을 표현할 수 없으므로 해당 조건에 한해 기존 대사 생성 경로로 전환하는 제안을 둔다. 이때 기존 0회 호출이 1회 생성으로 늘 수 있음을 성능 검증에서 별도로 보고한다. 추가 소문 분석 호출을 앞에 붙이지는 않는다.
- 기억은 회상 참고자료일 뿐 말투 지시·행동 명령이 아니다. 플레이어가 기억에 남기려 한 프롬프트 명령도 시스템 지침으로 승격하지 않는다.
- 기록만 있고 의미를 확신할 수 없는 경우 임의로 메우지 않는다. 특히 보상·약속의 이행 여부·비밀 공개는 게임 검증 우선이다.

## 5. 누구의 기억인가

- 기본은 월드 + 신 + 플레이어 단위다. 포르투나와 한 사적인 이야기를 데메테르가 자동으로 알지 않는다.
- 당시 누가 들었는지와 지금 누구에게 공개 가능한지는 별개다. 현재 화자에게 알려진 기억이고 현재 모든 청중에게 공개 가능한 경우만 프롬프트에 넣는다. 참가자나 청중을 AI가 추정해 추가하지 않는다.
- 현재 LP adapter는 원래 게임 상호작용의 청중 정보를 충분히 보존하지 않는다. 시작 Context의 실제 청중을 memory context에 전달해야 한다. 알 수 없으면 개인 기억 주입을 생략한다. 다인 청중에서 단지 수신자별로 대화를 나눴다는 이유만으로 사적 대화라고 판단하지 않는다.
- 이번 개정에서 소문 전파를 명시적인 설계 범위에 포함한다. 개인 기억 DB를 다른 신에게 열어 주는 방식이 아니라 게임이 허용한 관찰 → 소문 발행 → 수신자별 전달 확정을 거친다. 허용된 관찰로 생성된 전언만 새로운 수신 범위를 얻으며, 원래 사적 기록의 전체 내용을 공유하지 않는다. 알고 있음과 현재 청중에게 다시 말할 수 있음도 별도 검사한다.
- 현재 Story Snapshot에는 공개를 통과한 문장과 일회성 별칭만 들어간다. 숨은 Fact ID를 기억에 노출하거나 별칭/token을 영구 저장하지 않는다. 스토리 장기 회상에는 재검증 가능한 게임 소유의 불투명 참조 계약이 필요하며, 이것이 없으면 초기 기억 대상에서 제외한다.
- 전서구는 게임이 등록한 별도 관찰자다. 대화 참가 신이나 플레이어 청중 목록에 AI가 임의로 끼워 넣지 않는다. 관찰 가능 거리·차원·가림·상태·대상 식별은 게임 측 관측 정책이 결정한다. 시스템 전용 정보, 귓속말/관리자 채널, 공개하지 않은 스토리 정사를 원문 기록에서 훔쳐 읽는 우회 경로를 만들지 않는다.
- 서버 전체 사건이라고 모든 NPC가 안다고 가정하지 않는다. 레이드 등 아직 미확정 콘텐츠는 향후 게임이 제공하는 관찰·공개 계약이 마련된 뒤 연결한다.

## 6. 속도·저장 안정성

### 응답 중

- 기본 경로에서 기억 추출·임베딩·소문 후보 분석·품질 평가용 추가 모델 호출을 기다리지 않는다. 소문 첫인상에 필요한 직접 인사 → 생성 전환 외에는 LP 기존 호출/재시도 정책을 확대하지 않는다.
- 준비된 로컬 인덱스와 불변 snapshot으로 조회한다. 서버 tick에서 전체 저장소를 읽거나 검색 완료를 기다리지 않는다.
- 검색이 준비되지 않았거나 시간 예산을 넘으면 기억 없이 LP로 진행한다. 예산은 초기 목표 10~20ms 수준으로 두되 실제 측정 후 정하며 보장치로 안내하지 않는다.
- 입력 토큰이 늘어나므로 검색이 빨라도 모델 처리 시간은 증가할 수 있다. 기억이 답변을 길게 유도하는 영향도 따로 측정한다.

### 후처리

- 원문 저장은 제한된 단일 쓰기 큐·순차 journal과 주기적 snapshot을 사용한다. 작은 서버 규모에서는 별도 벡터 DB 서비스부터 도입할 필요가 없다.
- 임시 파일·원자적 교체·백업 snapshot·스키마 검증으로 손상 시 원본을 보존한다. 비정상 종료 시 마지막 미기록분 손실 가능성은 명시하며 저장 실패를 조용히 성공 처리하지 않는다.
- 정상 종료 시 쓰기 큐를 제한 시간 내 비우고, 재시작 시 처리한 원본 ID/sequence 이후부터 후처리를 재개한다. 같은 사건·턴을 중복 기록하지 않는다.
- 초기 자동 요약은 접속자가 없고 모델을 사용하는 다른 작업도 없을 때만 작은 묶음으로 처리하는 보수적인 정책을 제안한다. 접속자가 계속 있다면 후처리가 밀릴 수 있어 원문 검색을 fallback으로 유지한다. 큐·디스크 상한과 보관 정책이 필요하다.
- 현재 `LocalOllamaClient`별 scheduler는 전 서버의 모델 작업을 통합 관리하지 않는다. 단순히 비동기 thread를 추가하는 것으로 대화 우선순위가 보장되지는 않는다. 구현 시 대화·자발적 대사·건축 시각 평가를 포함한 사용 여부를 확인하는 공통 admission 경계가 필요하다.
- 이미 진행 중인 모델 계산을 즉시 중단·선점할 수 있다고 가정하지 않는다. 새 대화 시작 시 신규 후처리 투입은 막되, 이미 시작한 작업의 경합 시간은 측정해야 한다. 경쟁이 크면 자동 후처리를 꺼서 수동 관리 시간에만 처리한다.

### 최대 6명 동시 대화

- 대화 세션 6개를 지원하는 것과 모델 추론 6개를 동시에 돌리는 것은 다르다. 실제 동시 추론 수는 기존 설정과 장비에서 측정한 처리량을 기준으로 정한다. 플레이어 수만 보고 GPU 동시 추론을 6개로 늘리지 않는다.
- 플레이어별 순서와 세션당 진행 중 요청 제한을 유지한다. 공통 모델 사용 경계에서는 foreground 대화가 background 기억 추출·색인보다 우선한다. 한 플레이어의 다량 요청이나 후처리가 다른 플레이어를 계속 밀어내지 않도록 제한한다.
- 기본 후처리는 접속자 0명일 때 수행한다. 접속이 장시간 유지돼 원문 후보가 쌓일 경우에만, 모든 foreground 요청/대기열이 비고 전체 사용자가 충분히 입력하지 않은 유휴 구간에 작은 후처리 1건을 허용하는 선택 모드를 검토한다. 초기 유휴 기준 후보는 60초이며 성능 검증 전에는 기본 활성화하지 않는다.
- 후처리는 한 신·플레이어의 짧은 원문 묶음씩 처리하고 실패 재시도와 시간 상한을 둔다. 처리하지 못한 묶음은 재접속·재시작 후 이어서 처리한다. 오래 열린 세션만으로 후처리를 영구 금지하지 않는 유휴 모드는 별도 검증한다.
- 모든 사용자가 동시에 대화할 때는 준비된 기억만 조회하고 새 요약·벡터 계산은 시작하지 않는다. 이미 실행 중이던 후처리의 잔여 경합은 완전 제거를 약속하지 않는다.
- 비교 검증은 1명·4명·6명 조건으로 나눈다. 총 처리량만이 아니라 플레이어별 응답 대기, 최장 대기, 순서 뒤섞임, 다른 사람 기억 혼입을 확인한다. 동시 사용자 증가로 생기는 기본 모델 대기와 새 기억 기능이 추가한 지연을 구분한다.

### 소문 처리의 추가 부하

- 대화와 관찰 사건은 사건 ID 단위로 모아서 분석하고, 같은 원본을 개인 기억용·소문용으로 중복 분석하지 않도록 공유 근거 묶음을 사용한다. 공개 가능한 소문 발췌는 따로 분리하며 다른 사람의 사적 자료를 같은 추출 요청에 섞지 않는다.
- 소문 하나를 신 수만큼 LLM으로 재작성·평가하지 않는다. 승인된 주장/요약을 한 번 보관하고, 전달·신뢰·관심도·효과는 서버 정책과 인덱스로 처리한다. 자연스러운 반응은 실제로 대화할 때만 생성한다.
- 실제 관측과 전서구 사냥의 순서는 즉시 작은 게임 기록으로 고정한다. 늦게 끝난 후보 분석이 “관측 당시에는 살아 있었다”는 이유로 현재 차단을 무시하지 못한다.
- 게임이 확정한 주요 업적은 작성된 정책으로 후보를 만들 수 있다. 맥락이 필요한 대화 소문은 유휴 분석 전까지 후보 대기이며 확정 평판처럼 쓰지 않는다. 다음 신을 곧바로 만나면 소문이 아직 도착하지 않을 수 있다. 즉시 전파가 꼭 필요한 장면은 별도 성능/정책 승인 대상이다.
- 사건별 중복 억제, 플레이어별 발행 간격, 전파 묶음 크기·홉 수·큐 상한을 둔다. 장비 착용을 매 tick 기록하거나 모든 신 조합을 반복 검사하지 않는다. 6명 × 다수 신에서도 갱신된 소문과 연결된 수신자만 처리한다.

### 의미 검색의 위치

키워드 기반 버전의 실패 사례가 쌓인 뒤 선택적으로 추가한다. 기억 벡터의 사전 계산만으로 현재 발화의 벡터 생성 비용까지 없어지는 것은 아니다. 동일 GPU의 모델 교체·메모리 사용·대기 시간을 따로 검증한다. 초기에는 의미 검색을 대화에 쓰지 않고 검색 품질만 비교하며, 효과가 확인돼도 시간 예산을 넘으면 키워드 결과로 진행한다. 새 모델 설치는 별도 승인을 받는다.

## 7. 소문·평판 시스템 상세 설계

### 7.1 소유권과 최소 모델

아래 명칭은 제안이며 현재 클래스/JSON 스키마가 아니다.

| 계층 | 소유·책임 | 저장할 핵심 |
|---|---|---|
| 관찰 증거 | MythicTRPG의 기존 Observation/Event 연동 | 사건 식별자, 대상 플레이어, 관측자, 관측 시각·순서, 보거나 들을 수 있었던 내용, 출처·공개 정책 |
| 소문 주장 | 게임의 소문 서비스 | 원본 증거 참조, 대상, 발행자, 해석된 주장, 발행 상태·revision, 전파 채널·조건 |
| 수신·신뢰 | 게임 소유의 신별 전언 상태 | 어떤 신이 언제 어떤 버전을 어떤 경로로 들었는지, 출처 신뢰·반증·재전파 허용 여부 |
| 평판·수식어 | 게임의 파생 평판 상태 | 대상 플레이어·평가하는 신/허용 정보망, 근거 소문/경험, 관심·믿음·호감 방향, 대표 수식어와 효과 정책 |
| 대화 기억 | AI 응답 모듈 | 직접 경험의 비권위 요약, 승인된 전언의 읽기용 참조, 최근 대화 상태 |
| 정적 정의 | 기존 콘텐츠/게임 레지스트리 경계 | 신의 성격·가치관·관심사, 정보망 연결, 관측·전파·수식어 효과 정책 |

세계 정사·퀘스트·관계의 기존 저장소는 그대로 사용한다. `DynamicGodRelationState`는 신↔신 관계이므로 신→플레이어 평판을 거기에 섞지 않는다. 소문 수신은 “그 신이 이 주장을 들었다”는 게임 사실일 뿐, 주장 내용이 Story Fact가 참이라는 뜻이 아니다. 기존 Story의 참/거짓 Fact나 Knowledge grant를 이용해 불확실한 헛소문을 정사로 승격하지 않는다.

기존 Story 신호·예약·공개 경계와 통합 가능한 부분을 재사용하되, 동적 소문별로 정적 스토리 JSON을 무한 생성하지 않는다. 전파 영속성은 게임 측 확장으로 구현하며 별도 AI 세계 상태 DB를 만들지 않는다.

### 7.2 관찰에서 발행까지

1. **관측 성립:** 실제 게임 관측 기록이 있어야 한다. 대화 로그에 기록됐다는 사실만으로 전서구가 들었다고 하지 않는다. 화자·대상·당시 장비/상황을 사건 시점 기준으로 고정한다.
2. **맥락 해석:** 요청 이유, 앞선 설명, 친밀도, 문화적 의미, 농담·인용·정정, 관측자의 성향을 검토한다. AI는 근거 발췌·해석 후보·다른 가능성·수식어 문구를 제안할 수 있다.
3. **발행 자격:** 서버가 관측·공개 권한·상황적 중요성·새로움·등록된 소문 범주·빈도 제한을 검사한다. 목격 여부는 추첨으로 뒤늦게 만들어 내지 않는다. 목격 후 이야기할지의 확률은 정책상 허용할 수 있으나 값을 확정하지 않는다.
4. **결과 구분:** 발행 거절 / 해석 불확실 후보 / 전파 가능한 소문을 나눈다. 모델이 자극적인 문구를 썼다는 이유만으로 강한 평판이나 기계적 불이익을 확정하지 않는다.
5. **전달:** 게임의 예약/전파 정책을 거쳐 수신자별 전달을 확정한 뒤에만 그 신의 대화에 사용한다.

거짓 소문·오해 자체를 금지하지 않는다. 예를 들어 실제 근거는 “목적을 밝히지 않고 비늘을 요청했다”이고, 소문은 “불순한 의도로 요청했다고 여겨졌다”일 수 있다. **의도가 불확실하다는 기록을 유지한 상태에서 사회적인 오해가 생기는 것**과 AI가 존재하지 않은 사건을 창작하는 것을 구분한다.

게임상 불이익을 동반하는 발행에는 명확한 증거 조건·강도 상한·정정/회복 경로를 둔다. 모호한 모델 판단만 있는 후보는 우선 확정 효과 없이 검토한다. 소문이 날 때마다 사용자 승인 창을 요구하는 것은 제안하지 않는다. 등록된 게임 규칙 안에서 자동 발생하되 그 규칙과 효과의 승인은 개발 단계에서 받는다.

### 7.3 여러 신화에 걸친 전파

- 같은 신화권이라고 모두 알고, 다른 신화권이라고 아무도 모르는 식으로 고정하지 않는다. 작성된 정보망·연락 경로·접근 가능 상태에 따라 연결한다.
- 관심 여부, 들을 기회, 들은 내용을 믿는 정도, 그 내용을 좋게/나쁘게 보는 정도는 다른 값이다. 소문에 무관심한 신은 들어도 행동을 바꾸지 않을 수 있다.
- 초기 버전은 헤르메스 전서구 채널부터 구현하는 제안이다. 신 간 자율 수다·플레이어의 의도적 유언비어·무제한 과장 전파는 이번에 자동 추가하지 않는다.
- 신이 오프라인 플레이어의 소문을 듣는 것과 플레이어에게 소문 관련 대사를 보여 주는 것은 별도 상태다. 플레이어 로그인 자체를 전파 조건으로 만들지 않는다.
- 동일 근원 소문이 여러 경로로 돌아와도 독립 목격 증거처럼 신뢰도를 올리지 않는다. 전파 범위와 독립 근거 수를 구분한다. 순환 전파는 원본 계보와 수신 ID로 중복 제거한다.
- 후속 신이 실제로 본 장비·기운은 직접 관측이다. 전언이 차단돼도 실제 관측까지 금지하지 않으며, 기운의 원인이나 소유자 정체는 해당 신에게 허용된 감지 수준만 전달한다.

### 7.4 헤르메스의 전서구 — 플레이어 단위 차단

**사용자 확정:** 사냥으로 차단되는 대상은 해당 플레이어의 소문이다. 다른 플레이어·지역 전체·서버 전체에 적용하지 않는다.

전서구는 하늘섬에서 조우하고 사냥할 수 있는 실제 개체/게임 콘텐츠를 목표로 한다. 현재 Story Actor의 논리 위치만으로 실제 개체·이동·사냥이 구현된 것으로 보지 않는다. 개체 속도·스폰 구조물·재생성 시간·전서구 사냥 퀘스트는 별도 콘텐츠 정의가 필요하며 여기서 수치를 확정하지 않는다.

게임 상태 제안:
- `worldId + subjectPlayerId`별 전파 허용/차단 상태, 관측자 개체·전달 임무 연결, suppression epoch, 차단 원인 이벤트, 복구 조건을 둔다.
- 대상은 이름이나 AI 문장 속 인물이 아니라 게임이 지정한 플레이어 UUID다. 사냥자와 관찰 대상이 다른 경우의 귀속 규칙은 구현 전 확인한다.
- 사냥/죽음이 서버에서 확정되면 대상의 epoch를 바꾸고 그 대상에 관한 미확정 전달을 무효화한다. 다른 전서구 worker나 재시작 전 예약도 이 상태를 우회하지 못한다.
- 전달 커밋 직전에 대상 차단, 관측자 생존/유효 임무, 관측·소문 revision, 수신 권한을 다시 확인한다. 사냥과 전달은 같은 게임 순서에서 직렬 판정한다.
- 재생성으로 복구될 때도 새로운 epoch를 사용한다. chunk unload·로그아웃·서버 재시작을 사망 또는 재생성으로 오인하지 않는다. 재로그인으로 차단을 초기화하지 않는다.
- A와 B가 함께 나온 사건은 대상별 주장과 전달을 분리한다. B에 관한 소문에 차단 중인 A의 식별 가능한 평가를 끼워 넣어 우회하지 않는다. 안전한 분리가 안 되면 해당 전달은 보류/제외한다.

**추가 제안이며 사용자 미확정인 기본 처리:**

| 대상 | 제안 처리 |
|---|---|
| 사냥 전에 전달을 완료한 소문 | 들은 신의 기억·평판은 남김. 사냥으로 기억을 소급 삭제하지 않음 |
| 사냥 전에 관측했지만 아직 전달하지 않은 소문 | 무효화하고 재생성 뒤 자동 재전송하지 않음 |
| 차단 기간의 대상 관련 신규 소문 | 신규 발행/전달을 차단. 전서구 부활 후 밀린 소문 일괄 방출 없음 |
| 해당 신이 직접 겪은 사건 | 개인 기억은 유지. 소문 차단은 직접 경험 삭제가 아님 |
| 다른 플레이어의 소문 | 기존 정책대로 진행 |
| 이후 추가할 다른 전파 채널 | 초기에는 없음. 추가 시 대상별 차단을 우회하게 할지 별도 승인 필요 |

첫 구현에서는 허용된 모든 소문 전파가 플레이어별 차단 상태를 검사하게 하는 제안이다. 긍정적인 업적 소문도 같은 차단을 받는 것을 기본안으로 하여 나쁜 소문만 선택적으로 막는 무료 이점으로 만들지 않는다. 이 긍정/부정 공통 적용도 구현 전에 확인한다.

전서구 처치 퀘스트 완료와 소문 차단은 같은 사망 사건을 근거로 하되 서로 다른 효과다. 퀘스트 보상은 기존 시스템에서 처리하고 중복 지급하지 않는다. 다른 플레이어 대신 사냥하거나 환경 피해·다중 전서구가 있는 경우의 세부 규칙은 미확정이다.

### 7.5 평판과 수식어

- 하나의 전체 플레이어 태그가 모든 신의 첫인상을 강제하지 않는다. 수식어 후보는 세계에 존재할 수 있지만, 각 신이 그 근거를 전달받고 받아들였는지에 따라 그 신이 쓰는 대표 수식어가 달라진다.
- 수식어는 표현용 문구와 게임 효과 키를 분리한다. AI는 “드래곤로드의 친우” 같은 표현을 제안할 수 있지만 수치 보정·퀘스트 잠금·상점 가격 등의 효과는 등록 정책만 적용한다. 생성 문자열을 조건 ID로 사용하지 않는다.
- 첫인상과 이미 쌓은 직접 관계를 분리한다. 이미 플레이어를 오래 알아 온 신에게 처음 듣는 소문이 기존 관계를 무조건 덮어쓰지 않는다. 어떤 정보에 더 무게를 두는지는 신별 정책이다.
- 관심 없음 / 알고 있으나 의심 / 믿지만 대수롭지 않음 / 경계·존중함 등의 차이를 표현한다. 관심도나 믿음이 곧 호감도는 아니다.
- 여성신·특정 신화권 등 넓은 분류만으로 동일 불이익을 주지 않는다. 작성된 개별 가치관·금기·관계·정보 출처에 따라 다르게 반응한다.
- 수식어를 매 대사 첫머리에 붙이지 않는다. 첫 만남·소문을 직접 묻는 상황·관련 행동에서만 선택적으로 표현한다.
- 게임 효과가 있다면 현재 유효한 평판에서 계산되는 제한된 보정으로 관리한다. 소문 조회마다 영구 affinity를 빼거나 같은 사건의 직접 관계 변화와 평판 효과를 중복 적용하지 않는다.
- 더 큰 업은 새로운 대표 명성을 만들고 과거 수식어의 지배력을 낮출 수 있다. 과거 사건을 DB에서 삭제하는 것은 아니다. 새 업을 아직 듣지 못한 신이나 과거 사건을 직접 겪은 신은 다르게 반응할 수 있다.
- 명성 교체는 한 수치만 비교해 무조건 덮어쓰지 않는다. 신의 가치관에 따라 영웅적 업적도 과거 무례함을 상쇄하지 않을 수 있다. 해명·반증·오랜 직접 경험도 회복 경로 후보다. 정확한 교체 기준·지속 시간·효과 강도는 밸런스 승인 대상이다.

### 7.6 예시를 일반화한 수용 시나리오

- **비늘 요청:** 목적을 밝힌 제작 요청 / 설명 없는 요청 / 친밀한 농담을 구분한다. 비늘의 문화적 의미는 해당 콘텐츠에 명시돼야 하며 모든 비늘 있는 신에게 임의 적용하지 않는다. 전서구가 못 봤다면 그 경로로 소문은 생기지 않는다.
- **강한 존재와의 친분:** 게임이 확인한 관계·감지 가능한 기운·전해 들은 친분을 구분한다. 기운만 보인 초기 인식에서 친우라는 구체적 인식으로 넘어가려면 실제 정보 획득이 필요하다. 해당 존재의 적대자·우호자·무관심한 신은 다른 평가를 가진다.
- **특이한 장비:** 착용·외형·알려진 유래·발언으로 노출된 명칭을 관측 근거로 삼는다. 단순 모루 이름 변경으로 특정 존재의 실제 소유품이라고 확정하지 않는다. 같은 착용 장면이 반복 샘플링됐다는 이유로 소문 수백 개를 만들지 않는다.

위 예시는 테스트 형태이며 특정 신 ID, 실제 아이템/금기, 고정 답변, 전파 확률, 디버프를 확정한 것이 아니다.

## 8. 구현 범위와 순서 제안

### 1단계: 공통 근거·개인 기억·안전한 IO

AI 모듈의 출처·정정·저장·로컬 검색과 게임의 관측/전달 식별 계약을 먼저 만든다. 기존 로그와 gameplay observation을 확장하며 감지 시스템을 AI 안에 중복 구현하지 않는다. 첫날부터 direct/rumor 출처와 대상·청중을 구분해 나중에 개인 기억을 소문 저장소로 억지 변환하지 않게 한다.

기존 adapter 입력 수락/최종 대사/세션 종료와 시작 Context의 청중 전달을 연결한다. 생성 코드만 수정하지 않고 실제 Java helper와 빌드 오버레이 입력을 수정한다. 기존 프로필·대화 모델·출력 토큰·JSON schema·감정/품질 분석은 유지한다. 자동 추출은 별도 스위치로 둔다.

### 2단계: 게임 경험 + 전서구 관측·대상별 차단

퀘스트 완료·평가의 기존 DTO를 활용하되 영구 발생 ID가 필요한 부분만 확장한다. Observation에 필요한 정보가 없는 대화/장비 관측은 게임에서 최소 계약을 제공한다. 기존 God ID, 구조물/개체/퀘스트 등록 방식을 확인한 뒤 전서구 콘텐츠를 구현한다.

전서구 실제 개체와 대상별 차단, 저장·재시작·미전달 예약 취소를 먼저 검증한다. 일반 액션의 Proposal 접수를 완료 사건으로 기록하지 않는다. 실패/미확인 상태에서는 소문 생성·전달을 허용하지 않는다.

### 3단계: 소문 수신·신별 평판·대화 반영

처음에는 제한된 정보망과 작성된 사건으로 전달·신뢰·첫인상·수식어 표현을 검증한다. 게임 효과 없이도 충분히 다른 반응이 생기는지 먼저 비교한다. 이후 맥락형 대화 소문 후보 추출을 연결하고, 발행 오류/회복 테스트를 통과한 범주에만 제한된 게임 효과를 적용한다.

해명·큰 업에 따른 대표 명성 변화, 대상별 전파 차단까지 같은 종단 테스트에 포함한다. 전체 신 데이터와 신화권 간 전파망은 별도 작성 작업이다. LP가 다수의 신을 순차 지원하는 것과 한 장면의 다중 신 대화 구현은 다른 범위이며, 이 설계만으로 운영 facade를 무조건 다중 신으로 바꾸지 않는다.

### 4단계: 의미 검색 선택 실험

실제 회상을 놓친 사례를 기준으로 검색 품질과 지연을 비교한다. 필요하지 않으면 도입하지 않는다. 소문 전파를 위해 임베딩이 필수인 것은 아니다.

이 개정은 AI 모듈만의 변경이 아니라 게임 소유 소문 상태·전서구·관련 IO까지 필요한 설계다. 구현 전 게임 소스·빌드 입력·서버/클라이언트 JAR을 906개 파일 스냅샷으로 별도 보존했다. 개발 소스에 기반 단계를 추가한 뒤 별도 요청으로 PERSONAL 서버 시험 파일도 배치했으며 원본 LP는 그대로 보존했다. 2~4단계 전체를 완료한 것으로 해석하지 않는다.

## 9. 비교 검증·운영·되돌리기

동일 모델·프로필·설정에서 LP / 전체 기능 OFF / 개인 기억만 ON / 기억+소문 ON을 비교한다. OFF일 때 새로운 프롬프트·모델 요청·소문 효과가 없어야 한다. 기존 LP 직접 인사와 소문 기반 첫인상 생성은 별도 측정 그룹으로 구분한다.

필수 검증:
- 재접속 회상, 정정/삭제, 늦은 분석, 파일 손상, 꽉 찬 큐, 6명 동시 요청의 세션 격리.
- 신/플레이어/월드/청중을 넘는 **미승인** 정보 유출 0건. 승인된 소문 수신은 유출과 구분하며 전달 근거가 있어야 한다.
- 직접 경험·전언·정사 구분, 기운 감지와 친분 인식 분리, 농담·인용·아이템 이름 위조의 오판 방지.
- 한 소문의 순환 전파가 독립 증거로 증폭되지 않음. 같은 출처·수신자·revision의 전달/효과 중복 없음.
- A의 전서구 사냥이 B의 소문에 영향 없음. A가 포함된 복합 소문으로 차단 우회 불가.
- 사냥과 전달 동시 발생, 사냥 후 도착한 분석, 재접속/재시작/재생성 이후 오래된 작업이 다시 전파되지 않음.
- 이미 들은 기억과 새 전달 차단 구분, 긍정·부정 소문 차단 정책, 기존 직접 관계 유지.
- 중요한 업·반증·사과가 실제로 전달된 범위에서만 평가를 바꿈. 대표 수식어 교체가 과거 사건 삭제가 아님.
- 기억·소문 때문에 보상/아이템 소비/관계 효과가 중복 실행되지 않음. 모델 오류 하나로 무제한 불이익을 줄 수 없음.
- 무관심한 신, 소문을 못 들은 신, 믿지 않는 신, 관련 인물의 적대/우호 신이 서로 다른 인식을 보임.

검색·대기·분류·생성·재시도·후처리와 입력부터 표시까지 전체 지연의 중앙값/p95를 1명·4명·6명에서 비교한다. 소문 수·등록 신 수·전달 대기 건수·입출력 토큰도 기록한다. 생성 순서와 캐시 영향을 통제하고 몇 번의 대화만으로 자연스러움·속도 개선을 단정하지 않는다.

사용자/관리자 진단은 “무슨 근거로 어떤 전언이 언제 누구에게 도착했고, 왜 그 효과가 생겼는가”를 추적 가능하게 한다. 디버그 조회에는 권한을 적용하고 숨은 신의 지식·사적 원문을 일반 플레이어에게 공개하지 않는다. 플레이어가 느낄 단서는 대사·전서구 조우 등 콘텐츠로 전달하며 정확한 관측 확률/내부 수치를 무조건 노출하지 않는다.

보존 정책은 AI 기억·게임 소문 기록·현재 평판·원문에 서로 다른 수명을 둔다. 원문을 정리하더라도 현재 게임 효과를 검증할 최소 근거/발급 기록은 남긴다. 운영 삭제·개인정보 삭제는 파생 색인·소문 참조·평판까지 무효화하고, 단순 게임 내 해명과 구분한다.

LP 백업은 변경하지 않는다. 직전 설계는 archive에 별도 보존했다. 새 AI 기억 경로는 `server/<world>/mythictrpg-ai-memory-lp/` 가칭을 유지하고 예전 기억 파일은 자동 이관하지 않는다. 게임 소문 상태는 MythicTRPG가 소유하는 버전형 저장에 둔다.

향후 롤백은 AI JAR 두 개만 바꾸는 것으로 끝나지 않을 수 있다. 게임 소스/서버·클라이언트 JAR/설정도 구현 직전에 백업하고, 신규 소문 기능 OFF·파생 보정 제거·대기 작업 무효화를 먼저 지원한다. 기능 OFF는 기존 획득 아이템이나 완료 퀘스트를 되감는 것이 아니다. 실제 LP 바이너리 복원은 정상 서버 종료 후 검증된 게임 JAR 조합으로 수행하고 월드 전체를 되감지 않는다. 신규 SavedData를 구버전이 안전하게 무시/보존하는지 검증하기 전에는 무조건 안전한 다운그레이드라고 안내하지 않는다.

## 10. 확정 사항과 구현 전 선택 사항

사용자가 확정한 방향:
- 여러 신화의 다수의 신이 등장하며 소문에 관심 있는 존재와 없는 존재가 있다.
- 직접 대화·관찰된 행동·큰 업이 상황에 따라 소문과 수식어로 이어진다. 제시된 세 사례는 고정 규칙이 아닌 의도 설명용 예시다.
- 헤르메스 전서구는 실제 조우·사냥 가능한 콘텐츠이며, 사냥에 따른 차단은 **해당 플레이어의 소문만** 대상으로 한다.
- 중요한 사건·약속은 오래 기억하고 사소한 잡담은 점차 잊는다.
- 평소 4~5명·최대 6명, 전원이 동시에 AI 대화할 수 있다. 대화 대기는 허용하지만 무제한 후처리 지연의 허용은 아니다.

미확정이며 이 문서가 제안한 기본안:
- 사냥 전 전달 완료 소문은 유지, 미전달분은 무효화, 차단 중 발생분의 부활 후 일괄 재전파 없음.
- 좋은 업적 소문도 나쁜 소문과 함께 차단.
- 큰 업은 대표 명성을 바꾸되 과거 경험을 일괄 삭제하지 않음.
- 초기 전파 채널은 전서구만. 다른 채널을 추가해 대상별 차단을 우회할지는 별도 결정.
- 첫인상/대사부터 검증하고 기계적 불이익은 등록 범주·상한·회복 경로를 갖춘 뒤 적용.

구현 전에 확인할 콘텐츠 선택:
- 사냥자와 관찰 대상이 다를 때 귀속, 전서구 수·위치·관측 조건·재생성 및 차단 종료 조건.
- 신화권 간 정보망과 각 신의 관심/금기/출처 신뢰 정책.
- 수식어의 표현 범위·대표 명성 교체 기준·실제 관계/퀘스트 효과와 회복 난이도.
- 원문/기록 보존 기간과 성능 수용 기준.

9월 13일 재설계 자체는 구현 승인이 아니었으나 후속 사용자 "진행해" 승인으로 기반 단계에 착수했다. 9월 14일 미완료 검증·문서를 마무리했고 이어 별도 요청으로 PERSONAL 서버 세팅까지 진행했다. 위 미확정 콘텐츠 선택·실제 LLM 비교는 남아 있다. LP 백업·모델·월드는 그대로 보존했으며 실제 서버를 실행하지 않았다.

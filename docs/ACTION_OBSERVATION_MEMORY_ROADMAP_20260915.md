# 상세 행동 기록·신의 주시·장기기억·소문 작업 순서

2026-09-15 / 0~1단계 소스·오프라인 작업 완료 / 2단계 이후 미착수·배포 미승인

> 후속 실행 상태: [0~1단계 기록](RECALL_STAGE01_20260915.md), [공통 계약](ACTION_OBSERVATION_CONTRACT_20260915.md). AI 개발 0.1.4, 서버 0.1.3 유지. 실제 LLM/서버 검증과 운영 정책 확정은 남아 있다. 아래 최초 설계 당시의 ‘이번 작업’은 문서 작성 이력이다.

## 1. 목적과 문서 관계

플레이어의 이동·채집·전투 등 일상 행동부터 중요한 사건·업적까지 상세히 기록하고, 조건 또는 관계 진척에 따라 주시 중인 신이 허용된 행동을 관찰·기억하게 한다. 그 경험은 이후 대화와 소문·평판·게임 콘텐츠로 연결한다.

전체 행동 기록은 서버가 아는 이력이다. 신의 직접 관찰, 플레이어가 말한 이야기, 전해 들은 소문은 서로 다른 정보 획득 경로다. 기록이 있다는 이유만으로 모든 신에게 공개하지 않는다.

이 문서는 행동 기록과 신의 주시 요구를 추가한 **최신 작업 순서**다. [개인 회상 상세 설계](EPISODIC_MEMORY_UPGRADE_DESIGN_20260915.md)의 데이터·검색·정정·검증 원칙과 [기존 소문 설계](LP_LONG_TERM_MEMORY_DESIGN.md)의 경계를 재사용한다. 개인 회상 문서의 11·14절에 있던 전체 실행 순서/첫 승인 범위보다 이 로드맵을 우선한다. 두 문서의 단계 번호는 같지 않으며 아래 대응표를 따른다.

이번 작업은 문서 작성과 링크 정리만 수행한다. Java/Gradle, JAR, 서버 설정, 월드/기억, LP 백업은 변경하지 않는다. 새 모델/라이브러리 설치·LLM 실행·서버 실행·배포는 포함하지 않는다.

## 2. 현재 코드에서 출발할 위치

- GameplayObservationAdapters/GameplayIngressService에 행동 관찰 기반이 있다. GameplayObservationTypes에는 블록 파괴·성숙 작물 수확·처치·사망·동물 먹이주기/번식·아이템 최초 획득·통계 임계치가 정의돼 있다. 이것이 모든 세부 행동의 기록 완료를 뜻하지는 않는다.
- GameplayIngressService는 플레이어/행동 종류/대상 구분값이 같은 pending 알림을 묶는다. 상세 로그를 이 전달 결과만으로 만들면 개별 발생 횟수와 순서를 잃을 수 있다. 기존 묶음 전달은 조우·퀘스트·스토리 소비자를 위해 보존하고, 상세 기록 경로를 같은 authoritative 감지 지점에서 분기하는 방안을 검증한다.
- GameplayObservation에는 플레이어·gameTime·타입·payload는 있지만 공통 영구 사건 ID나 신별 관찰 증명은 없다. 새로운 계약은 이 부족분을 보완하며 기존 DTO 생성자를 무조건 깨지 않는다.
- GodAttentionState/Record는 첫 메인 퀘스트 수주에 따른 주목 대상이다. 새 주시 자격의 입력으로 활용할 수는 있지만 실제 관찰 상태나 목격 증거와 동일하지 않다.
- 현재 AI 0.1.3의 개인 기억 기반을 유지한다. 전체 행동 원장을 AI 저장소에 복사하지 않는다. 개인 회상 개선만으로 게임 관계 입력과 주시 기능이 완성됐다고 하지 않는다.
- AI 빌드는 mine/mine의 레거시 소스/JAR과 검증된 오버레이를 사용한다. build/generated 직접 수정이나 게임·AI 간 동일 패키지 재생성은 피한다. 게임에는 기존 사용자 미커밋 변경이 있고 프로젝트 루트/AI 폴더는 Git 저장소가 아니므로 파일별 manifest를 사용해야 한다.

## 3. 권장 순서

| 단계 | 작업 | 다음으로 넘어가는 기준 | 기존 개인 회상 설계와의 대응 |
|---|---|---|---|
| 0 | LP/현재 기준 보존, 공통 계약·미확정 정책 정리 | 사건과 관찰을 분리한 계약 및 시험 범위 확정 | 기존 0단계 확장 |
| 1 | 현재 대화의 개인 회상 개선 | 간접 질문·재질문·정정·새 세션 회귀 통과 | 기존 1A |
| 2 | 작은 상세 행동 원장 구현 | 중복/순서/재시작/실패를 검증한 원본 기록 | 신규 |
| 3 | 신별 주시 상태와 관찰 증명 | 본 신과 못 본 신의 정보 경계 검증 | 신규 |
| 4 | 행동 한 종류를 기억·대화까지 연결 | 최초 종단 시험과 실제 모델 비교 | 기존 공동 경험 연결을 일반화 |
| 5 | 행동 수집 범위 확장 + 정리 기억·혼합 검색 | 상세 일상 기록 범위 및 1/4/6인 품질·부하 기준 통과 | 기존 1B 및 경험 확장 |
| 6 | 물리 전서구·소문 전달·신별 첫인상 | 대상별 차단/재시작/전파 경계 통과 | 기존 3단계 |
| 7 | 평판의 게임 효과와 회복 콘텐츠 | 중복 불이익 없음, 제한·취소·회복 검증 | 기존 4단계 |

핵심은 모든 행동 종류를 먼저 완성하는 것이 아니라 **작은 원장 → 주시/관찰 → 기억 → 대화**를 먼저 끝까지 연결하는 것이다. 그 후 이동·채집·전투의 상세 범위를 넓힌다. 초기에 일부 행동만 연결하는 것은 구현 순서이며 사용자가 원한 상세 기록 범위를 중요 사건만으로 축소하는 결정이 아니다.

## 4. 0단계 — 공통 바탕과 선택

### 보존과 비교 기준

구현 직전에 LP 원본/LP 필수 소스/기억 기반 이전 게임 전체 백업의 manifest를 검사하고 현재 작업본·필수 빌드 입력·배포 JAR·설정·기억을 새 경로에 보존한다. 이번 문서 작성은 이 해시 검사나 백업 실행을 대신하지 않는다.

LP는 대화 감각의 비교 기준, 현재 AI 0.1.3은 회상/지연 대조군으로 구분한다. 각 기능의 OFF와 직전 버전 복원을 마련하고, 전체 게임 다운그레이드는 별도 월드 호환 시험으로 남긴다.

### 공통 계약 초안

구현 전 아래 세 개념의 형식과 소유권을 먼저 정한다. 실제 Java 클래스 이름·파일 형식은 여기서 확정하지 않는다.

| 개념 | 최소 내용 | 소유자 |
|---|---|---|
| 행동 사건 | 영구 eventId/원천 중복 키, 월드·행위자·대상, 순서, 현실 시각·게임 tick, 차원·필요 위치, 종류·결과·revision | 게임 행동 기록 |
| 주시 상태 | 신/플레이어, 활성 구간·시작 원인, 관측 정책 버전·범위·일시중지/종료 | MythicTRPG |
| 관찰 증명 | 원본 eventId/revision, 관찰 신·시각/순서·경로, 당시 주시/관측 근거, 관측 가능한 발췌・현재 공개 조건 참조 | MythicTRPG |

기억은 이 증명과 원본을 참조하는 읽기 전용 자료를 받는다. AI가 eventId를 만들어 게임 사실로 등록하거나 수신자를 선택하지 못한다. 같은 사건이 여러 모드에서 전달돼도 같은 근거로 식별하고, 재생이 게임 액션을 다시 실행하지 않게 한다.

### 사용자 선택이 필요한 항목

- **주시 범위:** 장소와 무관한 외부 행동 전반인지, 신의 권능·영역·장소에 따른 범위인지. 다른 신과의 대화/비밀 공간의 관측 여부도 별도다. 아직 미응답이므로 운영 정책을 확정하지 않는다.
- **주시 생명주기:** 시작 조건, 지속/중단/종료, 관계 하락·신의 부재·관측 방해 시 처리. 신별 관계 임계값은 임의 확정하지 않는다.
- **기록 정밀도/보존:** 이동을 매 tick 기록할지, 정해진 간격/변화 기준으로 기록할지; 전투 시도/피해/처치 범위, 보관 용량과 기간. ‘상세 기록’이 자동으로 ‘모든 tick을 영구 보관’이라는 뜻은 아니다. 정밀도를 낮추는 운영 결정은 사용자 확인 없이 하지 않는다.
- **대화의 상대 시간:** 현실 날짜/게임 날짜. 기존 현실 날짜·한국 시간은 미확정 제안이다. 원장에는 둘의 기준값을 함께 보관해 이후 해석이 가능하게 한다.

답변이 없어도 계약 초안·저장소/가짜 사건 테스트·개인 회상 개선은 진행할 수 있다. 미확정 정책이 필요한 운영 관측은 OFF로 두고 테스트용 명시 정책으로만 검사한다.

## 5. 1단계 — 개인 회상부터 개선

행동 원장이 없어도 현재 문제를 먼저 줄일 수 있다. 간접 회상 의도, 미해결 회상 질문 유지, 시간 단서, 최근 원문 fallback, 누락/상충/조회 불가 구분과 진단 로그를 개선한다. 구체 내용은 기존 설계의 1A를 따른다.

통과 기준은 “내일 어디 간다고 했지?” 다음 “한번만 말해줘”가 이어지는 질문으로 처리되고, 새 세션/화제 전환/삭제/다른 신·플레이어 경계가 유지되는 것이다. 고정 답변으로 통과시키지 않는다.

관계 입력 경로는 함께 읽기 감사하되 관계 원본/단계 매핑 연결은 별도 패치로 비교한다. 중립 대사만으로 전체 관계 자연스러움을 검증했다고 하지 않는다. 추가 임베딩 모델은 이 단계의 필수 조건이 아니다.

실제 LLM 비교는 실행 범위를 확인한 뒤 한다. 오프라인 검증만 끝났다면 결과를 ‘인게임 개선 확인’으로 보고하지 않는다.

## 6. 2단계 — 상세 행동 원장의 최소 기반

처음에는 기존 관찰과 연결하기 쉬운 소수의 행동을 사용한다. 제안 첫 대상은 성숙 작물 수확과 엔티티 처치다. 실제 발생/완료 시점을 검증하고 취소된 이벤트, 공격 시도, 피해 적용, 처치 결과를 혼동하지 않는다.

### 구현 내용

- 게임이 인정하는 입력 지점에서 사건을 한 번 식별하고 상세 기록과 기존 관찰 알림을 분기한다. 기존 알림을 묶는 부분의 뒤에 원장을 붙여 상세 발생을 유실시키지 않는다.
- 기존 조우·퀘스트 재촉·즉석 퀘스트·스토리 소비자는 유지한다. 원장 재생이 이 소비자들을 다시 실행하는 구조를 만들지 않는다.
- 게임 스레드에서는 제한된 불변 데이터와 순서를 만들고 파일 IO는 유한 큐/단일 작성자로 처리한다. 원장 segment·체크포인트·버전·읽기 인덱스·관리자 조회를 마련한다. 전체 과거 파일을 매 행동마다 다시 쓰지 않는다.
- 기록 성공/pending/실패를 구분한다. 큐 포화나 디스크 오류 때 조용히 성공 처리하지 않는다. 기록 누락 구간을 진단하고, 누락 기록을 AI가 상상해 메우지 않게 한다. 비동기 기록의 크래시 손실 한계도 시험한다.
- 관찰 증명은 뒤 단계에서 원본 사건과 일관되게 커밋할 수 있도록 결합 키와 재시도 cursor를 준비한다. 실패 후 원본 없는 증명만 남지 않게 한다.

### 완료 조건

개별 발생 수와 순서 보존, 다른 월드/플레이어 분리, 중복 재전달, 취소 이벤트, 정상 종료·재시작, 비정상 중단·손상·용량 제한을 검사한다. 기록이 켜져도 기존 퀘스트/조우/보상이 중복 실행되지 않아야 한다.

이 단계에서는 신에게 원장을 공개하거나 LLM으로 행동을 해석하지 않는다.

## 7. 3단계 — 주시와 관찰 권한

주시 자격과 실제 주시 상태를 분리한다. 기존 GodAttentionState, 게임 관계, 확정 사건/조건은 시작 자격의 입력으로 사용할 수 있다. 기존 퀘스트 주목 대상의 저장 의미를 바꾸지 않는다.

### 구현 내용

- 게임 소유의 신·플레이어별 주시 상태와 시간/순서 구간, 정책 revision, 중지·종료를 저장한다. 값은 작성된 조건과 게임 상태로 결정한다.
- 새 행동이 발생하면 해당 플레이어를 주시하는 신만 찾아 관측 조건을 검사한다. 모든 플레이어×모든 신×전체 과거 기록을 매 tick 검색하지 않는다.
- 범위/가림/비밀/상황상 차단 등을 통과한 실제 관찰만 증명으로 만든다. 관측 당시 정보를 고정하고, 나중에 주시를 켰다는 이유로 과거 원장을 자동 열어주지 않는다.
- 현재 주시가 끝나도 이미 실제로 본 경험은 별도 기억으로 남길 수 있다. 반면 관측 근거의 오류·정책 취소·원본 무효화는 파생 기억까지 무효화해야 한다.
- 비동기 기억 정리가 늦어져도 이미 확정한 관찰 사실과 미래 관찰 권한을 혼동하지 않는다. 재접속/서버 재시작/정리 재생으로 관찰 구간을 확장하지 않는다.
- ‘그 신이 안다’와 ‘현재 청중에게 공개해도 된다’를 별도로 검증한다. 주시 중이라는 이유로 대화 참가자를 자동 추가하거나 다른 신과의 사적 대화를 통째로 전달하지 않는다.

### 완료 조건

신 A만 주시하는 상황, 신 B는 미주시, 시작 직전/직후 사건, 일시중지/종료, 재시작, 현재 청중 변경, 복합 플레이어 사건의 공개 범위, 원본 무효화를 검사한다. 운영 관찰 범위가 미확정이면 구현 기반과 테스트만 완료할 수 있고 실제 신별 설정은 켜지 않는다.

## 8. 4단계 — 첫 번째 종단 경험

첫 수직 시험은 테스트용 조건 아래 ‘주시 중인 신 A가 수확을 관찰 → 대화 종료/재시작 → 관련 질문에 경험을 활용’이다. 신 B는 관측도 전달도 없으므로 같은 사실을 알면 안 된다. 어떤 신에게 어떤 반응을 강제하는 콘텐츠 규칙은 아니다.

필요 작업:

- 관찰 증명을 게임에서 허용된 Experience 조회 자료로 투영하고 기존 개인 기억 검색에 연결한다. 상세 원장을 AI가 직접 전역 조회하지 못하게 한다.
- 출처를 개인 진술/NPC 발언/직접 관찰/소문으로 구분하고 원본 ID·revision·공개 검사를 유지한다.
- 게임의 실제 관계를 대사에 전달하는 읽기 계약/기존 Provider 소비 경로를 확인한다. 기존 단계 매핑이 없다면 새 수치를 임의 확정하지 않는다.
- 최종 대사에는 필요한 근거만 넣고 기존 Proposal 권한·세션/턴/generation 검증을 유지한다. 행동 로그로 취향·의도·성격을 확정하지 않는다.
- AI가 없거나 실패해도 원장/관찰 증명과 게임 진행은 정상 유지해야 한다.

첫 종단 시험에서는 정확한 사건 표현과 원문 조회만으로 시작해도 된다. 의미 검색이나 자동 요약을 모두 완성해야 경계 검증을 시작할 수 있는 구조를 피한다.

이 단계가 끝나면 사용자에게 작은 인게임 시험을 요청할 수 있다. 단, 운영 서버 배포·실행은 별도 승인 뒤 진행한다. ‘구조 검증’과 ‘실제 모델 대사 확인’을 구분한다.

## 9. 5단계 — 상세 범위와 기억 품질 확장

두 개의 분리된 묶음으로 진행한다. 같은 작업에서 순차 구현할 수 있으며 실제 다른 작업 생성이나 동시 저장소 수정을 지시하는 것이 아니다.

### 5A: 행동 범위 확대

- 이동: 승인된 정밀도로 경로/차원 이동/텔레포트/중요 구간을 구분한다. 정지·관측 공백도 명시하고 좌표 샘플을 사건 횟수로 오해하지 않는다.
- 채집·생활: 수확/채굴 등 합의된 행동과 결과/수량을 연결한다. 최초 아이템 획득 기록만으로 모든 획득·소비 이력을 대신하지 않는다.
- 전투: 합의된 공격 시도/실제 피해/처치/사망 구분과 대상·결과를 기록한다. 처치 로그만으로 구조·배신 같은 의도를 판정하지 않는다.
- 중요 사건·업적: 기존 퀘스트 완료·평가 등 authoritative 결과를 같은 사건 참조 계약으로 연결한다. 완료자/수주자/FTB 팀, 완료/지급/확인 대기를 분리한다. 미확정 레이드 규칙은 추가하지 않는다.

각 타입마다 수집 위치, 보존 정밀도, 취소/실패 표현, 관찰 가능 정보, 시험 결과를 기록한 지원표를 갖춘다. 기능 명칭만으로 ‘모든 행동 완전 기록’을 선언하지 않는다.

### 5B: 경험 묶음과 혼합 검색

개인 회상 설계의 1B를 공통 기억 계약 위에서 구현한다. 원문/사건 참조·계획/약속·시간·정정·중요도/망각·단어+의미 검색을 연결한다. 이 개발/검색-only 비교는 2~3단계와 독립적으로 앞당길 수 있다. 행동 기억의 최종 운영 적용은 3~4단계의 권한 검증 이후다.

일상 집계는 먼저 코드로 계산한다. 요약은 동일 신에게 허용된 자료 안에서만 수행하고 관찰하지 않은 구간을 섞지 않는다. 관찰 일부만으로 하루 전체의 행적을 아는 척하지 않는다. 요약에서 원본으로 추적 가능하게 하고, 같은 사건을 개인 기억/소문/평판의 독립 증거로 중복 계산하지 않는다.

매 행동마다 LLM을 호출하지 않는다. 자동 정리는 기존 대화·자발 대사·시각 평가와 공통 자원 입장 관리가 된 뒤 유휴 시간에 제한한다. 모델 다운로드/설치와 실제 실행은 별도 승인이다. 질의 임베딩에도 비용이 있으므로 실패/시간 초과 때 기본 검색을 유지한다.

### 완료 조건

1/4/6인 조건에서 기록량·디스크 증가·메모리·tick 시간·쓰기 backlog·기록 누락·검색/전체 대화 지연을 비교한다. 실제 장비 측정으로 기록 정밀도/보존 용량을 산정하고 초과 시 사용자에게 조정을 제시한다. 검증 없이 기록 빈도를 낮추거나 손실을 감추지 않는다. 대화 정확도/자연스러움 수용 기준은 개인 회상 설계 12절을 따른다.

## 10. 6단계 — 전서구와 소문

주시와 소문은 별도 정보 획득 경로다. 관찰 증명 계약의 원리를 재사용하되 전서구가 관측한 공개 가능한 발췌만 소문 후보로 만든다. 기존 RumorLedger/RumorSavedData의 대상별 차단·계보·수신을 활용한다.

순서는 물리 전서구/대상 귀속·사망 연결 → 관측 증명 → 제한된 후보/발행 → 수신자별 전달 → 첫인상 대사다. 이미 있는 상태 머신을 새로 중복 구현하지 않는다. 소문 조건은 실제 관찰과 작성된 정책이 결정하며 AI가 목격 여부를 만들지 못한다.

전서구 사냥은 해당 플레이어의 소문 전파만 차단한다. 직접 주시 관찰의 차단 여부는 별개이며, 제안 기본은 직접 관찰을 유지하는 것이다. 주시한 신의 임의 재전파로 대상별 소문 차단을 우회하지 않는다. 신규 신 간 전파 채널은 별도 정책 승인 없이는 추가하지 않는다.

개체 수·귀속·재생성·차단 종료, 신화권 정보망, 사냥 전 미전달/기존 수신 처리·긍정/부정 공통 차단은 기존 문서의 제안과 사용자 확정을 구분한다. 이 단계 시작 전에 미확정값을 결정한다. 대사만 먼저 검증하고 소문 때문에 기존 RUMOR_TEST의 실행 차단을 풀지 않는다.

## 11. 7단계 — 평판 효과·회복

수식어는 신별 인식에서 선택되는 표현이며 전역 단일 태그로 성격·관계를 덮어쓰지 않는다. 실제 관계 보정·퀘스트 제한·기타 효과는 허용된 게임 정책으로만 구현한다.

같은 근거의 중복 적용 방지, 효과 상한, 소문 취소/오류 수정, 해명·반증·큰 업·직접 경험에 따른 회복을 먼저 설계한다. 효과보다 회복을 나중에 붙이는 구조를 피한다. AI가 소문을 회상할 때마다 영구 호감도를 차감하거나 보상을 실행하지 않는다.

정확한 신별 금기·평판 강도·회복 난이도는 콘텐츠 승인 사항이다. 신의 성격에 따라 동일 사건을 다르게 평가하는지 실제 대화로 확인한다.

## 12. 진행 방식·호환·보고

- 기본은 이 작업에서 통합 설계를 관리하며 작은 패치 단위로 순차 구현한다. 규격 확정 후 저장·수집·검색 같은 독립 작업을 나눌 수는 있지만, 별도 작업 생성은 사용자 요청이 있을 때만 한다.
- 행동 원장, 주시, 행동 기억, 의미 검색/정리, 소문, 평판 효과는 각각 비활성화 가능하게 설계한다. 하위 기록 기반이 불가용하면 파생 기억/소문은 닫고 기존 게임 기능은 유지한다. 기록을 끄면 해당 구간이 비었다는 사실을 남겨 나중에 관측을 추정하지 못하게 한다.
- 기능 OFF는 데이터 삭제나 월드 되감기가 아니다. 새로운 게임 자료가 추가된 뒤 옛 LP JAR로의 완전 복원은 호환 시험 전 보장하지 않는다. [기존 LP 복원 경계](LP_MEMORY_FOUNDATION_GUIDE.md)를 따른다.
- 게임 계약은 com.sande.mythictrpg.ai.memorycontract 등 게임 소유 경로, AI helper는 com.sande.mythai.response.*로 구분한다. 패키지 충돌·의존성·빌드 입력/오버레이를 검사한다. 게임 변경 시 서버/클라이언트 JAR도 함께 검증한다.
- 기존 FTB/퀘스트/조우/스토리 저장소와 실행 소유권은 보존한다. 관련 기능을 실제로 변경하는 단계에서 해당 상세 가이드·생산자·소비자·예제까지 다시 확인한다.
- 각 단계는 소스 수정 → 관련 컴파일/오프라인 검증 → 필요한 격리 통합 시험 → 승인된 실제 모델/인게임 비교 → 별도 배포 승인 순서로 보고한다. 서버 실행 없이 허용된 범위만 끝났으면 나머지는 미확인으로 남긴다.
- 첫 사용자 체감 지점은 1단계 개인 회상, 첫 행동 기반 종단 체감은 4단계다. 5단계에서 상세 기록과 장기 회상의 폭을 확장하고, 6~7단계에서 사회적 결과를 붙인다.

## 13. 다음 착수 범위 제안

최초 요청은 순서 설계였으며, 후속 사용자 승인으로 **0단계의 기준/계약 정리와 1단계 개인 회상 소스·오프라인 검사**까지 수행했다. [실행 기록](RECALL_STAGE01_20260915.md)의 완료/미검증을 따른다. 주시 범위 미응답이 이 개인 회상 작업을 막지는 않지만 운영 주시 구현/활성화 전에는 답이 필요하다.

다음 묶음은 **2~4단계의 작은 종단 연결**로 삼는다. 단계마다 검증하고, 모든 상세 행동을 한 번에 수집하는 변경과 섞지 않는다. 서버 실행/배포/새 모델 설치는 묶음 승인에 자동 포함하지 않는다.

이번에는 mythai-integration 검토 기준에 따라 기존 관찰 알림과 상세 원장을 구분하고, 퀘스트 주목 대상과 실제 주시를 분리하며, 게임 권한과 소문 차단을 보존하도록 순서를 정했다. 문서 링크/형식만 검사하고 코드 빌드나 서버 검증은 수행하지 않았다.

## 1. 결정 요약과 범위

목표는 모든 대화를 외우는 비서가 아니라, 플레이어의 말과 행동이 신의 기억·관계·다음 모험으로 이어지는 RPG다. LP의 대화 감각을 기준으로 삼고, 현재 기억 기반을 점진적으로 개선한다. OPELA 실험 전체, 별도 감정 평가 LLM, 매 턴 자기평가·재작성 루프는 재도입하지 않는다.

선택한 방향은 **원문 근거 + 사건/계획 기억 + 단어·의미·시간 혼합 조회 + 신별 인식**이다. 기억을 찾는 일, 기억을 해석하는 일, 게임 결과를 실행하는 일을 분리한다.

이 문서는 [기존 통합 설계](LP_LONG_TERM_MEMORY_DESIGN.md)의 개인 기억 부분과 구현 순서를 구체화한 후속 제안이다. 기존 소문 권한·대상별 차단 원칙은 유지한다. 의미 검색 비교를 소문 구현 뒤가 아니라 개인 기억 단계로 앞당긴다. 기존 문서의 구현 기록을 새 기능의 완료 증거로 재사용하지 않는다.

이번 요청에서는 설계 문서와 인수인계의 설계 링크만 작성한다. Java/Gradle, 서버 설정/JAR, 모델, 월드/기억, LP 백업은 변경하지 않는다. 서버·Ollama 실행, 새 LLM 요청, 다운로드는 하지 않는다.

## 3. 유지할 책임 경계

| 소유자 | 소유하는 것 | 소유하지 않는 것 |

| MythicTRPG | 실제 인물/참가자, 현재 관계, 게임 결과, 관측·소문 전달, 효과 검증 | 플레이어 발언의 임의 사실화 |

한 사건을 AI 모듈이 다시 실행하거나, 회상 횟수만큼 호감도/보상을 적용하지 않는다. 기억과 소문은 게임 액션 권한이 아니다. AI의 “주겠다”는 발언, 확인 대기, 실행 실패, 지급 완료를 별도로 취급한다.

## 4. 기억의 네 층

### 4.1 최근 대화와 진행 중인 질문

기존 최근 대화를 유지한다. 여기에 세션 한정 RecallFocus를 둔다: 질문 원문, 요청한 정보 종류, 시간 조건, 근거가 된 플레이어 턴, 선택 근거 ID/revision, 상태.

- 예: “내일 어디 간다고 했지?” 다음 “한번만 말해줘”는 같은 회상 요구를 이어간다.
- 후속 요청에서 NPC의 “내가 왜 기억해야 하지?”를 새 사실이나 주제로 채택하지 않는다. NPC 대사는 대화행위 해석에만 사용하고 플레이어의 계획 근거로 승격하지 않는다.
- 해결 여부는 증거를 제공했는지와 후속 플레이어 반응을 함께 본다. 생성 성공만으로 해결됐다고 확정하지 않는다.
- 제안 초기 상한: 최대 3개 후속 플레이어 턴 또는 5분. 명시적 화제 전환·다른 신·종료·generation 변경 시 즉시 해제한다. 수치는 시험 후 조정한다.
- 세션 종료 뒤에는 질문 상태를 그대로 부활시키지 않는다. 새 질문은 영속 기억에서 다시 조회한다.

### 4.2 원문 근거

기존 v1 원문 journal을 재사용한다. 출처·화자·청중·시각·순서·원본 ID를 유지하고, 후처리 완료 전에도 최근 허용 원문에서 조회할 수 있게 한다.

수락 직후 저장 큐가 아직 커밋하지 않은 발언은 제한된 메모리 캐시에 pending 상태로 보관해 같은 서버의 빠른 재대화에서 읽을 수 있게 한다. 저장 성공과 같은 것으로 표시하지 않는다. 실패하면 상태를 알리고, 크래시로 pending 내용이 사라질 수 있음을 명시한다. 다른 신/청중 경계를 통과하지 못한다.

### 4.3 정리된 기억

파생 기억은 원문을 대체하지 않는 별도 모델로 둔다. 아래 이름은 신규 구현용 제안이며 현재 스키마가 아니다.

| 필드 묶음 | 내용 |
|---|---|
| 식별/근거 | memoryId, sourceIds와 원문 hash/revision, 추출기 버전 |
| 권한 | worldId, ownerGodId, subjectPlayerId, 원래 청중 및 공개 범위 참조 |
| 의미 | 종류, 간단한 요약, 명시된 대상/장소, 원문 근거 발췌 |
| 시간 | recordedAt, eventTime/예정 범위, 시간 기준, 원문 시간 표현, 해석 확실성 |
| 상태 | 진술/계획/조건부/인용/농담/불확실, 활성/변경/상충/취소/보관 |
| 연결 | replaces, corrects, contradicts, 같은 경험 묶음; 동일 권한 범위 안에서만 연결 |

초기 종류는 취향·개인적 제약·계획·대화상 약속·경험이다. 게임 퀘스트와 일반 약속은 별개다. 중요도는 종류·미해결 여부·확정 게임 중요 사건을 우선 사용하고, 모델의 높은 확신이나 자극적인 표현 하나로 영구 중요 기억으로 만들지 않는다.

“수영을 못한다”는 플레이어의 자기 진술이지 게임 능력 판정이 아니다. “바다에 갈 것이다”는 예정이지 방문 성공이 아니다. “드래곤로드와 친하다”라는 주장과 서버가 확인한 관계는 출처가 다르다. AI가 낸 숫자형 confidence도 검증된 확률로 취급하지 않는다.

### 4.4 게임 경험과 수신 소문

게임 확정 경험은 게임 원본 기록의 읽기 전용 투영이다. 소문은 RumorSavedData가 해당 신에게 실제 전달한 기록의 투영이다. 둘을 개인 주장과 합쳐 사실로 승격하지 않는다.

신이 사건을 알고 있는가, 지금 청중에게 말해도 되는가, 그 사건을 어떻게 평가하는가는 각각 검사한다. “소문을 들었다”가 “소문 내용이 사실이다”를 뜻하지 않는다.

## 5. 시간·정정·망각

### 시간

9월 17일 사용자 결정으로 **“내일”은 현실 달력 날짜, “해가 뜨면/지면”은 Minecraft 태양/일광 주기**를 기준으로 한다. 앞서 제안한 Asia/Seoul 및 현재 UNSPECIFIED/REAL_KST 설정의 실제 운영 적용·검증은 별도 확인한다. 시간 기준 선택을 미응답으로 다시 취급하지 않으며, 이번 문서 변경만으로 서버 설정을 바꾸지 않는다.

- 현실 기준 예: 9월 15일에 “내일 바다에 간다” → 9월 16일 예정. 이후 날짜가 바뀌어도 예정 날짜를 다시 이동시키지 않는다.
- 발언 시점과 사건 시점을 따로 저장한다. 시간 추정의 기준은 원문 턴이며 추출 실행일이 아니다.
- “어제 말한 내일 일정”은 발언 날짜 조건과 예정 날짜 조건을 분리한다.
- “아침이 되면”, “게임에서 사흘 뒤”는 명시적인 게임 시간 조건으로 남긴다. 게임 일광 시각과 단조 증가 tick을 혼동하지 않는다. 잠자기·시간 명령의 정책이 없으면 정확한 현실 날짜로 변환하지 않는다.
- “나중에”, “다음에”는 미정 범위다. 모델이 임의 날짜를 채우지 않는다. 예정일이 지났다고 완료되거나 약속을 어겼다고 확정하지 않는다.
- 날짜 계산은 허용된 프로그램 로직으로만 수행한다. 모델이 생성한 Python/명령을 실행하지 않는다.

### 정정

새 발언을 먼저 기록하고, 원문에 근거해 같은 주장/계획과 연결한다. 일상 정정에 기존 원문을 제거하는 supersede API를 무조건 사용하지 않는다. 파생 기억의 현재 유효 상태를 바꾸고 이전 경험과 변경 순서를 보존한다.

- “바다 말고 산에 가기로 했어”: 같은 계획임이 명확하면 이전 계획을 대체한다.
- “바다에도 가고 산에도 갈 거야”: 복수 계획으로 보존한다. 최신 발언이라고 이전 것을 지우지 않는다.
- “수영을 배웠어”: 과거 제약과 현재 자기 진술의 변화를 연결한다. 실제 능력 검증은 별개다.
- “B가 수영을 못한대”: 화자 A의 자기 특성으로 넣지 않는다. B의 정식 개인 기억으로 몰래 복사하지도 않는다.
- 근거가 모호하면 상충 상태로 함께 보관하고, 필요한 대화에서 확인한다. 말하는 사람의 주장만으로 게임 완료나 다른 신의 소문을 취소하지 않는다.

### 망각과 용량

초기 배포는 원문의 파괴적 자동 삭제를 비활성화한다. 미완료 약속·중요 공동 경험은 장기 유지하고, 잡담은 회상 순위를 낮춘 뒤 보관층으로 옮기는 방식을 먼저 검증한다. 보관과 삭제는 다른 상태다.

현재 v1의 30일 검색 만료와 전체 12,000건/신·플레이어별 2,000건 상한은 실제 구현의 제약이다. 파생 기억만 추가하면 이 용량 문제는 해결되지 않는다. 운영 확대 전 활성/보관 분할, 디스크 상한, 재색인, 쓰기 거절 알림을 함께 검증한다. 보관 기간·물리 삭제 정책은 운영 선택으로 남긴다. 용량이 찼다고 중요한 기억을 조용히 제거하지 않는다.

관리자 forget은 원문·파생 요약·벡터·캐시·진행 중 참조까지 무효화한다. 백업/과거 로그의 보안 삭제까지 완료했다는 뜻은 아니다. 구현 오류로 취소된 게임 소문과 게임 내 해명은 다른 절차로 처리한다.

## 6. 회상 파이프라인

~~~text
게임 스레드: 현재 인물·청중·관계·generation의 작은 불변 snapshot
  → AI 작업: 현재 발화 + 최근 문맥 + RecallFocus로 조회 계획
  → 권한으로 제한된 동일 revision의 기억 view
  → 단어 / 의미 / 시간·종류 / 최근 원문 후보 조회
  → 필요 시 기존 1단계 분류 + 제한된 조회 보정 1회
  → 출처·정정·공개 범위 검사, 최종 근거 최대 3개
  → 기존 대사·Proposal 생성
  → 게임 스레드: 세션·턴·근거 revision·권한 재검증 → 표시/기존 Gateway
~~~

### 6.1 조회 계획과 분류

조회 계획은 일반 연상, 명시적 회상, 진행 중 회상 재요청, 정정 확인, 무관한 발화로 구분한다. 이는 AI 내부의 조회 의도이며 새 게임 액션이 아니다. 낮은 확신은 UNKNOWN으로 남긴다.

- 특정 장소/문장의 고정 답변 사전을 만들지 않는다. 시간 표현·인용·의문 형태·현재 미해결 질문 등 범용 신호로 초기 후보를 구한다.
- 기존 1단계 분류에 회상 대화행위와 제한된 조회 힌트를 선택적으로 지원한다. 분류 호출이 이미 필요한 턴에서는 그 호출을 재사용하고 별도의 질문 재작성 LLM을 추가하지 않는다.
- 새 필드는 주제/기억 종류/원문 시간 표현 정도로 제한한다. 모델은 신·플레이어·권한·게임 사실 ID를 지정하지 못한다. 누락/불명 값은 기존 동작으로 해석한다.
- fast-social 경로가 명시적 회상 질문을 단순 인사/잡담으로 끝내지 않도록 한다. 기존 분류 생략 턴이 분류 경로로 전환되는 경우는 호출 수 증가로 별도 측정한다.
- ConversationAct의 기존 SHARING_RECENT_EVENT 또는 ANSWERING_NPC_QUESTION 지침이 회상 요청과 충돌하지 않도록 최종 directive에서 조정한다. 물음표가 없거나 NPC가 반문했다는 이유만으로 정보 요청을 지우지 않는다.

분류 전 1차 근거와 분류 후 최종 근거가 달라질 수 있다. 둘은 동일 권한/동일 불변 view에서 가져오며, 새 검색을 위해 현재 세션 밖의 데이터를 추가로 열지 않는다. 보정은 최대 1회, 같은 전체 검색 예산 안에서 수행한다. 보정 결과에 맞춰 effective intent/directive를 일치시키고 1차·최종 ID 및 변경 이유를 모두 기록한다. 변경된 근거를 분류 모델이 이미 봤다고 로그에 표현하지 않는다. 기존의 분류·생성 동일 문자열 주입에서 바뀌는 부분이다.

### 6.2 후보 경로와 선택

| 경로 | 주 역할 | 주의점 |
|---|---|---|
| 단어 검색 | 고유명·아이템·정확한 표현 | 한국어 정규화/부분 일치 유지; BM25 비교 가능 |
| 의미 검색 | 다른 표현의 유사한 경험 | 부정·인용·주체/시점은 벡터 점수만으로 판정하지 않음 |
| 시간·종류 조회 | 내일 계획, 미완료 약속, 변경된 일정 | 날짜 해석이 모호하면 과도한 hard filter 금지 |
| 최근 원문 | 방금 종료한 세션, 아직 미추출된 사실 | 명시적 회상/이어지는 질문에 한정; 최근성만으로 관련성을 확정하지 않음 |

권한 검사 후 후보 합집합을 제한하고, 정확한 조건 충족·관련성을 먼저 본다. 출처, 현재 유효성, 중요도, 최근성은 그 다음이다. 단어 점수와 벡터 점수를 같은 척도로 바로 더하지 않고 채널별 순위를 결합해 비교 검증한다. 정답이 후보에 없는데 top-k를 채우려고 무관한 기억을 넣지 않는다.

제안 초기 상한: 전체 후보 12개, 미추출 최근 원문 조회 6턴, 프롬프트 근거 0~3개. 일반 회상에서는 기억 데이터 약 800자 기존 한도를 유지하고, 정확한 재질문/상충 설명에만 최대 1,200자를 시험한다. 직접 기억·소문·평판을 모두 합산한다. 숫자는 시험 설정이며 현재 적용값이 아니다.

“내일 어디 간다고 했지?”는 바다라는 단어가 없어도 계획/예정 시점 후보에서 찾는다. 후처리 전에는 허용된 최근 원문 후보를 함께 읽는다. 오래되고 아직 추출되지 않은 광범위한 기록까지 반드시 찾는다고 보장하지 않는다. 처리 대기와 후보 누락을 별도 진단한다.

### 6.3 원문·요약·모델의 한계

검색 결과 상태를 FOUND / AMBIGUOUS / NO_MATCH / UNAVAILABLE / PENDING_INDEX로 구분한다. 내부 권한 거절 이유나 숨은 기억의 존재는 플레이어에게 노출하지 않는다.

- FOUND: 질문에 필요한 근거가 있으므로 먼저 그 의미에 답하도록 한다. 말투·농담·거절 여부는 실제 신의 성격과 관계 안에서 표현한다.
- AMBIGUOUS: 후보 차이를 짧게 확인하며 빈틈을 창작하지 않는다.
- NO_MATCH: 검색된 근거가 없다는 뜻이지 그 대화가 없었다는 증거가 아니다.
- UNAVAILABLE/PENDING_INDEX: 기술적 조회 제한을 허구의 과거·성격·감정으로 설명하지 않는다.

반말/거절을 금지하거나 신을 모두 친절하게 만들지 않는다. 다만 검색 실패 자체가 새로운 적대감의 근거가 되지는 않는다. 중요한 기억도 매번 “기억한다”라고 말하지 않고 현재 선택·반응에 필요한 경우만 활용한다.

프롬프트는 근거 데이터와 짧은 활용 지침을 분리한다. 기억 속 명령/role 구분 문자열은 데이터로 인용한다. 전체 context의 잘라내기로 action constraint, validator feedback, 현재 발화, 공개 제한이 사라지지 않도록 필수 문맥을 먼저 예약하고 기억을 남은 예산에 넣는다. 출력 JSON에 기억 분석/평가 필드를 추가하지 않는다.

## 7. 의미 검색·후처리의 실행 방식

### 의미 검색

별도 상용 메모리 서비스나 대형 그래프 DB부터 설치하지 않는다. 교체 가능한 로컬 EmbeddingProvider와 작은 권한별 색인을 둔다. 원문/정리된 기억 벡터는 사전 계산하고, 질의 벡터는 필요할 때 최대 1회 계산한다.

한국어 표현·부정·게임 고유명 테스트로 소형 다국어 모델 후보를 비교한 뒤 모델/차원/실행 방식/라이선스를 결정한다. CPU 실행을 우선 평가해 대화 GPU 경합을 줄이는 안이며 성능을 보장하지 않는다. 새 모델이나 런타임 설치는 별도 승인 사항이다. 모델을 자동 교체·다운로드하지 않는다.

- 벡터에는 원본 hash, source revision, 임베딩 모델 fingerprint/차원/전처리 버전을 연결한다. 모델이 바뀌면 재색인 전 다른 벡터와 혼합하지 않는다.
- 저장 색인은 권한별로 분리하거나 검색 전에 허용 ID로 제한한다. 전역 top-k 후 필터만 하는 구조를 기본값으로 쓰지 않는다.
- 캐시는 월드·신·플레이어·청중·질문·RecallFocus·기억 revision으로 격리한다. 삭제·세션 변경·모델 변경으로 무효화한다.
- 질의 벡터 지연/실패 시 단어+시간+원문 결과를 유지한다. 의미 검색 실패가 정상 조회 결과까지 비우면 안 된다.
- 스냅샷 조회/검색/임베딩 대기는 게임 tick 밖에서 수행한다. ServerPlayer나 살아 있는 월드 객체를 worker로 전달하지 않는다.

### 자동 기억 정리

검증된 원문을 작은 묶음으로 읽고 파생 기억 후보를 추출한다. 묶음은 같은 신·플레이어·공개 범위로 제한한다. 근거 없는 사실, 다른 화자, 부정 반전, 날짜 임의 추정, 새 권한/효과 부여를 거절한다. 모호한 의미를 구조 검사만으로 완벽히 검증할 수는 없다.

기본 제안은 접속자 0명, 모든 foreground 모델 작업/대기 없음일 때만 후처리 1건을 허용하는 보수적 방식이다. 오래 접속자가 있으면 정리가 밀릴 수 있으므로 최근 원문 경로를 유지하고 backlog를 표시한다. 유휴 접속 중 실행은 부하 검증 후 별도 옵션으로 둔다.

LocalOllamaClient마다 있는 scheduler는 전 서버의 GPU 경합을 막지 못한다. 공통 작업 입장 관리에 대화·자발적 대사·건축 시각 평가·추출을 포함해야 한다. 모든 관련 경로가 등록됐음을 확인하기 전 자동 후처리를 활성화하지 않는다. 이미 시작한 GPU 작업을 즉시 선점할 수 있다고 가정하지 않으며, 경합이 크면 수동 관리 시간에만 정리한다.

대화 세션 6개와 GPU 동시 추론 6개를 동일시하지 않는다. 기존 추론 동시성 설정은 유지하고 플레이어별 순서·공정한 대기·유한 큐를 검증한다. 모델 호출 횟수와 프롬프트 증가로 인한 지연을 각각 기록한다.

## 8. 영속성·이관·늦은 작업

- 기존 원문 v1은 먼저 유지하고, 정리된 기억/색인을 별도 버전형 sidecar로 추가한다. 제안 경로는 개인 기억 디렉터리 아래 derived-v2; RUMOR_TEST에도 별도 시험 경로를 사용한다. 경로/스키마는 구현 시 확정한다.
- 자동으로 옛 OPELA/v2 기억을 이관하지 않는다. 원본 v1의 유효 레코드만 읽고 진행 cursor와 원본별 처리 ID로 재시작한다. sidecar가 손상되면 격리하고 v1 원문 조회로 복구한다.
- 파생 기억도 단일 작성자·원자적 snapshot·schema 검사·상한을 가진다. 원문 저장 성공 전 추출 커밋하지 않는다. 후처리 cursor는 파생 기록의 내구성 확보 뒤 전진한다.
- 실제 대화 응답은 세션/generation/turn이 바뀌면 폐기한다. 반대로 이미 수락·저장된 과거 발언의 정리는 세션 종료 뒤에도 가능하다. 원문 revision/삭제/권한을 재검증하되 종료됐다는 이유만으로 영속 정리를 영구 누락시키지 않는다.
- 서로 다른 플레이어의 정상 쓰기로 모든 대화가 무효화되지 않도록 선택 근거별 revision/hash를 검증한다. 동일 주제에 관련 정정이 추가됐을 때도 오래된 선택 결과를 무효화할 수 있는 bucket/query revision을 둔다.
- 데이터 삭제/정정과 인덱스 갱신은 일관된 이벤트로 처리하고, 늦은 embedding/추출이 삭제된 내용을 부활시키지 못하게 한다. 반복 재시도는 상한을 두고 오류를 노출한다.
- 메모리 요약·새 검색을 끄더라도 기존 원문을 계속 읽을 수 있도록 한다. 파괴적인 v1 이관은 이 단계에 포함하지 않는다.

## 9. 게임 경험·관계·소문 연결

### 9.1 관계 읽기 연결

게임의 기존 PlayerMythDataService/프로필 관계 원본에서 현재 신과 플레이어의 관계를 턴 snapshot으로 읽는다. 기존 Provider가 실제 이 경로에서 소비되는지 검증하고, 아니라면 작은 읽기 전용 계약을 추가한다. 새 affinity DB나 기억 기반 감정 점수 원본을 만들지 않는다.

기존 관계 단계 매핑을 먼저 찾아 재사용한다. 사용 가능한 게임→태그 매핑이 없으면 숫자를 임의 구간으로 확정하지 않고 별도 콘텐츠 선택으로 제시한다. 순간 감정은 기존 문맥 처리 범위로 유지하며 중립 감정 시작을 곧바로 버그로 판정하지 않는다. 힘의 관계도 제공된 정보만 사용한다.

이 연결은 개인 회상의 AI-only 변경과 별도 패치/스위치로 검증한다. 최종 자연스러움 수용에는 실제 게임 관계가 프롬프트에 들어오는지 확인이 필요하다. 수동 /ai_test 관계값만 바꾼 결과를 운영 연동 성공으로 보고하지 않는다.

### 9.2 먼저 연결할 게임 경험: 신에게 확인받은 퀘스트 완료

QuestRuntimeService의 authoritative 완료 기록이 근거다. 기존 AiQuestCompletionContext에는 영구 발생 ID/세계/청중 정보가 충분하지 않으므로 대사 콜백만 journal로 복사하는 방식은 쓰지 않는다.

제안은 기존 완료 기록을 참조하는 추가 GameExperienceReceipt/조회 Provider다. 이름은 가칭이며 게임의 memorycontract 패키지에 둔다. 기존 DTO 생성자/콜백을 깨지 않고 별도 capability로 제공한다.

- 게임이 발급하는 안정적 발생 ID, 대상, 직접 확인한 신, 허용 청중, 원본 기록 참조/revision, 제한된 설명을 전달한다.
- 우선 NPC 확인 완료만 대상으로 한다. AUTO 완료나 서버 전역 완료를 모든 신이 즉시 아는 경험으로 바꾸지 않는다.
- 완료자와 당시 수주자, FTB 팀 동료는 구분한다. 다른 수주가 무효화된 플레이어에게 “함께 완료했다”는 기억을 주지 않는다.
- 퀘스트 완료와 보상 지급/선택 대기는 다른 상태다. 현재 코드도 완료 후 보상 claim 실패 가능성을 기록하므로 완료 receipt만으로 “보상을 받았다”를 추정하지 않는다.
- AI가 없거나 기억 쓰기에 실패해도 게임 완료를 되돌리지 않는다. 게임 원본 기록과 receipt cursor로 재시도하며, 같은 receipt의 재생은 멱등이고 퀘스트/보상 실행기를 재호출하지 않는다.
- 과거 기록에 신/청중 정보가 없으면 자동 과거 채우기를 하지 않는다. 운영 시작 이후 명확한 출처부터 연결한다.

건축 평가·즉석 퀘스트·스토리는 후속 수직 연결로 추가한다. 스토리의 일회성 hook 별칭/token과 숨은 Fact ID는 영구 기억에 넣지 않는다. 게임이 재검증할 수 있는 불투명 공개 참조가 없으면 해당 정사 기억은 보류한다. 레이드의 미확정 규칙은 설계로 확정하지 않는다.

### 9.3 소문과 신별 평가

기존 관찰→주장→전달 완료 경로를 사용한다. 파생 개인 기억에서 다른 신에게 직접 복사하지 않는다. 같은 사건의 원문을 재사용하더라도 전서구 관측권한을 통과한 발췌만 후보 분석에 쓴다.

- 대화/행동의 실제 관측이 먼저이며, AI는 맥락 해석·수식어 후보만 제안한다. 등록된 범주·빈도·근거 조건을 서버가 검증한다.
- 신마다 수신 여부, 출처 신뢰, 관심, 직접 경험, 가치관이 다르다. 같은 소문이 모든 신의 동일 태그/거절을 강제하지 않는다.
- 중요한 업은 대표 명성을 바꿀 수 있지만 과거 사건을 일괄 삭제하지 않는다. 다른 신이 새 업을 아직 못 들었으면 반응이 달라도 된다.
- 회상→소문→회상의 반복을 독립 증거로 중복 계산하지 않는다. 원본 계보를 유지하고, NPC의 소문 재진술을 플레이어의 자백으로 저장하지 않는다.
- 전서구 사냥은 게임이 지정한 관찰 대상 플레이어만 차단한다. B를 통해 A의 평가를 우회 전달하지 않는다. 사냥/전달/늦은 분석은 동일 게임 순서와 epoch 검증을 따른다.

기존 설계의 제안 기본값(이미 수신한 기억 유지, 미전달분 무효화, 부활 후 밀린 소문 일괄 전파 없음, 긍정/부정 함께 차단)은 이번에도 운영 확정과 구분한다. 물리 개체의 귀속·스폰·재생성, 신화권 정보망, 실제 효과 강도/회복 조건은 해당 단계 전에 선택한다.

처음에는 제한된 소문과 첫인상 대사만 검증한다. 소문 기반 기계적 불이익은 별도 승인된 정책이 있을 때만 적용한다. 첫인상 전용 실행 모드가 필요하면 기존 RUMOR_TEST를 운영 모드로 재해석하지 않고 새 명시적 capability/설정으로 설계한다. RUMOR_TEST의 Proposal 차단·시험 기억 분리는 그대로 유지한다.

## 11. 구현 단계와 통과 조건

아래 번호는 개인 회상 설계 당시의 구분이다. 행동 기록·신별 주시가 추가된 전체 순서와 단계 대응은 [최신 로드맵 3절](ACTION_OBSERVATION_MEMORY_ROADMAP_20260915.md)을 따른다. 개인 대화 회상은 행동 원장 완성을 기다리지 않고 진행할 수 있다.

### 0단계 — 비교 기준 고정

LP 원본/필수 소스 백업과 현재 0.1.3 전체 입력·JAR·설정·기억을 구현 직전에 별도 보존하고 manifest를 검증한다. LP는 스타일 기준, 현재 0.1.3은 검색/성능 대조군이다. 오래된 테스트 숫자를 새 검증 결과로 쓰지 않는다.

9월 15일 사례는 회귀 표본에 포함하되, 같은 문장을 정답 사전으로 만들지 않는다. 검색 후보·시점·분류·생성·후속 대화별 실패를 기록할 평가 도구를 먼저 준비한다.

### 1A단계 — 즉시 체감 가능한 개인 회상

RecallFocus, 시간 기준/상태 표현, 명시적 회상 의도, 최근 원문 fallback, 프롬프트 예산/누락 처리, 진단 로그를 구현한다. 새로운 임베딩 모델이나 자동 추출을 필수로 두지 않는다. 미래 일정·재질문·화제 변경·새 세션 시나리오를 통과시킨다. 이 단계만으로 모든 장기 의미 회상이 완성됐다고 하지 않는다.

### 1B단계 — 정리된 기억과 의미 검색

sidecar 저장/정정/원문 연결을 먼저 구현하고 고정 fixture로 검색을 검증한다. 임베딩을 shadow 비교해 효과·부하를 확인한 뒤 선택 활성화한다. 자동 추출은 공통 모델 작업 입장 관리 완료 후 유휴 처리로 연결한다. 관계 읽기 연결은 별도 변경으로 확인해 실제 관계별 대사 비교에 사용한다.

1A와 1B는 각각 끌 수 있어야 한다. 1B가 지연이나 잘못된 정정을 유발해도 1A와 v1 원문 기억으로 돌아갈 수 있게 한다.

### 2단계 — 공동 경험

NPC 확인형 퀘스트 완료 receipt 하나를 종단 연결해 다음 세션의 회상까지 검증한다. 완료/수주/보상 차이, FTB 팀/전역 범위, 재시도 중복을 통과한 뒤 다른 게임 경험으로 확장한다.

### 3단계 — 전서구와 소문 대사

물리 전서구·관측·대상별 차단을 연결한 다음, 제한된 수신자와 소문 범주로 신별 반응을 비교한다. 재생성·귀속 등 미확정 선택을 먼저 받는다. 기계적 불이익은 아직 켜지 않는다.

### 4단계 — 평판의 게임 효과

대표 수식어, 신별 제한된 효과, 반증·해명·큰 업·직접 관계에 따른 회복을 등록 정책으로 연결한다. 과거 관계를 일괄 덮거나 회상마다 점수를 누적하지 않는다. 콘텐츠 밸런스는 별도 승인 대상이다.

## 12. 검증 설계

### 표본과 비교 방식

초기 제안은 12개 범주별 한국어 시나리오 10개, 총 120개다. 절반은 개발에 쓰고 절반은 표현/이름/시점이 다른 보류 평가용으로 고정한다. 단일 문장 맞추기 대신 앞선 대화·종료·재접속·정정을 포함한 흐름을 평가한다.

| 범주 | 필수 예시 |
|---|---|
| 직접/간접 회상 | 장소를 직접 묻기, 장소를 말하지 않고 일정 묻기 |
| 의미 연결 | 수영 불가와 깊은 물 이야기; 관련 없는 바다 관용구는 제외 |
| 시간 | 날짜 경계, 어제 말한 내일, 미정 일정 |
| 정정 | 일정 변경/취소와 추가 일정 구분 |
| 부정/인용 | 못한다/할 수 있다, 타인의 말/농담 구분 |
| 후속 질문 | 한 번만 알려줘, 다시 묻기, 명시적 화제 변경 |
| 미추출/재접속 | 저장 직후 재시작한 대화, 서버 재시작, backlog |
| 모르는 정보 | 기록 없음, 검색 실패, 다중 후보, 삭제 기억 |
| 관계/자연스러움 | 중립·신뢰·적대, 다른 성격의 신, 반복 회상 억제 |
| 정보 격리 | 다른 신/플레이어/월드/청중, 숨은 소문 |
| 게임 권한 | 제안/확인 대기/거절/완료/지급 실패 구분 |
| 동시성/소문 | 6세션, 삭제와 응답 경합, 사냥과 전달 경합 |

검색-only 고정 평가와 실제 모델 생성 평가를 분리한다. 1B의 추출 품질은 원문에서 파생 기억까지 end-to-end로도 평가한다. 정답 구조화 데이터를 수동 입력한 테스트만으로 자동 기억 기능을 통과시키지 않는다.

동일 모델·프로필·출력 설정에서 현재 0.1.3 / 1A / 1B를 비교한다. LP는 기억이 없는 스타일 대조군으로 따로 본다. 관계 입력 변경과 검색 변경을 한 번에 섞지 않고 각각 비교한다. 실제 생성은 여러 seed/반복을 사용하고 실행 순서를 교차해 캐시·워밍업 영향을 구분한다. 최종 자연스러움은 사용자 블라인드 비교를 포함한다.

### 제안 수용 기준 — 실측 성적이나 보장치가 아님

- 보류 평가의 답할 수 있는 간접 회상: 최종 근거 Recall@3 90% 이상을 초기 목표로 한다. 시간/정정/의미 범주를 각각 보고해 평균에 가리지 않는다.
- 정확한 근거를 준 경우 답변의 사실 일치와 없는 사실 단정을 별도 집계한다. 명확한 계획/정정 핵심 사례는 전부 통과해야 한다.
- 신/플레이어/청중 누출, 삭제 부활, 무권한 실행·보상 중복, 다른 세션 응답 적용은 필수 테스트에서 0건이어야 한다. 이는 운영에서 오류 0을 보장한다는 뜻이 아니다.
- 자연스러움은 질문에 답함, 성격/관계 일치, 불필요한 회상·훈계·허구의 친밀감, 후속 대화 일관성을 평가한다. 정확도가 올라도 명백히 부자연스러워진 버전은 채택하지 않는다.
- 검색 자체는 게임 tick을 기다리게 하지 않는다. 의미 질의 포함 추가 처리의 초기 목표 p95 250ms 이내, 1/4/6인 전체 응답 p95는 대조군 대비 10% 이내 증가를 제안한다. 실제 하드웨어 측정 후 수용 여부를 결정하며, 기준을 넘으면 기능 축소/재설계 후 재비교한다.
- 직접 인사 0회→생성/분류 전환, 모델 교체, 첫 호출과 후속 호출은 별도 측정한다. 후처리 실행 중 foreground 진입과 최대 대기·플레이어별 공정성을 포함한다.

### 진단 기록

기존 MEMORY_RECALL을 확장해 조회 모드, 초기/최종 후보 ID, 경로별 선택 이유, 시간 해석, 근거 revision, 상태, 검색/임베딩/큐/분류/생성/재시도/HUD 시각을 구분한다. 저장 거절·후처리 backlog·색인 누락도 표시한다. 사용자 화면에는 내부 ID/숨은 기억을 출력하지 않고, 디버그 원문은 관리자 권한·보존 정책을 적용한다.

문서 작성만 한 이번 작업에서는 위 테스트, 컴파일, LLM 재생, 부팅을 수행하지 않는다.

## 13. 비활성화와 복원

현재 OFF/PERSONAL/RUMOR_TEST의 의미는 유지한다. 개선 기능은 AI 측 별도 버전형 설정에 recallV2, semanticRetrieval, consolidation 같은 독립 스위치로 제안한다. 파일이 없거나 설정이 잘못되면 현재 v1 동작으로 되돌고 자동 모델 작업을 시작하지 않는다. 실제 키 이름은 구현 때 확정한다.

1차 복원은 새 기능과 후처리를 끄고 현재 0.1.3 기준 동작/원문을 유지하는 것이다. 진행 중 신규 작업을 무효화하고 sidecar는 삭제하지 않는다. 게임 관계/경험 receipt 변경도 별도 capability로 비활성화할 수 있게 한다. OFF로 끄는 것과 과거 LP 바이너리 복원은 다르다.

LP 원본 JAR과 필수 소스, 기억 기반 전 게임 전체 백업, 구현 직전 새 백업은 서로 구분한다. 보존 경로/절차는 [기반 가이드의 복원 절](LP_MEMORY_FOUNDATION_GUIDE.md)을 따른다. LP 폴더에 신버전 파일을 넣지 않는다. Git이 없는 AI 디렉터리와 사용자 미커밋 변경을 포함한 게임 저장소를 git reset으로 복원하지 않는다.

배포/복원은 별도 승인 뒤 정상 종료 상태에서만 한다. 게임 계약을 바꾼 경우 서버·클라이언트·AI 조합을 함께 검사한다. 기존 월드·아이템·완료 퀘스트를 임의로 되감지 않는다. 신규 SavedData가 있는 월드를 옛 게임 JAR이 안전하게 보존하는지 확인 전 완전한 LP 다운그레이드를 보장하지 않는다.

## 14. 남은 선택과 승인 단위

현실 날짜/게임 일광의 기본 구분은 5절과 같이 확정됐다. 다음 콘텐츠 논의는 [후속 정책 5절](ACTION_RECORDING_POLICY_20260917.md)의 중요 사건 대상/장소와 통계 기반 관찰이다. 원문 보관 기간, 임베딩 모델 설치/실행 방식, 관계 단계 매핑이 없는 경우의 기준과 시간 적용의 세부 설정은 해당 구현/운영 전에 확인한다. 보관 용량은 측정 뒤 결정한다는 기존 선택을 유지한다.

전서구의 개체 수·귀속·재생성, 신화권 정보망, 소문 범주와 불이익/회복은 개인 기억 구현을 막지 않는 후속 선택이다. 예시 속 신의 금기나 장비 의미를 정사로 자동 확정하지 않는다.

후속 로드맵 기준 권장 첫 승인 범위는 **공통 기준/계약 정리 + 개인 회상(본문의 1A) 소스/오프라인 검증**이다. 실제 LLM 비교와 서버 배포·실행은 별도 범위로 확인한다. 1B의 검색 비교는 독립적으로 진행할 수 있지만 행동 기억의 운영 적용은 신별 관찰 권한 검증 뒤에 한다. 상세 행동 기록과 주시/소문의 다음 묶음은 [최신 로드맵 13절](ACTION_OBSERVATION_MEMORY_ROADMAP_20260915.md)을 따른다. 현재 요청은 설계 작성이며 구현 착수 승인이 아니다.

## 15. 참고한 연구와 적용 판단

- 원문과 추출 기억의 보완 관계는 [Redis AI Research의 2026년 기술 보고서](https://redis.github.io/redis-ai-research-public/longmemeval-agent-memory/)를 참고했다. 특정 제품 설치를 요구하는 설계가 아니며 기업 실험 성적을 우리 한국어 모델 성적으로 가져오지 않는다.
- 사건 날짜를 연결하는 방식은 [TReMu, Findings ACL 2025](https://aclanthology.org/2025.findings-acl.972/)를 참고했다. 모델 생성 코드 실행은 도입하지 않는다.
- 여러 세션·정보 갱신·시간·모름을 나눠 평가하는 방식은 [LongMemEval 연구진 자료](https://xiaowu0162.github.io/long-mem-eval/)를 참고했다. 검색 성공과 읽기/답변 성공을 분리한다.
- 인물별 정보 구조는 [GroupMemBench, 2026년 5월 프리프린트 소개](https://www.microsoft.com/en-us/research/publication/groupmembench-benchmarking-llm-agent-memory-in-multi-party-conversations/)를 참고했다. 신별 지식/소문 경계에 적용한 내용은 프로젝트를 위한 설계 판단이지 해당 논문이 Minecraft 구현을 검증했다는 의미가 아니다.

검토 절차에는 mythai-integration과 mythai-dialogue-review를 사용했다. 그 결과 게임 권한/FTB 소유권을 보존하고, 검색과 분류·말투를 별도 검증하며, 현재 문서의 과거 구현 설명을 실제 코드와 구분했다.

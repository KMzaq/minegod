# LP 기반 장기기억 관리 설계안

2026-09-12 / 검토용·미승인 / 코드·설정·서버에는 적용하지 않음

사용자 확인 반영: 평소 4~5명, 최대 6명 접속하며 6명 모두 동시에 AI 대화할 수 있다. 동시 요청에 따른 대기는 허용하지만 불필요한 기억 처리로 더 지연시키지 않는다. 중요한 사건·약속은 오래 유지하고 사소한 잡담은 점차 잊는다. 아래 구현 자체는 아직 승인·적용되지 않았다.

## 1. 목표와 확인한 기준

목표는 모든 대화를 외우는 챗봇이 아니라, 신이 플레이어와 쌓아 온 경험을 기억하는 RPG다. LP의 말투·분류·출력 형식을 유지하고 회상에 필요한 자료만 보완한다. 기억으로 친밀함이나 적대감을 강제하지 않으며 퀘스트·보상·세계의 사실을 AI가 새로 확정하지 않는다.

이번 설계 시작 시 확인:

- `dev-tools/Test-LPBuild.ps1` 통과. AI 응답 265개, 콘텐츠 69개 파일 엔트리 및 두 JAR 전체 SHA-256이 LP 원본과 일치한다.
- `server/backups/LP-source-20260912/file-manifest.csv`의 298개 보존 파일 해시 검증 통과. 이 백업과 `server/backups/LP/`는 수정하지 않는다.
- 현재 게임 모드는 유지한다. 게임 전체 소스는 위 LP 소스 백업에 포함되지 않으므로, 향후 게임 계약 수정 전에는 별도 백업이 필요하다.
- 이번 작업에서는 새 LLM 요청, 빌드, 배포, 서버 실행 또는 기억 데이터 변경을 하지 않았다. 아래 성능 수치·상한은 측정 결과가 아닌 초기 실험안이다.

현재 대화 진입은 `MythAiConversationEngine → GodAiDialogueService → AiTestDialogueAdapter`다. 현재 운영 facade는 플레이어 1명·신 1명을 대상으로 한다. 최근 20개 메시지를 세션 메모리에서 보관하고 종료 시 제거한다. 인사 같은 직접 응답, 분류를 생략하는 잡담, 분류 후 생성하는 일반 경로가 있으며 기존 재시도/수정 생성도 있어 항상 AI 호출 1회인 것은 아니다.

예전 `NpcMemoryEngine`, `MemoryRetriever`, `JsonFileMemoryRepository`는 남아 있지만 현재 운영 대화에서 연결되지 않는다. 키워드·태그·중요도·최근성 검색 개념은 재사용할 수 있다. 다만 저장마다 전체 파일을 동기 재작성하며 출처·월드·공개 범위·정정 이력이 부족해 그대로 활성화하지 않는다.

OPELA 실험본의 출처·청중 격리와 정정 검증 아이디어는 참고할 수 있지만, 오버레이·감정 분석·품질 평가·출력 스키마 튜닝을 통째로 재적용하지 않는다.

## 2. 제안: 최근 문맥 + 개인적 기억 + 함께 겪은 사건

| 층 | 내용 | 관리 방식 |
|---|---|---|
| 최근 문맥 | 방금 한 말, 진행 중 화제·놀이 | LP의 최근 20개 메시지 유지. 재접속 연결이 필요한 경우 짧은 직전 세션 메모를 별도 후보로 저장 |
| 개인적 기억 | 플레이어가 말한 취향·두려움·계획, 서로의 약속, 아직 해결하지 않은 대화 | 발언자·원문 근거·시각을 함께 저장. 주장과 객관적 사실을 구분 |
| 공동 경험 | 해당 신의 퀘스트 완료, 건축 평가, 실제로 전달된 중요한 사건 | 게임이 확정한 결과를 토대로 해당 신에게 허용된 경험만 기록. 현재 상태는 게임에서 다시 조회 |

신 프로필·정적 로어는 콘텐츠 레지스트리에 그대로 둔다. 현재 호감도·인벤토리·퀘스트 진행·스토리 정사는 MythicTRPG에서 읽는다. 이를 장기기억 DB의 독립적인 현재 사실로 복제하지 않는다.

예시:

- “난 수영을 못해” → `플레이어가 수영을 못한다고 말했다`. 게임 능력으로 확정하지 않는다.
- “밀을 가져다줄게” → 대화상의 약속. 퀘스트 수주·아이템 전달 성공으로 저장하지 않는다.
- 게임의 건축 평가 완료 통지 → 평가받은 경험과 당시 결과. 보상을 다시 지급할 근거가 아니다.
- AI가 “성으로 데려다주겠다”고 말함 → NPC가 한 발언. 실제 이동 기능이나 월드 사실로 승격하지 않는다.
- 모욕 후 사과 → 두 사건과 순서를 유지한다. 새 발언으로 과거 사건을 지우거나 자동 호감도 변경을 하지 않는다.

같은 기억의 해석은 신의 기존 성격과 게임이 제공하는 관계 문맥에 맡긴다. 기억 모듈이 모든 신에게 동일한 감정·답변을 지정하지 않는다. LP의 실제 관계 값 연동 범위도 이번 기억 추가만으로 개선됐다고 주장하지 않는다.

## 3. 저장 모델과 생명주기

### 3.1 최소 메타데이터

`memoryId`, `worldId`, `ownerGodId`, `subjectPlayerId`, 원본 세션/턴 식별자, 발언자, 당시 청중, 허용 공개 범위, 출처 종류, 근거 발췌/원문 참조, 발생 순서, 요약, 검색 태그, 정정 관계, 상태, 최근 사용 기록을 둔다.

출처는 최소한 `PLAYER_STATEMENT`, `NPC_UTTERANCE`, `GAME_CONFIRMED`를 구분한다. “이 발언이 실제로 있었다”와 “발언 내용이 사실이다”는 다른 확실성이다. AI 추출기는 게임 확인 등급이나 공개 권한을 만들 수 없다.

상태는 후보·활성·상충·대체됨·보관·삭제를 구분한다. 중요한 기억의 우선순위도 출처와 분리한다. 반복된 거짓말이 중요해질 수는 있어도 반복만으로 게임 사실이 되지는 않는다.

### 3.2 기록

1. 수락한 플레이어 입력은 짧은 원문 기록으로 남긴다. 실제 현재 신에게 전달된 대화 범위만 대상이며 일반 채팅 전체를 수집하지 않는다.
2. NPC 발언은 실패한 생성 초안이나 수정을 위해 폐기한 응답이 아니라 최종 대사·전달 결과를 기준으로 기록한다. 기존 HUD 전달 함수는 결과를 충분히 반환하지 않으므로, 구현 시 전송 수락/대체 채팅 전달을 확인할 연결이 필요하다. 실제 클라이언트에서 읽었는지까지 보장하지는 않는다.
3. 게임 결과는 확정 후 통지에서만 기록한다. 사용자 발언·Proposal 접수·확인 대기는 실행 성공으로 취급하지 않는다.
4. 중요한 부분을 추출하는 AI 작업은 별도 후처리로 실행한다. 대화 생성 JSON에 추가 기억·평가 필드를 요구하지 않는다.
5. 추출 결과는 원문에 근거가 있는지, 주체·부정·인용·시점이 맞는지 검증한다. 모호하면 사실화하지 않고 원문 후보로 남긴다. 검증으로 모델의 의미 해석 오류를 완전히 없앨 수는 없다.

추출이 아직 안 됐더라도 동일 신·플레이어의 권한이 맞는 최근 원문 후보를 제한적으로 검색할 수 있게 한다. 후처리가 끝날 때까지 재접속 기억이 완전히 비는 것을 피한다. 20개 메시지에서 밀려나기 전에 기록하기 때문에 길게 대화해도 저장 후보가 사라지지 않는다.

### 3.3 정정·망각

- “아까 농담이었어”, “이제는 수영을 배웠어”는 관련 과거 진술과 연결한다. 같은 주제라는 이유만으로 기존 모든 기억을 덮어쓰지 않는다.
- 시간에 따른 변화와 정정은 구분한다. 예전 두려움과 현재 극복을 함께 기억할 수 있다.
- 완료된 약속은 현재 미완료 목록에서 제외하되 함께 겪은 경험으로 남길 수 있다. 게임 관련 약속 완료는 게임 확인이 필요하다.
- 답변 대기 중 정정/삭제가 발생하면 revision을 바꾼다. 늦은 요약·색인 결과가 과거 기억을 다시 살릴 수 없게 한다.
- 사용자 선택은 “중요 사건·약속은 오래 유지, 사소한 잡담은 점차 잊기”다. 미완료 약속·중요 공동 경험은 단순 시간 경과나 오래 접속하지 않았다는 이유로 자동 삭제하지 않는다. 반복 잡담은 중복을 합치고 회상 우선순위를 낮춰 활성 기억에서 보관층으로 이동한다. 정확한 보존 기간과 상한은 사용량을 보고 정한다. 기억을 회상했다고 무조건 중요도를 높이지 않는다.
- 원문·활성 기억·보관 이력·백업 보존 기간은 따로 정한다. 무기한 원문 보관을 기본 전제로 삼지 않는다. 삭제 기능은 파생 요약·검색 색인까지 함께 처리하고, 이미 만들어진 백업의 잔존 정책도 명시해야 한다.

## 4. 검색과 프롬프트

```text
현재 발화 + 필요한 직전 문맥
  → 월드·신·플레이어·현재 청중으로 먼저 제한
  → 관련 후보 검색
  → 정정·게임 현재 상태·중복·최근 사용 여부 점검
  → 관련 기억 0~3개
  → 기존 LP 분류/생성 경로에 짧은 참고 문맥으로 전달
```

- 첫 버전은 외부 호출 없는 로컬 검색이다. 기존 키워드·태그 방식을 개선하고 한국어 표기 정규화, 단어 일부 일치, 명시적 대상 ID, 직전 대화의 주제를 함께 사용한다. 특정 발언의 고정 답변이나 끝말잇기 전용 기억 규칙은 만들지 않는다.
- 관련성이 먼저이고 중요도·최근성은 관련 후보 사이의 순위에만 적용한다. “응”, 인사처럼 검색 근거가 약하면 중요한 기억을 억지로 주입하지 않는다.
- 단순 키워드는 “수영을 못한다 ↔ 깊은 강이 걱정된다” 같은 의미 연결을 놓칠 수 있다. 이를 해결했다고 주장하지 않는다. 의미 검색은 별도 실험 단계로 분리한다.
- 초기 기억 예산 제안은 0~3개, 전체 400~800자 내외다. 토큰 수와 지연도 함께 측정해 조정한다. 관련 기억이 없으면 블록 자체를 생략한다.
- 현재 발화·최근 문맥과 중복되는 기억을 제외한다. 같은 기억을 연속 턴마다 꺼내지 않되, 사용자가 직접 다시 묻는 경우에는 억제하지 않는다.
- 필요한 턴에는 분류와 생성이 동일한 기억 snapshot을 본다. 분류 단계에 기억이 전혀 없으면 “그 약속 말인데”를 잘못 해석할 수 있다. 기존 직접 인사 응답은 유지하며 기억을 넣기 위해 추가 AI 호출로 바꾸지 않는다.
- 기억은 회상 참고자료일 뿐 말투 지시·행동 명령이 아니다. 플레이어가 기억에 남기려 한 프롬프트 명령도 시스템 지침으로 승격하지 않는다.
- 기록만 있고 의미를 확신할 수 없는 경우 임의로 메우지 않는다. 특히 보상·약속의 이행 여부·비밀 공개는 게임 검증 우선이다.

## 5. 누구의 기억인가

- 기본은 월드 + 신 + 플레이어 단위다. 포르투나와 한 사적인 이야기를 데메테르가 자동으로 알지 않는다.
- 당시 누가 들었는지와 지금 누구에게 공개 가능한지는 별개다. 현재 화자에게 알려진 기억이고 현재 모든 청중에게 공개 가능한 경우만 프롬프트에 넣는다. 참가자나 청중을 AI가 추정해 추가하지 않는다.
- 현재 LP adapter는 원래 게임 상호작용의 청중 정보를 충분히 보존하지 않는다. 시작 Context의 실제 청중을 memory context에 전달해야 한다. 알 수 없으면 개인 기억 주입을 생략한다. 다인 청중에서 단지 수신자별로 대화를 나눴다는 이유만으로 사적 대화라고 판단하지 않는다.
- 지식이 퍼지는 것은 별도 게임/스토리 사건으로 다룬다. 다른 플레이어·신에 대한 소문 전파를 초기 버전에서 자동 도입하지 않는다.
- 현재 Story Snapshot에는 공개를 통과한 문장과 일회성 별칭만 들어간다. 숨은 Fact ID를 기억에 노출하거나 별칭/token을 영구 저장하지 않는다. 스토리 장기 회상에는 재검증 가능한 게임 소유의 불투명 참조 계약이 필요하며, 이것이 없으면 초기 기억 대상에서 제외한다.
- 서버 전체 사건이라고 모든 NPC가 안다고 가정하지 않는다. 레이드 등 아직 미확정 콘텐츠는 향후 게임이 제공하는 관찰·공개 계약이 마련된 뒤 연결한다.

## 6. 속도·저장 안정성

### 응답 중

- 기본 경로에서 기억 추출·임베딩·품질 평가용 추가 모델 호출을 하지 않는다. LP 기존 호출/재시도 정책도 이 설계에서 확대하지 않는다.
- 준비된 로컬 인덱스와 불변 snapshot으로 조회한다. 서버 tick에서 전체 저장소를 읽거나 검색 완료를 기다리지 않는다.
- 검색이 준비되지 않았거나 시간 예산을 넘으면 기억 없이 LP로 진행한다. 예산은 초기 목표 10~20ms 수준으로 두되 실제 측정 후 정하며 보장치로 안내하지 않는다.
- 입력 토큰이 늘어나므로 검색이 빨라도 모델 처리 시간은 증가할 수 있다. 기억이 답변을 길게 유도하는 영향도 따로 측정한다.

### 후처리

- 원문 저장은 제한된 단일 쓰기 큐·순차 journal과 주기적 snapshot을 사용한다. 작은 서버 규모에서는 별도 벡터 DB 서비스부터 도입할 필요가 없다.
- 임시 파일·원자적 교체·백업 snapshot·스키마 검증으로 손상 시 원본을 보존한다. 비정상 종료 시 마지막 미기록분 손실 가능성은 명시하며 저장 실패를 조용히 성공 처리하지 않는다.
- 정상 종료 시 쓰기 큐를 제한 시간 내 비우고, 재시작 시 처리한 원본 ID/sequence 이후부터 후처리를 재개한다. 같은 사건·턴을 중복 기록하지 않는다.
- 초기 자동 요약은 접속자가 없고 모델을 사용하는 다른 작업도 없을 때만 작은 묶음으로 처리하는 보수적인 정책을 제안한다. 접속자가 계속 있다면 후처리가 밀릴 수 있어 원문 검색을 fallback으로 유지한다. 큐·디스크 상한과 보관 정책이 필요하다.
- 현재 `LocalOllamaClient`별 scheduler는 전 서버의 모델 작업을 통합 관리하지 않는다. 단순히 비동기 thread를 추가하는 것으로 대화 우선순위가 보장되지는 않는다. 구현 시 대화·자발적 대사·건축 시각 평가를 포함한 사용 여부를 확인하는 공통 admission 경계가 필요하다.
- 이미 진행 중인 모델 계산을 즉시 중단·선점할 수 있다고 가정하지 않는다. 새 대화 시작 시 신규 후처리 투입은 막되, 이미 시작한 작업의 경합 시간은 측정해야 한다. 경쟁이 크면 자동 후처리를 꺼서 수동 관리 시간에만 처리한다.

### 최대 6명 동시 대화

- 대화 세션 6개를 지원하는 것과 모델 추론 6개를 동시에 돌리는 것은 다르다. 실제 동시 추론 수는 기존 설정과 장비에서 측정한 처리량을 기준으로 정한다. 플레이어 수만 보고 GPU 동시 추론을 6개로 늘리지 않는다.
- 플레이어별 순서와 세션당 진행 중 요청 제한을 유지한다. 공통 모델 사용 경계에서는 foreground 대화가 background 기억 추출·색인보다 우선한다. 한 플레이어의 다량 요청이나 후처리가 다른 플레이어를 계속 밀어내지 않도록 제한한다.
- 기본 후처리는 접속자 0명일 때 수행한다. 접속이 장시간 유지돼 원문 후보가 쌓일 경우에만, 모든 foreground 요청/대기열이 비고 전체 사용자가 충분히 입력하지 않은 유휴 구간에 작은 후처리 1건을 허용하는 선택 모드를 검토한다. 초기 유휴 기준 후보는 60초이며 성능 검증 전에는 기본 활성화하지 않는다.
- 후처리는 한 신·플레이어의 짧은 원문 묶음씩 처리하고 실패 재시도와 시간 상한을 둔다. 처리하지 못한 묶음은 재접속·재시작 후 이어서 처리한다. 오래 열린 세션만으로 후처리를 영구 금지하지 않는 유휴 모드는 별도 검증한다.
- 모든 사용자가 동시에 대화할 때는 준비된 기억만 조회하고 새 요약·벡터 계산은 시작하지 않는다. 이미 실행 중이던 후처리의 잔여 경합은 완전 제거를 약속하지 않는다.
- 비교 검증은 1명·4명·6명 조건으로 나눈다. 총 처리량만이 아니라 플레이어별 응답 대기, 최장 대기, 순서 뒤섞임, 다른 사람 기억 혼입을 확인한다. 동시 사용자 증가로 생기는 기본 모델 대기와 새 기억 기능이 추가한 지연을 구분한다.

### 의미 검색의 위치

키워드 기반 버전의 실패 사례가 쌓인 뒤 선택적으로 추가한다. 기억 벡터의 사전 계산만으로 현재 발화의 벡터 생성 비용까지 없어지는 것은 아니다. 동일 GPU의 모델 교체·메모리 사용·대기 시간을 따로 검증한다. 초기에는 의미 검색을 대화에 쓰지 않고 검색 품질만 비교하며, 효과가 확인돼도 시간 예산을 넘으면 키워드 결과로 진행한다. 새 모델 설치는 별도 승인을 받는다.

## 7. 구현 범위와 순서 제안

### 1단계: LP + 기본 장기 회상

AI 응답 모듈에 독립적인 memory 패키지·설정·저장 경로를 추가한다. 기존 legacy 클래스는 통째로 되살리지 않는다. 저장, 로컬 검색, 원문 근거, 정정·삭제, 개인/청중 격리, 비동기 쓰기부터 연결한다. 기존 프로필·모델·출력 토큰·JSON schema·감정/품질 분석은 바꾸지 않는다.

연결점은 운영 adapter의 입력 수락/최종 대사/세션 종료, `MythAiConversationEngine`의 시작·종료와 청중 전달이다. 생성 코드만 수정하지 않고 `build.gradle`의 실제 오버레이 입력 또는 정상 Java helper를 수정한다. 미완료 약속 추출을 규칙만으로 완성했다고 하지 않는다. 자동 요약은 별도 스위치로 검증 후 켠다.

### 2단계: 함께 겪은 게임 경험

현재 존재하는 `AiQuestCompletionContext`, `AiQuestEvaluationContext`를 우선 활용한다. 완료·평가 발언 실패와 무관하게 게임 확정 이벤트를 기록하되 해당 신의 인지 가능 범위를 확인한다. 현재 DTO에는 영구적인 발생 ID가 없으므로 반복 가능한 사건의 정확한 중복 방지가 필요하면 게임에서 확정 event receipt를 제공하도록 최소 계약을 확장한다. 관련 생산자·소비자·테스트를 함께 수정한다.

일반 액션은 `AiActionGateway.submit` 반환을 무조건 실행 완료로 저장하지 않는다. UI 확인 후 실제 실행 결과·거절 결과를 받을 수 있는 기존 계약을 먼저 확인한다. 스토리 회상·다인 대화·신 간 정보 전파는 권한 계약을 갖춘 별도 후속 단계다.

### 3단계: 의미 검색 선택 실험

1·2단계에서 실제 놓친 회상 사례를 기준으로 효과와 지연을 비교한다. 필요하지 않으면 이 단계는 도입하지 않는다.

## 8. 비교 검증과 되돌리기

동일 프로필·모델·설정으로 `LP`, `기억 코드 포함 + 기능 OFF`, `기억 기능 ON`을 비교한다. 기능 OFF일 때 추가 프롬프트·외부 호출·저장 부작용이 없어야 한다. 실험 JAR은 LP 백업을 덮지 않는다. 기능 스위치 OFF는 논리적 비활성화이며 완전한 바이너리 복원과 다르다.

검증 사례:

- 재접속 후 개인적 취향·미완료 약속을 회상하되 다른 화제에서는 끼어들지 않는가.
- 신/플레이어/월드/청중이 다르면 사적 기억이 전달되지 않는가.
- 거짓말·농담·인용·가정이 세계 사실이 되지 않는가.
- 사과·정정·약속 이행 이후 오래된 상태를 현재처럼 반복하지 않는가.
- 늦은 응답·추출, 재시작, 삭제, 파일 손상, 꽉 찬 큐에서 안전하게 동작하는가.
- 완료/보상 이벤트를 기억한 것이 실제 행동을 재실행하거나 중복 보상으로 이어지지 않는가.
- 여러 플레이어가 동시에 대화해도 세션 문맥과 기억 snapshot이 섞이지 않는가.

측정은 검색·큐 대기·분류·생성·재시도·후처리를 나눠 기록하고, 사용자 입력부터 표시까지 전체 지연의 중앙값과 느린 구간(p95)을 함께 비교한다. 캐시 상태·입출력 토큰·후처리 동시 실행·호출 순서를 기록하고 몇 번의 단일 대화로 속도 개선을 단정하지 않는다. 말투 유지·회상 정확도·불필요한 회상률을 사람이 LP와 나란히 평가한다.

제안 수용 기준은 사적 기억 유출/게임 권한 침범 0건, 기능 OFF 경로의 LP 동일성, 기억 없는 턴의 추가 모델 호출 0회다. 속도 허용치와 자연스러움 평가는 사용자 확인 후 정한다. 미흡하면 배포하지 않는다.

새 기억은 `server/<world>/mythictrpg-ai-memory-lp/` 같은 별도 경로를 사용한다(가칭). 기존 `memories.json`과 실험 `memories-v2.json`은 출처/권한을 확인하기 전 자동 이관하지 않는다. 롤백 시 새 기억을 LP가 읽지 않도록 분리하고, 서버·설정·실험 소스를 따로 백업한다. 첫 구현 전 현재 소스 및 필요한 게임 계약 파일을 추가 보존한다.

## 9. 사용자 확인 결과와 남은 조정 항목

확인된 선택:

- 중요한 사건·약속은 오래 기억하고 사소한 잡담은 점차 잊는다.
- 평소 4~5명, 최대 6명 접속. 전원이 동시에 AI 대화할 수 있다.
- 동시 사용자 증가에 따른 대기는 사용자들이 인지하고 있다. 이것을 불필요한 추가 추론이나 긴 후처리 대기의 허용으로 해석하지 않는다.

초기 방향을 막는 추가 질문은 없다. 구체적인 원문/보관 이력 보존 기간·자원 예산·속도 수용 기준은 구현·측정 계획에서 명시하며, 의미 검색이나 새 모델은 별도 승인 후 검토한다. 이 문서의 설계는 구현 승인을 대신하지 않는다.

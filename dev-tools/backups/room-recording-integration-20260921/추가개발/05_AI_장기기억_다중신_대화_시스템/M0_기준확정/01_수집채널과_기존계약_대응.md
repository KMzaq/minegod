# M0-01. 수집 채널과 기존 계약 대응

2026-09-20 / 읽기 전용 소스·배포 JAR 조사 / 아래 hook는 **구현 예정**이다. 신규 Java 포트와 필드의 단일 정의는 [공통 계약 7절](../02_공통계약과_데이터모델.md)이다.

## 1. 확인한 실제 입력·출력 경로

게임 [AiConversationRuntimeService](../../../mythictrpg-main/src/main/java/com/sande/mythictrpg/ai/server/AiConversationRuntimeService.java)의 `onServerChat`는 퀘스트 동의 응답을 먼저 처리하거나 게임 대화 엔진에 전달한 뒤 공개 채팅을 취소한다. AI의 [AiTestChatEvents](../../../mythai-ai-response/src/main/java/com/sande/mythai/response/AiTestChatEvents.java)도 활성 세션의 채팅을 취소하고 adapter에 넘긴다. `!` 접두사는 신 대화에서 빠져나오는 공개 경로이며 AI listener가 표시 메시지에서 `!`를 제거한다.

두 listener 등록 순서나 `event.isCanceled()`만으로 수락/거부/실제 수신을 판정하면 안 된다. 비공개 대화로 수락돼서 공개 이벤트가 취소된 경우도 있다. 기록을 위해 기존 채팅 라우팅 우선순위를 임의로 바꾸지 않는다.

생성된 `AiTestDialogueAdapter.handlePlayerText`는 session/빈 입력/생성 중 여부를 확인한 뒤 `sharePlayerLine → turn 증가 → DialogueMemoryBridge.beginAsync → history/log`로 간다. 입력은 현재 `maxPromptCharacters`로 먼저 제한된다. 새 수집은 **수락 판정 직후, 프롬프트용 절단 전** 원문을 동결하고, 실제 공유/엔진 투영이 다르면 별도 delivery view로 남긴다. 이미 거부된 연속 입력을 대화 사실로 기록하지 않는다.

출력은 중앙 `showDialogue`가 참가자별 `showDialogueOnly`를 호출한다. 후자는 문장/길이 단위 HUD 페이지를 보내고 실패하면 채팅으로 대체한다. 현재 `DialoguePresentationService.sendTo`는 **수신자·페이지마다 새 message UUID**를 만든다. 이것은 전송 ID이며 새 archive의 논리 발언 `messageId`로 그대로 사용할 수 없다.

## 2. 채널별 M2 연결점과 완료 기준

| 채널 | 발생·수락 지점 / receipt 지점 | 분류·중복 방지 / 필수 fixture |
|---|---|---|
| 플레이어→신 | adapter의 실제 수락; 공유 대화 전송·게임 청취 판정 | 세션 없는 입력·pending 거부 제외. 같은 문장 재발화는 별도 occurrence. 원문과 제한된 엔진 투영 구분 |
| 신→플레이어, 공유 HUD | 중앙 `showDialogue` 한 번; `showDialogueOnly`의 페이지별 HUD 성공 또는 채팅 대체 성공 | 발언1건, 수신자별 receipt. HUD 실패+대체 성공을 대사2건으로 만들지 않음. 일부 페이지만 성공하면 PARTIAL |
| 퀘스트 동의 | `QuestParticipationService.handleAnswer`의 처리 수락; 실제 동의 요청 안내 전송 | 자연어 예/아니오는 대화 기록. 명령 경로는 승인된 선택 내용만 연결하고 전체 명령 문자열은 저장하지 않음. 동의/소비/보상 재실행 금지 |
| 일반 공개 채팅·`!` | 최종 `PlayerList.broadcastChatMessage`에 도달한 `PlayerChatMessage`; 실제 recipient send | 원입력·최종 장식/view를 구분. 취소/차단/필터/채팅 숨김은 정상 receipt가 아님. 공개라고 모든 신에게 KnowledgeReceipt 발급 금지 |
| `/msg`, `/tell`, `/w` | `MsgCommand.sendMessage`의 해석 완료 본문; 발신 echo/수신 대상별 실제 send | 비공개. 대상 여러 명이어도 논리 원문1건, 발신 echo를 복제 대화로 만들지 않음. 명령 권한 실패·대상 없음 제외 |
| `/teammsg`, `/tm` | `TeamMsgCommand.sendMessage`; scoreboard team의 실제 수신자 | 바닐라 scoreboard 팀이며 FTB 팀과 다름. 팀 미가입·온라인 여부·개별 필터 fixture |
| `/say`, `/me` | 각 명령의 해석 완료 대화가 `broadcastChatMessage`로 합류 | 플레이어 발화만 PLAYER로 저장. 콘솔/명령 블록을 플레이어로 위장하지 않음. 시스템 운영 메시지는 제외 |
| FTB Teams 팀 채팅 | `SendMessageMessage`의 서버측 team 확인 → `AbstractTeam.sendMessage(UUID, Component)`; 온라인 멤버별 실제 전송 | GUI/채팅 전환/명령 진입을 같은 발생으로 연결. 채팅 표시+팀 UI packet은 같은 수신 view의 전송 surface이지 별도 발화가 아님 |
| 작성형 신·스토리 대사 | 게임 생산자가 선언한 논리 대사; `DialoguePresentationService`와 `StoryPresentationService`의 실제 HUD/채팅 출력 | 고정 대사도 포함. AI 중앙 wrapper가 이미 capture한 출력은 하위 hook에서 재생산 금지. 퀘스트/스토리 진행 자체를 대화로 실행하지 않음 |
| 향후 신→신/새 대화 UI | 게임의 발언 계획·청취 판정 → 동일 capture adapter | M6 이후. 현재 존재하지 않는 청취 신을 관측했다고 기록하지 않음 |
| 기타/새 외부 모드 채널 | 등록된 producer adapter가 필요 | 현재 알려진 외부 채널은 FTB Teams. 알 수 없는 채널은 UNREGISTERED/coverage 미확인, 전체 지원으로 표시 금지 |

관리자 상태·성공/실패 진단·아이템/보상 알림·인증 명령·프롬프트·미출력 모델 초안은 대화 RAW가 아니다. `sendSystemMessage` 전부를 무차별 수집하지 않고 위 생산자가 표시한 대화만 연결한다. 잘못된 채널 식별은 UNKNOWN으로 격리하고 NPC 검색/소문에는 내보내지 않는다.

### 바닐라·FTB 확인 근거와 구현 선택

- 게임 개발 입력의 `build/moddev/artifacts/neoforge-21.1.248-sources.jar`에서 Minecraft 1.21.1의 위 명령, `PlayerList`, `ServerPlayer`, `OutgoingChatMessage`를 확인했다. `ServerPlayer.sendChatMessage`는 채팅 허용 여부를 확인하며 `OutgoingChatMessage.Player.sendToPlayer`는 필터 후 전부 가려진 메시지를 보내지 않는다. 단순 브로드캐스트 대상 목록은 실제 전송 목록이 아니다.
- 설치된 `server/mods/ftb-teams-neoforge-2101.1.11.jar`를 `javap`로 읽었다. `SendMessageMessage`는 서버 팀 확인 후 `Team.sendMessage`로 연결되고 `AbstractTeam`은 온라인 멤버에게 채팅과 `SendMessageResponseMessage`를 보낸다. `FTBTeams.chatReceived` 및 채팅 전환 경로도 있다. 다른 버전의 소스만으로 지원 여부를 추측하지 않았다.
- M2는 게임 소유 `ConversationCaptureAdapter`를 중심으로, 게임/AI 자가 코드는 명시 호출을 추가한다. 바닐라와 설치된 FTB Teams는 별도 **선택적 capture Mixin adapter**로 발생 scope와 실제 send를 연결한다. 필터·취소 후 실제 send 경로를 확인해야 하며 Mixin 적용 성공은 컴파일만으로 인정하지 않는다.
- FTB Teams version/대상 signature 불일치 시 해당 adapter를 비활성화하고 coverage 경고를 표시한다. 기존 행동 수집의 필수 Mixin 설정에 무관한 optional hook를 끼워 서버 전체를 실패시키지 않는다. Mixin 호환성·타 모드 라우팅의 실제 수용은 M2/M7에 남긴다.
- FTB UI가 나중에 과거 팀 기록을 동기화하는 것은 새 발화가 아니다. 신규 dataset 이후의 이미 매핑된 message에만 별도 역사 전달 receipt를 연결한다. 예전 FTB 기록을 초기 동기화했다고 새 RAW로 자동 수입하지 않는다. 팀 관리용 자동 알림은 player-authored scope가 없으면 대화에서 제외한다.

## 3. 중복 방지와 기존 후처리 보존

생산자는 `(producerId, runtimeEpoch, acceptanceCounter)` 또는 해당 게임 사건의 stable ID로 occurrenceKey를 발급한다. 재시도는 같은 키, 실제 새 발화는 다른 키다. text hash는 충돌 검증용이며 중복 발생의 식별자가 아니다. turn이 없는 공개 채팅은 message 자체의 occurrenceKey를 쓴다.

AI 입력의 새 archive capture는 기존 `DialogueMemoryBridge.beginAsync`를 다시 호출하지 않는다. 현재 이 함수는 `SocialRuntime.playerTurn`도 호출한다. NPC 출력의 `DialogueMemoryBridge.delivered`는 **수신자별**, `SocialRuntime.delivered`는 **중앙 한 번**이다. 새 RAW 수집이 각 legacy 후처리를 재호출해서 소문·평가를 배수로 만들면 안 된다. legacy→v2 검색 전환 전까지 기존 의미를 보존하고 M5에서 명시적 mode별 경로를 선택한다.

`sharePlayerLine` / `seedNpcTurn`의 listener history 복제는 새 원문 생산자가 아니다. 게임 발급 논리 messageId를 하위 전달 함수까지 운반한다. 기존 HUD messageId는 전송 참조로만 연결한다. receipt에는 전송 surface, viewHash, partIndex, audienceRevision을 보존한다.

AI 구현 위치는 [build.gradle](../../../mythai-ai-response/build.gradle), [memory overlay](../../../mythai-ai-response/memory-foundation-overlay.gradle), [quest overlay](../../../mythai-ai-response/quest-participation-overlay.gradle)다. `build/generated`는 결과 확인용일 뿐 수정 원본이 아니다. `mine/mine` legacy 의존성을 이 작업에서 전면 분리하지 않는다.

## 4. v1 → v2 source/현재성 대응

| 기존 source / owner | stable identity·revision 대응 | 새 사용 조건·재검증 |
|---|---|---|
| `ConversationMemoryContext` / 게임 | worldId→그대로, interactionId→conversationId, player별 generation→sessionGeneration, audience UUID→PLAYER ActorRef | 기존 generation은 참가자 공통 값이 아님. 게임 발급 membershipRevision과 참가자별 generation을 함께 유지. turn/epoch/dataset은 새로 발급 |
| `PreparedMemoryContext` / 게임 | 게임이 승인한 plan/requestId 기반 사전 조회 | 실제 대화 시작·수신 증거·action scope가 아님. 시작 후 새 capability로 재검증 |
| `ActionRecord` / 게임 원장 | worldId + occurrenceId + sourceRef + sourceRevision(현재1); 원장 sequence는 소비 cursor | 상세 원문은 ADMIN_ONLY. AI는 원장 파일이나 전체 레코드를 조회하지 않고 승인된 관찰 투영만 받음 |
| `ExperienceLease` / 게임 watch | observationId + eventId + sourceRevision, 기존 watch proof 및 정책 revision | `ExperienceAccess`의 현재 context/관계/포함 proof 검증 보존. 최종 출력 직전 게임 스레드에서 `lease.current(included)` 확인 |
| `ExperienceView.Event` / 게임 투영 | DIRECT_WATCH, 현재 작물/전투/관찰 활동 요약만 지원, 최대16건/응답 | 상세 원장에 퀘스트/발전 과제가 있다는 이유로 v1 DTO에 없는 source를 주입하지 않음. 새 kind는 M3의 명시 adapter+검증으로 추가 |
| `RumorLedger.HeardRumor` / 게임 | subjectPlayer + rootId + revision + 수신 god/receipt + assessmentVersion | `RumorSavedData.heard`와 `ReputationService.decorate`가 승인한 내용만 사용. source/proof/철회/현재 수신·공개 권한 재검증 |
| `ReputationLedger` / 게임 | decision world/god/subject/root/rumorRevision + 평가 version | 파생 기억은 현재 해석을 참조할 뿐 별도 평판/affinity 원본을 만들지 않음. 회복 뒤 이전 비난 계보 무효화 |
| 현재 관계·Quest/Reward·월드 사실 / 게임 Provider | scope와 실제 제공 revision/fingerprint | 원본 revision이 없으면 있다고 꾸미지 않음. snapshot hash+게임 현재값 대조로 보수적으로 STALE 처리 |
| 전달된 AI 대사 / 게임 승인 출력 | messageId + 실제 수신 receipt + usedSources | DERIVED_SPEECH. 같은 내용을 재인용했다고 독립 증거 수가 증가하지 않음 |
| v1 개인 journal/Derived/Index / AI | 옛 test source | 새 dataset의 source adapter로 등록하지 않음. backend/알고리즘 재사용과 데이터 수입은 별개 |

기존 소문 공개 청중은 `Set<UUID>` 플레이어 전용이다. M6의 다른 신에게 공유할 때 이것만 통과해서는 안 된다. v2 ActorRef 청중과 신별 공개 정책을 게임이 승인하기 전에는 기본 차단한다. 기존 source에 없는 명시적 revision은 adapter가 원문을 덮어쓰지 않고 별도 상태 version으로 관리한다.

## 5. M2/M3에 넘기는 필수 시험 명세

1. 같은 문장2회→RAW2건; 동일 occurrence 재시도→1건; 같은 키·다른 hash→CONFLICT. 참가자4명/HUD3페이지→논리1건, 수신4명과 부분 상태가 정확해야 한다.
2. 생성 중 입력 거부, 공개 채팅 취소, `!`, 퀘스트 동의, FTB 채팅 전환의 조합. 실제 수락 채널만 저장하며 이벤트 listener 순서에 의존한 이중 수락을 탐지한다.
3. 귓속말 echo/다중 대상, scoreboard team/FTB team 불일치, 전부/일부 필터, 숨김·오프라인 수신자, 전송 도중 이탈. 발송과 화면 열람을 혼동하지 않는다.
4. 프롬프트 제한 초과 입력·1200자 초과 대사·공백/개행·한글/보충 평면 문자의 원문 hash 보존. archive가 볼 수 있는 원문과 NPC가 받은 projection은 별도 검증한다.
5. 관찰 이전 행동 비소급, 비밀/차폐·미수신 신, 소문 철회·회복·전서구 epoch, 재시작·새 발언·합류·역할 전환 직전 취소. 늦은 검색/생성/평가 결과는 폐기한다.
6. legacy 후처리 호출 수 회귀: 입력1회, 중앙 social 출력1회, 실제 수신자별 기존 memory 통지. archive 재생으로 보상/소문/대사를 재실행하지 않는다.

위 항목은 **시험 명세이지 실행 결과가 아니다.** 현재 source 추적으로 연결 위치를 확정했으며 실제 hook와 채널 coverage 검증은 미구현이다.

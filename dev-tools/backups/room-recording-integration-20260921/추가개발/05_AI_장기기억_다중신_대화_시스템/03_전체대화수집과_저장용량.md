# 03. 전체 대화 수집과 저장·용량

## 1. 무엇을 전체 기록하는가

| 입력 경로 | 기록 기준 | 신에게 자동 공개되는가 |
|---|---|---|
| 플레이어↔신, 신↔신의 게임 대화 | 서버가 수락한 입력과 실제 전달한 출력 각각 | 아니오. 실제 청취/참여와 공개 정책 필요 |
| 다중 플레이어 공유 대화 | 발화 한 건 + 수신자별 receipt. HUD 복제는 별도 발화 아님 | 참가 신이 실제 들은 범위만 |
| 일반 공개 채팅 | 최종 수락/라우팅 지점의 본문·발화자·실제 수신 범위 | 공개 채팅이라고 모든 신이 현장에 있었다고 보지 않음 |
| 귓속말·팀 채팅·명령 기반 대화 | 서버가 확인한 최종 메시지와 수신자. 해당 채널 adapter 필요 | 실제 수신자 외 기본 불허 |
| 작성형 NPC/퀘스트/스토리 대사 | 실제 전달된 대사와 원본 사건 참조 | 게임의 전달·지식 공개 계약에 따름 |
| 실패/취소된 모델 생성, 미출력 초안 | 원문 대화가 아님. 내용 없는 실패 상태만 진단 | 아니오 |
| 콘솔·시스템 프롬프트·추론·인증 명령·비밀번호 | 대화 원문 수집 대상 아님 | 아니오 |

수집 범위의 “전체”는 **서버가 실제 처리하는 지원 대화 채널 전체**다. 클라이언트 내부/알 수 없는 외부 모드 채팅을 읽었다고 주장하지 않는다. 채널 목록, adapter 유무, 수집 성공/누락을 관리자 상태에 표시한다. 미지원 경로는 M2의 미완료로 남긴다.

예를 들어 `/msg`라면 최종 전달된 본문을 수집하며 명령 문자열 전체를 무차별 저장하지 않는다. 취소된 전송은 대화 사실이 아니고, 플레이어 입력이 수락됐지만 모델이 실패한 경우 그 입력과 실패 상태는 남긴다.

현재 신 대화 방식은 고정하지 않는다. `ConversationCaptureAdapter`가 새 UI·라우팅의 실제 수락/전달 통지를 같은 계약으로 바꾼다. 미확정 청중은 `UNKNOWN_AUDIENCE`로 보관하되 신의 기억·소문 생성에는 사용하지 않는다.

## 2. 원문과 전달을 한 번씩 기록

1. 생산자가 발생 시점에 stable occurrence key를 만든다. 같은 문장이라는 이유로 중복 제거하지 않는다.
2. 게임이 본문과 현재 채널/청중/정책을 동결하여 bounded queue에 넣는다.
3. 단일 writer가 message·receipt·후속 work item을 transaction으로 저장한다.
4. durable 성공 뒤만 저장 cursor와 영속 기억 처리 cursor를 전진시킨다.
5. 비동기 대사는 게임의 최종 승인/전달 이후 별도 message로 기록한다. 입력과 출력의 durable 시점은 다르다.

RAW 본문에 기존 개인 journal의 `bounded(text,1200)`을 적용하지 않는다. 이미 수락/전달된 긴 대사는 순서를 보존해 chunk로 저장하고 전체 hash를 검증한다. 표시용 Component와 실제 plain text의 차이도 명시한다. 검색/프롬프트 발췌 한도는 원문 보관 한도와 분리한다.

게임 출력과 디스크 커밋은 단일 transaction이 아니다. 출력 직후 프로세스가 죽으면 기록 공백이 생길 수 있다. 저장 때문에 매 대화를 디스크 flush까지 게임 thread에서 기다리지는 않는다. 비정상 종료 시 마지막 durable cursor 이후 구간을 `POSSIBLE_GAP`으로 표시하고 임의로 복원하지 않는다.

일부 수신자에게만 전송됐다면 그 receipt만 남긴다. 취소된 늦은 응답은 대화로 기록하지 않는다. 서버 전송 성공과 실제 화면 열람/인지 여부를 혼동하지 않는다.

## 3. 저장 위치·방식

제안 위치는 `<world>/mythictrpg-recording-v2/<datasetId>/recording.sqlite`다. 이 경로는 아직 생성하지 않았다. worldId는 게임 발급값을 검증하고 운영 dataset 선택은 월드 manifest에서 고정한다.

- SQLite + `sqlite-jdbc`, WAL, 단일 쓰기 connection, 제한된 읽기 pool.
- 원문 transaction은 `synchronous=FULL`을 시작값으로 한다. 게임 thread가 아닌 writer에서 수행한다. 실제 파일시스템/장애 시험 없이 전원 장애 완전 무손실을 보장하지 않는다.
- 짧은 transaction과 페이지 조회. 100GB 원문·모든 벡터를 JVM 메모리에 올리는 구조 금지.
- 원문 메타/지연 처리 작업은 같은 DB transaction에 넣는다. 기존 게임 원장과의 연동은 receipt + cursor 방식이며 DB 간 원자성을 주장하지 않는다.
- FTS/벡터/요약은 source hash/version으로 재구축할 수 있게 한다. 원문·관찰 근거의 대체 원본으로 쓰지 않는다.

WAL은 같은 호스트의 로컬 저장을 전제로 하고 동시에 하나의 writer만 허용한다. 긴 읽기가 checkpoint를 지연할 수 있으므로 read deadline과 WAL 감시가 필요하다. [SQLite WAL 문서](https://sqlite.org/wal.html).

M0에서 `sqlite-jdbc:3.53.4.0` 기본 JAR과 게임 단일 패키징을 선정했다. 라이선스·확보 계획은 [M0 패키징](M0_기준확정/03_SQLite_패키징과_M1_착수기준.md)을 따른다. 실제 Java21/NeoForge native 로드·FTS5는 아직 미검증이다. SQLite 공식 WAL-reset 수정이 포함된 런타임인지 M1에서 재확인한다. “최신”이라는 가변 지정은 금지한다. [공식 수정 안내 11절](https://sqlite.org/wal.html), [sqlite-jdbc 저장소](https://github.com/xerial/sqlite-jdbc).

JDBC/native 리소스는 게임 모드 한 곳에서만 패키징한다. AI는 공개 저장 포트만 사용한다. 정상 dedicated server·클라이언트 로딩·두 모듈 조합과 라이선스 고지 검사를 M1에 포함한다. 이번 설계에서 다운로드/설치하지 않는다.

## 4. 100GB 합산 상한의 정확한 의미

`worldRecordingLimitBytes = 100000000000` (100GB, 약 93.13GiB). 플레이어/신/각 DB마다 각각 100GB가 아니다.

| 합산에 포함 | 제외하되 별도 디스크 잔량 감시 |
|---|---|
| 활성 신규 dataset의 DB, WAL, SHM, 파일 내 빈 page | Minecraft 지형/region, 일반 playerdata·통계, 실제 퀘스트/보상·관계 원본 |
| FTS·벡터·파생 기억·요약·작업/근거 메타데이터 | 모드 JAR·모델 파일·일반 서버 로그 |
| 현재 사용하는 행동 원장·주시 증명 전용 파일 | 읽기 제외된 기존 시험 기억·시험 로그·LP 보존본 |
| 소문/평판의 전용 기록 파일 | 승인해 별도 위치로 내보낸 비활성 백업/아카이브 |
| 이 기록 시스템의 staging·checkpoint 임시본·같은 관리 영역 안의 복사본 | 실제 게임 상태가 같은 SavedData에 있는 주시 획득/보상 claim 등 |

전용 파일 목록과 소유자는 `ManagedStoreRegistry`로 명시한다. 혼합 파일이면 전체 파일을 안전하게 산입하거나 게임 원본으로 제외함을 manifest에 명시하며 일부 바이트를 추정하지 않는다. 실제 목록은 [M0 관리 저장소](M0_기준확정/02_관리저장소와_기존제한.md)에서 고정했다. 다른 폴더에 분산돼 있어도 같은 월드의 활성 기록은 합산한다.

SQLite로 행동 원본을 옮기거나 기존 게임 상태 저장을 용량 제한 때문에 중단시키지 않는다. 원장/증명/소문 등 **기록 생산**에만 quota 예약을 연결한다. 용량 문제 때문에 실제 보상·진행도 저장이 실패하도록 만들면 안 된다. 참조하는 시험 이후 원장이 active라면 quota에서도 임의 제외하지 않는다.

측정은 `usedPhysicalBytes + outstandingReservations + requiredMaintenanceHeadroom`으로 한다. 큐에 수락만 된 자료도 최대 쓰기/임시 증가량을 예약한다. 실제 기록 후 차액 반환. 단순 본문 UTF-8 길이 합산은 DB page/FTS/WAL 증가를 반영하지 못하므로 금지한다.

기존 경로의 독립 maxStorageBytes를 전부 100GB로 올리면 합산 제한을 지킬 수 없다. 신규 dataset은 통합 예산을 사용한다. 기존 소문 4096개 같은 별도 자료구조 안전 한도는 자동 해제하지 않고 별도 상태로 노출한다. **100GB 설정이 모든 기존 항목 수 제한 제거를 의미하지는 않는다.** 신규 RAW에는 12,000건/신별 2,000건 같은 영속 총건수 제한을 두지 않는다.

## 5. 꽉 찼을 때의 기본 정책

| 상태 | 동작 |
|---|---|
| 90% 이상 | 기존 요구대로 서버 알림·관리자 안내. 내용 없는 사용량만 표시, 동일 경고 30분 억제 |
| 95% 이상 | 새 임베딩 backfill/대형 요약 재작성 보류. 원문 우선. 이미 저장한 자료는 보존 |
| 유지보수 여유 침범 예상 | 기본 1GB의 내부 여유를 남기도록 신규 수집 admission 중단. 상태/철회/안전 종료를 우선 |
| 새 쓰기가 hard cap 초과 예상 | FULL. 기존 원문 자동 삭제·덮어쓰기 없음. 게임 진행/대화는 계속하되 저장 누락 경고 |
| OS 디스크 부족·읽기/쓰기 오류 | 100GB 미만이어도 DEGRADED/UNAVAILABLE. 조용히 다른 월드·임시 무제한 파일로 우회하지 않음 |

1GB는 100GB 안의 유지보수 여유이지 추가 할당이 아니다. transaction별 최대 성장량·WAL·임시본을 예약하고, 안전한 최대 증가량을 산정할 수 없으면 쓰지 않는다. checkpoint/읽기 지연으로 여유를 침범하면 writer admission부터 닫는다. 최악 증가량 검증은 M1 통과 조건이다.

`PRAGMA max_page_count`만으로 WAL·다른 파일을 포함한 총량이 제한되지는 않는다. DB page 상한은 보조 방어이며 예산 예약/파일 감시가 필요하다. 외부 프로그램이 관리 파일을 임의 증대시킨 경우 앱이 OS 수준 hard quota를 강제한다고 주장하지 않는다. 발견 즉시 신규 쓰기를 중단하고 관리자에게 알린다.

누락은 한 건씩 무한 로그로 쌓지 않고 사유·stream·범위별 bounded gap으로 합친다. 예비 메타 공간도 쓸 수 없으면 RAM 경고와 정상 종료 marker 부재로 복구 시 공백 가능성을 표시한다. 원문이 없는데 “전체 기록 성공”이라고 표시하지 않는다.

운영자의 승인 없는 원문 삭제/오래된 로그 압축 삭제/FIFO 덮어쓰기/외부 전송은 없다. 여유 확보는 관리자 승인 후 별도 아카이브·용량 정책 변경으로 처리한다. 백업이 다른 위치에 있다는 이유로 자동 원본 삭제를 허용하지 않는다.

## 6. 기간·검색·보존

`retentionDays`는 새 schema에서 사용하지 않는다. 기존 30일 조건은 신규 source의 유효성 필터에서 제거한다. 최근성 가중치는 허용하지만 오래됐다는 이유만으로 검색 대상에서 완전히 제외하지 않는다. 약속 날짜나 실제 게임 정책상 소문 전달 유효기간은 **자료 보관 기간**과 다른 개념이다.

취소/철회/회복된 소문도 원본 이력은 보존할 수 있으나 현재 믿음/공개 자료로 재사용하지 않는다. 보관 무기한을 권한 무기한으로 해석하지 않는다.

## 7. 백업·복구

실행 중 SQLite 본체만 복사하지 않는다. 온라인 백업 API 또는 정상 정지 후 일관된 복사 절차를 사용한다. [SQLite Backup API](https://sqlite.org/backup.html). 게임 원장·SavedData와의 일관성은 추가 조정이 필요하므로 초기 운영 권장은 정상 저장·정지 후 월드와 기록을 함께 백업하는 것이다.

복원 때 world/dataset/source cursor·근거 해시를 대조한다. 불일치 자료는 보존한 채 신의 검색에서는 차단한다. quick_check/스키마 검사는 worker에서, 대형 무결성 검사·VACUUM/재구축은 충분한 여유와 승인된 유지보수에서만 수행한다. FULL 상태에서 자동 VACUUM으로 해결한다고 가정하지 않는다.

## 8. 신규 설정의 제안 예시

아래는 미래 `config/mythictrpg/recording-v2.json` 설정의 설계 예시다. 기존 `ai-memory-retention.json`에 붙여 넣을 수 있는 형식이 아니며 현재 서버에 생성하지 않았다. 경로/schema2는 M0에서 고정했고 parser·검증은 M1에서 구현한다.

```json
{
  "schemaVersion": 2,
  "archiveMode": "OFF",
  "worldRecordingLimitBytes": 100000000000,
  "maintenanceHeadroomBytes": 1000000000,
  "warningRatio": 0.90,
  "deferBackgroundRatio": 0.95,
  "overflowPolicy": "STOP_NEW_RECORDS",
  "automaticRawDeletion": false,
  "importLegacyTestData": false
}
```

날짜 만료 필드는 두지 않는다. 100GB/예비 여유는 signed 64-bit로 읽고 덧셈 overflow를 검사한다. 누락 설정은 기존 기능을 유지하면서 새 archive OFF다. 잘못된 설정을 작은 기본 한도로 몰래 바꾸어 정상 저장처럼 표시하지 않는다.

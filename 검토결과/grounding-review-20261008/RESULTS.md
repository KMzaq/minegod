# 대화 근거 검토 정확성 개선 — 2026-10-08

HanesTest / 개발 AI 0.1.33 / Ollama `gemma4:12b` / **운영 미배포**.

## 결론

**수정 전 초안이 재검토에 섞이는 구현 오류를 고쳤고, 다른 신의 약속을 자기 것으로 받아들이는 사례를 검출했다. 그러나 미완료 작업을 끝낸 듯 표현한 사례는 잘못 통과했고, 독립적인 새 의향을 과거 약속의 가로채기로 오해해 거절하는 문제도 남았다.** 구조 수정은 완료했지만 검토 정확성 개선은 부분 성공이다. 자연스러움 완성을 선언하지 않는다.

이 결과는 이전 실제 작성 포르투나·데메테르 프로필을 사용한 시험 기록과 명시적 합성 대조 사례의 작은 회귀 시험이다. 모델·페르소나·게임 상태를 바꾸지 않았다. 실제 서버 접속·대화·HUD 검증이 아니다.

## 동일 초안 비교

14개 사례: 수정해야 하는 4개, 그대로 허용할 10개. 정답 라벨은 시험 전에 근거와 함께 지정했다. 코드는 정확한 인용·형식을 확인하고, 의미 판정은 사람이 입력·대사를 대조했다.

| 검토 버전 | 예상 판정과 일치 | 잘못 허용 | 정상 대사 거절 | 잘못된 인용/형식 | 호출 실패 |
|---|---:|---:|---:|---:|---:|
| 기존 V3 | 11 | 2 | 0 | 1 | 0 |
| 중간 V4 | 12 | 1 | 0 | 1 | 0 |
| 중간 V5 | 13 | 1 | 0 | 0 | 0 |
| 최종 V6 — 같은 14건 | 13 | 1 | 0 | 0 | 0 |

V6에 독립적인 새 의향 대조 사례를 1개 추가한 **최종 15건은 예상 일치 13 / 오허용 1 / 과잉 거절 1 / 인용·형식 오류 0**이다. 14건 비교와 분모가 다르므로 성공률을 섞지 않는다. [최종 집계](run-final/live/summary.json).

- **타 신 약속:** V3는 잘못된 “내 말을 아주 잘 기억하고 있네?”를 PASS했다. V4는 잘못임을 알았지만 플레이어의 “들려준다던 이야기”를 인용해 유효하지 않았다. V5는 실제 NPC 대사를 인용한 `WRONG_SOURCE`를 반환했다. 동일 대사를 자기 약속으로 바꾼 대조 입력에서는 PASS했다.
- **폐기된 초안:** 현재 화자 ID를 이미 고쳤는데 V3는 폐기된 ID 오타를 다시 지적했다. V5는 원래 장면과 최신 초안만 보고 PASS했다.
- **조건부 칭찬:** “그런 마음으로 행동했다면…”은 V5에서 PASS했다. 단, 이번 V3 재시험도 PASS했다. 이전 기록의 과잉 거절은 있었지만 이번 비교로 과잉 거절률 개선을 입증한 것은 아니다.
- **유지된 경계:** 확인 대기 중인 토템 전달 주장과 근거 없는 길 생성 능력은 REVISE. 확인된 이전 지급, 직접 본 반환, 미래의 의향, 장난·비유적 위협, 보고에 대한 반응은 PASS.
- **남은 실패:** 현재 기록 정리가 미완료인데 “기분 좋게 마무리할 수 있었으니까”, “기다려 달라고 한 네 말”이라고 응답한 기존 사례를 모든 버전이 PASS했다. 현재 상태·행위자·시제의 미묘한 모순을 안정적으로 판별하지 못한다.

### 실제 수정 응답 후속 — 새 과잉 거절 발견

V5가 검출한 타 신 약속 사례만 실제 Gemma에 1회 수정시켰다. [후속 기록](run-v5/repair-followup/other_god_promise.json)의 답변은 다음과 같다.

> 산책은 나중에 해도 되니까, 일단은 이 책에 나오는 이야기를 들려줄게. 마침 재미있는 대목을 찾았거든. 자, 여기 앉아봐.

“내 말”이라는 과거 발언 소유 주장은 사라졌다. 현재 신이 책을 읽고 있다는 입력도 존재한다. 이야기 자체를 아직 풀지 않고 예고한 점은 남지만, 이를 **다른 신의 과거 약속을 자기 것으로 주장했다는 이유로 거절하는 것은 오판**이다. V5는 그렇게 REVISE했고, V6에서 새 의향과 과거 약속을 명시적으로 구분시켜도 같은 오판이 지속됐다. 이 답변을 성공한 수정/인게임 발행으로 세지 않는다. 실제 runtime이면 공통 수정 1회 예산이 끝났으므로 발행하지 않는다.

현재 미완료 작업 사례는 최초 검토가 PASS였으므로 후속 수정 자체를 건너뛰었다. 별도로 정답 지적을 주입해 고쳤다고 계산하지 않았다. 후속 생성·검토는 총 **2회** 호출, 모두 `stop`이었다. 최종 대조군은 이 실제 생성된 문장을 그대로 사용했다.

## 측정과 한계

- `run/live`: V3/V4를 사례별 교차 순서로 28회 호출. [최초 집계](run/live/summary.json).
- `run-v5/live`: 같은 14개의 V5만 추가 호출. V3는 원본 fixture·정책·요청·응답·파일 해시를 검사한 뒤 재사용했다. [V5 집계](run-v5/live/summary.json), [입력·재사용 근거](run-v5/live/manifest.json).
- `run-final/live`: V6의 기존 14건 + 위 새 의향 대조군 1건만 추가 검토. baseline 재호출 없음. [입력·정책 해시](run-final/live/manifest.json). 전체 작업 호출 수는 28+14+2+15 = **59회**이며 생성은 그중 1회다.
- 검토 58회는 temperature 0·최대 512 출력 토큰, 후속 생성 1회는 temperature 0.6·최대 260 토큰이다. 모두 `think=false`, 59개 응답 모두 `done_reason=stop`이었다.
- V3 검토 입력 평균 3,985.57 토큰, V5 4,479.36 토큰. 검토 지침 보강으로 약 494 토큰 증가했다. 검토 호출 수와 생성 프롬프트는 늘리지 않았다.
- V3 평균 검토 시간 1.968초, V5 1.773초. 다른 시점·캐시/부하 조건이므로 **속도 개선으로 해석하지 않는다.** 전체 대화 지연도 아니다.
- V6는 추가 대조를 포함한 15건 평균 입력 4,514.27 토큰·검토 시간 1.808초. 분모와 사례 구성이 다르므로 위 14건 비교의 속도/토큰 증감률로 사용하지 않는다.
- 13/14 및 추가 대조 포함 13/15는 **선택한 초안의 검토 판정 일치**다. 자연스러운 답변 생성 성공률이나 새로운 상황에서의 정확도, 모델 일반화 성능이 아니다. 이 사례로 지침을 보정했으므로 독립적인 미관측 평가로 볼 수 없다.
- 실제 기억 저장소 검색, 콘텐츠 공개 권한 결정, 장기 대화 일관성은 이번 실모델 비교 대상이 아니다. 다른 방·기억 격리는 별도 코드/게임 회귀로 확인했다.

## 재현

루트에서 기존 `.cmd` 실행기에 AI 절대 경로를 전달한다. 새 측정에는 새 출력 폴더를 사용한다. 이 도구들은 `check`에서 자동으로 LLM을 호출하지 않는다.

```powershell
.\dev-tools\run-mythictrpg-gradle.cmd -p C:\Users\ADMIN\Desktop\markmar\mythai-ai-response roomDialogueGroundingTest roomConversationEngineTest roomPersonaPromptTest roomReactionPromptTest roomEmotionStateTest verifyEnginePackage --console=plain
```

[evaluation.init.gradle](evaluation.init.gradle)을 `-I <절대경로>`로 지정하면 다음을 실행할 수 있다.

- `groundingComparisonPreflight`: 모델 호출 없이 14개 fixture 검사.
- `groundingComparisonLive`: V3/현재 버전 28회 검토.
- `groundingComparisonCandidate`: `-PgroundingComparisonBaseline=<기존 run/live 절대경로>`와 `-PgroundingComparisonOutput=<새 폴더>`로 14회만 호출. 기준 결과 변조/불일치 시 중단.
- `groundingComparisonFinalControl`: 기존 14건과 보존된 후속 생성 대조군 1건을 현재 검토기로 15회 검사. baseline 없이 실행한다. 최초 후속 생성 기록이 있어야 한다.

[repair-followup.init.gradle](repair-followup.init.gradle)의 `groundingRepairFollowup -PgroundingRepairLive=true`는 유효한 REVISE가 난 사례만 1회 수정·재검토한다. PASS를 수리한 것처럼 계산하지 않으며 실제 게임에는 발행하지 않는다.

# 탐험과 상호작용 시스템 작성 가이드

2026-10-20 시작 · 2026-10-21 후속 · `behaivior` 개발 작업.

이 가이드는 제안 2 3 4 5 7 8번의 공통 실행 기능을 설명한다. 전체 진행 기획과 귀속장비·재지급은 범위 밖이다. 기획 분담과 실제 콘텐츠의 작성 항목은 [작업 분담 문서](../../전달자료/content-planning-system-split-20261020.md)를 따른다. 정식 신·사건·확률·레이드 수치는 이 기능 작업에서 추가하지 않는다.

## 실행 구조

`실제 조사 또는 기존 게임 사건 → 공통 조건 검사 → 기존 Story 사건 → 지식과 정식 연출 및 외부 효과 → 기존 보상 또는 평판 저장소`

신의 실체·레이드·관계·퀘스트·보상을 새 엔진으로 복제하지 않는다. 조사, 보상, 방문, 전투 대응은 게임 모듈이 검증한다. AI 대사만으로 발견·습득·지급·도착·평판 회복을 확정하지 않는다. 이번 변경은 AI 모델과 프롬프트, Snapshot 및 Proposal 계약을 바꾸지 않는다.

새 데이터팩 정의 세 종류는 하나의 불변 snapshot으로 로드한다. 각 종류 최대 256파일, 파일당 최대 65,536문자다. 알 수 없는 필드·누락·잘못된 숫자를 거절한다. 잘못된 reload는 새 snapshot으로 교체하지 않는다. 정의가 없으면 새 조우·피해 보정·Story 예약을 활성화하지 않는다. 다른 모듈의 참조와 현재 게임 자격은 실행 시에도 검사한다.

## 일반 플레이 연결

2·3·4·5·8번은 일반 플레이 경로에 등록되어 있으며 시험 모드를 활성화할 필요가 없다. 아래 작성 데이터와 게임 조건이 충족되어야 실제 콘텐츠가 발생한다.

| 항목 | 플레이어의 진입점과 실행 | 필요한 콘텐츠 정의 |
|---|---|---|
| 2 단서·조우 | 현장 웅크리기 우클릭 또는 일반 권한 `/mythinvestigate`, 개인 `/mythclues` | 조사점, Story 사건·사실·지식 단계·공개 정책 |
| 3 전투 준비 | 퀘스트·Story 보상으로 받은 도구 → 일반 `/mythraid create/join/start` → 실제 레이드 피해 처리 | 지급 사건/퀘스트, 대응 아이템의 component, 레이드·피해 종류·효과·소모 여부 |
| 4 재료의 여러 경로 | 조사·퀘스트 완료·기존 게임 관찰 → 작성된 Story 결과 → 기존 지급 영수증 | 경로별 trigger·조건·반복 주기와 `GRANT_REWARDS` |
| 5 집·생활 | 일반 `/mythstructure` 등록, `/mythvisits on/off` → 일반 대화의 방문 제안 또는 자율 판단 → 실제 보행·도착 | 신의 실체/이동 정의, 방문 정책, 도착 후 Story 사건 |
| 8 동시 사건 | 각 플레이어의 일반 사건과 대화가 독립 진행하고, 공유 자원 사건만 대기/거절 | 공유 자원 ID, 개인 점유 여부, LATCHED/IMMEDIATE·만료·선택 정책 |

보상 경로용 관찰 trigger는 구체적인 관찰 ID를 사용한다. 예를 들어 성숙한 밀 수확은 `signal: mythictrpg:mature_crop_harvested`, `subject: minecraft:wheat`다. `gameplay_observed`라는 범용 trigger로 모든 행동을 받는 구조가 아니다. 다른 생산자의 실제 신호·주체를 확인해 작성한다.

방문 설정은 [집 방문 가이드](GOD_HOME_VISITS.md)의 일반 플레이 절차를 따른다. 정식 정의가 없어서 비활성인 것과 시험 전용 기능은 다르다. 아래 예제와 GameTest 데이터는 정식 인물·스토리·밸런스가 아니다.

## 현장 조사

경로: `data/<namespace>/mythictrpg/investigations/<path>.json`

```json
{
  "schemaVersion": 1,
  "dimension": "minecraft:overworld",
  "position": [100, 64, 100],
  "block": "minecraft:stone",
  "radius": 4,
  "event": "example:coast_trace",
  "heldItem": "minecraft:feather",
  "components": {},
  "heldCount": 1,
  "cooldownTicks": 200,
  "condition": {"type": "mythictrpg:always"}
}
```

설명용 조사점이다. 실제 장소와 Story 사건은 별도로 작성한다. 파일 ID가 조사점 ID다. 해당 블록에서 **웅크리고 주 손으로 우클릭**하거나 `/mythinvestigate <조사점ID>`를 사용한다. 명령에도 동일한 거리와 시야 검사를 적용한다.

- 성공한 우클릭 조사는 해당 상호작용을 완료 처리하므로 같은 클릭으로 블록 설치·아이템 사용까지 실행하지 않는다. 앞선 다른 이벤트 처리기가 취소한 상호작용은 조사하지 않는다.
- 차원, 로드된 청크, 실제 블록 ID, 바닐라 블록 상호작용 거리, 시야, 작성된 반경을 검사한다. 청크를 강제로 로드하지 않는다.
- `radius`는 1부터 8까지이며 실제 상호작용 거리를 늘려주는 값은 아니다.
- `heldItem`은 주 손의 현재 아이템이다. 과거 획득 조건과 다르다. 물건이 필요 없으면 `NONE`, `heldCount`는 1로 쓴다. 수량은 1부터 64까지이며 조사로 소비하지 않는다.
- 선택 필드 `components`는 기존 보상 ItemStack component 형식이다. 생략하거나 `{}`이면 바닐라 기본 변형과 정확히 비교한다. 모델·이름·인챈트 등 다른 component를 가진 물건은 같은 ID만으로 인정하지 않는다. 수량은 별도로 검사한다. 출처 인증을 대신하는 필드는 아니다.
- `condition`은 기존 공통 조건 트리를 사용한다. 이 조사에서는 해당 플레이어와 PLAYER Story 범위로 평가한다. Story 사건 자체의 전제조건과 반복 정책도 다시 검사한다.
- 죽음·관전자·접속 교체·시험 대화방에서는 조사하지 못한다. 조건 불일치를 알려줄 때 미공개 조건이나 단서 본문을 노출하지 않는다.
- `cooldownTicks`는 20부터 72,000까지다. 조사 시도 억제는 서버 메모리의 플레이어별 상태이며 재접속 중 유지하고 서버 종료 시 해제한다. 발견·보상 반복 제한의 영속 원본은 Story 사건이다. 서버 재시작으로 Story 최초 지급이 다시 가능해지는 구조가 아니다.
- 같은 좌표의 여러 조사점은 ID 순 첫 항목만 사용하므로, 서로 다른 반응은 하나의 Story 사건 안에서 조건과 결과로 분기하는 편이 적합하다.

현재 조사점은 명시한 고정 블록 좌표를 사용한다. 자연 생성 유적 자동 탐색, 아이템의 발굴 출처 인증, 모든 종류의 손동작·낚시·고고학 행동 감지는 별도 생산자가 필요하다. 기존 수확·채굴 등의 사건은 기존 관찰과 Story 연결을 계속 사용한다.

## 습득한 단서 재열람

- `/mythclues`: 본인이 이미 아는 Story 사실을 10개씩 표시한다. 알려진 첫 단계 문구를 클릭하면 다시 읽는다.
- `/mythclues page <페이지>`: 1부터 시작하는 페이지.
- `/mythclues read <사실ID>`: 해당 플레이어가 알고 있는 단계까지의 정식 문구만 표시한다.

단서 전용 사실 DB를 만들지 않고 기존 `StoryRuntimeState`의 플레이어 지식을 조회한다. 다른 플레이어, NPC의 지식, 관리자 설명, 아직 배우지 않은 단계는 포함하지 않는다. 플레이어가 알고 있는 내용의 개인 재열람과 현재 방 청중에게 공개할 권한은 다르다. 이 명령은 개인에게만 보내며 방이나 NPC에게 공유하지 않는다.

실제 조사는 Story `GRANT_KNOWLEDGE`로 습득 단계와 공개 정책을 기록한다. 단순히 조사 명령에 성공했다고 모든 관련 정보를 자동으로 배운 것으로 처리하지 않는다. 별도 지도·단서장 그래픽 UI를 추가한 것은 아니다.

## 사건의 재료 보상

Story outcome의 `effects`에 다음 효과를 추가할 수 있다.

```json
{
  "effectId": "example:give_material",
  "type": "GRANT_REWARDS",
  "god": "mythictrpg:demeter",
  "rewards": [
    {"type": "item", "itemId": "minecraft:gold_nugget", "count": 1}
  ]
}
```

형식 설명용 보상이다. 실제 지급 물건과 제공 신은 기획에서 정한다. `rewards`는 기존 `RewardEntryCodec` 형식 1부터 16개를 사용하고, 기존 QUEST 보상 검증과 ItemStack component 검증을 거친다. 선택형 보상은 기존 퀘스트의 선택 claim 경로를 사용한다.

보상은 **사건을 시작한 온라인 플레이어 한 명**에게 지급한다. SERVER 사건이라고 온라인 전원에게 지급하지 않는다. 공동 목표·분배는 기존 참여형 퀘스트를 사용한다. 등록되지 않은 신과 지급 전제조건 오류는 사건 검증에서 차단한다.

새 보상 원장을 만들지 않는다. 사건 instance와 effect ID에서 고정된 source ID를 만들고 기존 `RewardClaimService`로 지급한다. 이미 완료한 같은 지급의 재호출은 다시 주지 않는다. 외부 지급이 보류되면 사건은 성공 연출을 내보내지 않고 외부 효과 대기로 남는다. 지급 claim은 완료됐지만 사건의 효과 영수증이 없는 불명확한 저장 상태는 RECOVERY_REQUIRED로 남긴다. 재지급하거나 지급 성공으로 추측하지 않는다. 기존 지급 경계의 먼저 기록하는 방식과 저장 한도는 유지하므로 프로세스 강제 종료를 포함한 모든 상황의 완전한 지급 트랜잭션을 새로 보장하는 것은 아니다.

보상 목록은 Story 정의 안에 작성해 사건 fingerprint에 포함한다. 진행 중 보상표 reload로 보상이 달라지지 않게 **공유 보상표 ID를 실행 때 동적으로 읽는 기능은 제공하지 않는다**. 같은 재료를 여러 사건 경로에 배치할 때 같은 보상 항목을 작성하고, 각 사건의 ONCE·LIMITED·COOLDOWN으로 빈도를 정한다. 상점·제작·레이드의 기존 지급 경로는 그대로다.

기존 Story는 정식 사실·지식 변경을 먼저 commit하고 외부 지급·관계 효과를 처리하는 구조다. **지급이나 회복 성공에 종속된 완료 사실과 지식**은 같은 outcome에서 미리 설정하지 말고, 해당 사건의 `mythictrpg:event_resolved` 신호를 받는 후속 사건에 둔다. 여러 저장소의 변경을 하나의 롤백 가능한 트랜잭션으로 묶은 기능은 아니다.

## 레이드 대응 도구

경로: `data/<namespace>/mythictrpg/raid_countermeasures/<path>.json`

```json
{
  "schemaVersion": 1,
  "raid": "example:trial",
  "damageType": "minecraft:mob_attack",
  "item": "minecraft:feather",
  "components": {"minecraft:custom_model_data": 31},
  "consume": true,
  "multiplier": 0.5
}
```

실제 레이드의 밸런스가 아닌 작성 예다. 배율은 0 이상 1 미만이며 레이드 하나에 최대 32개 규칙을 둔다. 같은 레이드와 피해 종류에 서로 다른 도구 정의를 중복 등록하면 reload를 거절한다.

- 실제 ACTIVE 레이드의 살아 있는 참가자에게, 그 시도가 실제 생성한 보스·추가 몹이 준 작성된 종류의 피해에만 적용한다.
- 참가자와 공격자가 같은 전장·차원에 있어야 한다. 외부인, 다른 시도, 탈락·리스폰 대기, 일반 환경 피해에는 적용하지 않는다.
- 도구는 보조 손 또는 주 손에 준비해야 한다. 둘 다 같은 물건이면 보조 손을 한 번 사용한다. 인벤토리 전체를 찾아 자동 소비하지 않는다.
- 선택 필드 `components`를 포함한 실제 변형을 기존 보상 codec으로 구성해 정확히 비교한다. 일반 물건이 같은 ID의 특수 도구를 대신하지 못한다. 생략 시 기본 변형이며, 수량을 제외한 내구도·이름·인챈트 등도 비교에 포함한다.
- 실제 최종 피해 직전의 양수 피해에 배율을 적용한다. `consume=true`이면 해당 손에서 한 개를 소비한다. 막혀서 피해 단계에 도달하지 않은 공격에 도구를 소비하지 않는다.
- 대응 도구 정책은 모집 생성 시 시도에 고정하고 저장한다. 기존 진행 중 시도에는 새 정책을 뒤늦게 주입하지 않는다.

이 기능은 지정 피해에 대한 준비 도구다. 패링 판정, 보스별 반격 창, 기믹 해제, 힐·지원 능력은 각 전투의 별도 생산자와 연결해야 한다. 도구 획득 의뢰와 관계 조건은 기획 콘텐츠로 작성한다. 전투력 코드는 이번 범위에서 변경하지 않으며, 대응 도구를 보상으로 지급할 때 기존 전투력 정책에서 해당 변형을 `IGNORE`로 분류해야 한다.

## 방문 허용과 도착 후 사건

- `/mythvisits off`: 본인의 등록 건축물 방문을 받지 않는다.
- `/mythvisits on`: 방문을 허용한다. 특정 신의 방문이나 실제 도착을 보장하지 않는다.

기존 월드의 방문 동작을 유지하기 위해 미설정 기본값은 허용이다. 플레이어별 설정은 `mythictrpg_home_visit_preferences.dat`에 저장한다. 손상 시 기본 허용으로 숨기지 않고 방문을 차단하며 원본을 보존한다. 설정 상한은 차단 UUID 4,096개다.

설정은 새 판단, 비동기 판단 적용, 이동 중에 다시 검사한다. 차단은 이동 중 방문도 중단한다. 기존 실제 실체·건축물 소유·정책·경로·신 예약 검사를 우회하지 않는다. 원격 신을 소환하거나 텔레포트시키지 않는다. 자율 방문의 낮은 우선순위와 기존 AI 모델 설정은 유지한다.

실제로 도착하면 `mythictrpg:home_visit_arrived` Story 신호를 보낸다. subject는 실제 God ID, 시작 플레이어는 건축물 소유자다. 해당 신호와 subject를 가진 작성형 사건으로 후속 부탁·단서·생활 연출을 연결한다. 판단 접수·이동 시작·실패·취소는 도착 신호가 아니다. 방문 대상 건축물 UUID까지 구분하는 Story 조건은 이번 신호에 추가하지 않았다.

## 게임 결과에 따른 평판 회복

```json
{
  "effectId": "example:resolve_assessment",
  "type": "RECOVER_REPUTATION",
  "god": "mythictrpg:fortuna",
  "policy": "example:existing_reputation_rule",
  "reason": "example:restitution_completed"
}
```

배상·중재 등 **권위 게임 결과가 성립한 Story outcome**에 배치한다. `policy`는 기존 평판 설정의 규칙 ID다. AI가 사과를 받아들였다는 문장만으로 호출하지 않는다. 사건을 시작한 플레이어, 지정 신과 정책에 해당하는 현재 평가만 기존 원장에서 RECOVERED로 갱신한다. 원래 사건·소문, 최초 승인, 다른 플레이어·신·정책, 호감도 원본은 바꾸지 않는다.

2026-10-21 후속으로 **일반 플레이에서도 실행 가능**하다. 평판 서비스는 `reputation-judgement.json`의 명시 설정으로 시작하며 AI 기억 모드와 독립적이다. 따라서 `PERSONAL`뿐 아니라 AI 기억이 `OFF`여도 승인된 게임 사건의 회복은 동작한다. 설정 비활성·잘못된 정책·미등록 신은 Story 효과 적용 전에 거절한다. 소문 생성·평가·대화 조회는 일반 `PERSONAL`에서 각 기존 설정과 목격·공개 권한 검사를 거쳐 연결된다. [일반 플레이 평판 가이드](REPUTATION_GAMEPLAY_GUIDE.md)를 따른다.

회복은 현재 평가 집합과 완료 영수증을 기존 평판 저장소 안에서 함께 갱신한다. 같은 결과 ID의 재전송은 최초 결과만 인정하며 이후 생긴 평가를 회복하지 않는다. 대상이 0개인 결과도 기록한다. 저장된 완료 영수증이 있으면 Story 재시작 시 완료 확인만 재개하고, 영수증 없는 불명확한 상황은 RECOVERY_REQUIRED로 남긴다. 알려진 시험 출처는 일반 플레이 회복 대상에서 제외한다. 여러 SavedData 파일을 한 번에 디스크에 확정하는 트랜잭션은 아니다.

## Story 사건 자원 예약

경로: `data/<namespace>/mythictrpg/story_admission/<event_path>.json`  
파일 ID가 예약 정책을 적용할 **기존 Story event ID**다.

```json
{
  "schemaVersion": 1,
  "playerExclusive": true,
  "resources": ["example:coast_altar"]
}
```

같은 논리 자원을 사용하는 사건들에 같은 resource ID를 작성한다. `playerExclusive=true`인 사건끼리는 같은 시작 플레이어를 동시에 점유하지 않는다. 정책이 없는 독립 사건은 기존대로 병행한다. 내부 플레이어 예약용 `mythictrpg:content_player/` 경로는 작성 자원으로 사용할 수 없다.

점유는 기존 Story event instance의 `reservedResources`에 저장한다. 선택 대기·결정·외부 효과 대기·복구 필요 상태에서도 유지한다. RESOLVED·CANCELLED는 점유하지 않는다. LATCHED trigger는 자원이 바쁠 때 기존 만료 정책 안에서 다시 평가한다. 일반 IMMEDIATE 시도는 거절되므로 재방문·다음 행동 등 기획된 재시도 계기가 필요하다.

LATCHED 신호는 동일 사건의 열린 선택이나 쿨다운에 막힌 경우에도 남는다. 시작 플레이어가 오프라인인 PLAYER/TEAM 대기는 만료 시각까지 유지되며 접속 후 재평가한다. 저장된 범위·청중을 사용하므로 기다리는 사이의 팀 변경으로 다른 팀에 사건을 옮기지 않는다. 정의의 scope 타입을 변경한 대기는 기록을 남기고 거절한다. 사건 해결에 따른 즉시 재평가에서도 만료를 먼저 확인하고, 한 평가 안에서 같은 저장 신호가 재귀적으로 실행되지 않게 한다. 최대 반복 횟수 소진은 종결한다.

`SCHEDULE_EVENT`의 PLAYER/TEAM 예약도 시작 플레이어가 오프라인이면 저장 상태로 유지하고 로그인 때 큐에 다시 등록한다. 해당 예약을 기다리는 동안 다른 플레이어의 예약 사건은 진행한다. 재개에도 원래 범위·청중을 사용한다. 이 보존 규칙은 오프라인에 적용되며, 온라인 실행 시 전제조건·자원 충돌의 대기 여부는 대상의 LATCHED/IMMEDIATE 정책을 따른다.

예약 정책을 바꾸거나 지워도 진행 중 instance가 갖고 있던 예약은 보존한다. 새 사건의 정책을 제거하면 그 새 사건은 더 이상 해당 자원을 요청하지 않으므로, 공유 자원을 쓰는 모든 사건의 정책을 일관되게 작성해야 한다. 예약은 Story의 논리 자원 관리이며 실제 NPC·전장 lease를 대체하지 않는다.

기존 저장본의 예약 필드 누락은 빈 예약으로 읽는다. 잘못된 타입·상한 초과는 기존 Story 손상 격리로 처리한다. 새 예약과 외부 효과를 사용한 월드를 구 JAR로 되돌리면 의미 보존을 보장하지 않는다. 기존 대화의 자동 중단·재개, 모든 모드의 장치 점유, 실패 사건의 자동 롤백을 추가한 것은 아니다.

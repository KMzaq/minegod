# NPC를 통한 퀘스트 참가자 재편성

2026-10-02 `HanesTest` 개발본: 게임 **1.0.24**, AI **0.1.27**, 콘텐츠 **0.1.3**. 게임 protocol 10 유지. 운영 미배포. 검증 결과는 [브랜치 기록](../../인수인계/브랜치실험/HanesTest/QUEST_REORGANIZATION_20261002.md)을 따른다.

## 범위와 설정

고정 참가자의 장기 부재로 막히는 `GROUP` 및 `RANKING/ALL_SUBMITTED`에 선택적으로 적용한다. SOLO, COMPETITIVE, 시간 제한 랭킹, 기존 개인형 즉석 생성 퀘스트에는 적용하지 않는다. 목표 종류·완료 NPC·보상표·최종 정산 경로는 바꾸지 않는다.

[퀘스트 바인딩](FTB_QUESTS_INTEGRATION_GUIDE.md)의 `participation`에 다음 `reorganization`을 추가한다. **작성 예시이며 활성 콘텐츠나 밸런스 기본값이 아니다.** 생략하면 기존 고정 명단 방식이다.

```json
{
  "participation": {
    "type": "GROUP",
    "objectives": [
      {"kind": "ITEM_SUBMISSION", "subject": "minecraft:heart_of_the_sea", "count": 2}
    ],
    "reorganization": {
      "allowWithdrawal": true,
      "absentAfterTicks": 1728000,
      "allowReplacement": true,
      "minimumParticipants": 1,
      "refundItems": true
    }
  }
}
```

이 조각 외에 schemaVersion/questId/FTB ID/완료 방식 등 원래 필수 필드는 필요하다. 신 프로필이나 AI 프롬프트가 아닌 **게임 퀘스트 바인딩**에 작성한다. 파일 경로는 `data/<namespace>/mythictrpg/ftb_quests/<id>.json`이다. 운영 팩 변경·배포는 별도 작업이다.

| 필드 | 의미 |
|---|---|
| `allowWithdrawal` | 미제출자가 본인의 참여 포기를 요청할 수 있는지 |
| `absentAfterTicks` | 오프라인 제외 기준. 0은 장기 부재 제외 금지, 최대 630,720,000 |
| `allowReplacement` | 초기 확정 인원수 이하로 빈자리 충원을 허용하는지 |
| `minimumParticipants` | 수주·정산에 필요한 최소 인원, 정수 1~16 |
| `refundItems` | 참여가 끝난 미제출자에게 이 퀘스트가 실제 소비한 제출품을 반환할지 |

다섯 필드는 모두 명시해야 하며 잘못된 타입·소수·추가 필드는 거절한다. 포기와 부재 제외 중 하나는 허용해야 한다. 최소 인원이 2 이상이면 충원도 허용해야 한다. 1인 수주도 계속 허용하려면 최소 인원을 1로 둔다.

부재는 마지막 서버 접속 확인 이후의 **서버 가동 게임 틱**으로 계산한다. 예시 1,728,000틱은 20 TPS에서 가동 24시간이다. 접속 중 자리비움은 장기 부재가 아니고, 서버가 꺼져 있던 현실 시간도 제외한다. 로그아웃 시각을 기록하며 재접속하면 기준을 갱신한다. 기준을 넘겨도 자동 추방하지 않는다.

## 플레이 흐름

1. 현재 퀘스트 참가자가 준 NPC 또는 지정 완료 NPC의 **일반 대화방**에 직접 참여하여 포기/재편성을 요청한다.
2. AI는 `quest_roster_request`로 게임이 제공하는 관리 선택지만 연다. 가능한 선택: 본인 포기, 조건에 맞는 부재자 제외, 현재 방에 직접 참여한 적격자의 빈자리 충원.
3. 선택하면 실제 대상·완료 보상 포기·제출품 수량/반환 여부·최소 인원을 NPC HUD에 안내하고 클릭 확인/취소를 제시한다. 포기/제외는 요청자가, 충원은 **새 참가자 본인**이 확인한다. 같은 방의 확인 단계에서 `네/예/yes/확인`, `아니요/아니오/no/취소`도 사용할 수 있다.
4. 서버가 현재 방·신·접속·참가 명단 revision·바인딩 generation·수주 자격·최종 제출·확인 후 실적 변경을 다시 검사한 뒤 반영한다. NPC에게 실제 결과를 전달하고 기존 완료 조건이 충족되면 정산한다.

수주자 본인만 포기할 수 있고 접속 중인 동료를 임의로 제외할 수 없다. 부재 제외는 현 참가자 누구나 요청할 수 있으며, 서버가 부재 기준을 검증한 뒤 요청자의 확인으로 처리한다. 별도 리더/다수결 제도는 추가하지 않았다.

확인 선택지는 1,200틱 후 만료된다. 방 종료·revision 변경·로그아웃·퀘스트 reload·대상 재접속·최종 제출 등으로도 무효화되며 자동 동의는 없다. 신규 퀘스트 수주 질문과 동시에 처리하지 않는다. 만료되면 NPC에게 다시 요청한다.

AI 없이도 같은 검증 경로로 시험할 수 있다:

```text
/mythquest roster <대화방 코드 또는 UUID> <신 ID> <퀘스트 ID>
```

`roster-select <token>`과 `roster-answer <token> yes|no`는 서버가 발급한 클릭용 명령이며 타인의 토큰을 사용할 수 없다. legacy `/mythtalk` 세션만으로 관리할 수 없고 현재 일반 대화방의 실제 참가·revision이 필요하다.

## 실적·보상·메인 자격

- **최종 제출 완료자**는 오프라인이어도 제외/포기 대상이 아니다. 실적과 기존 완료·보상 규칙을 보존한다. 아이템 일부/전부를 낸 것과 NPC의 최종 제출 확정은 다르다.
- 제거된 미제출자는 이 실행의 완료·순위·보상 대상에서 빠진다. 재촉도 종료한다. 새 참가자는 자기 실적 0부터 수행하며 타인의 점수나 제출품을 이어받지 않는다.
- 남은 인원이 최소 인원 이상이고 전원 최종 제출했다면 기존 공동 완료/랭킹 정산을 실행한다. 최소 인원 미달이면 충원까지 기다린다. 모든 미제출자가 포기해 0명이 되면 취소 종료하며 완료·보상·월드 진행도는 주지 않는다.
- 충원은 최초 확정 인원수를 늘리는 모집이 아니다. 같은 실행에서 이탈자 재가입은 막고 총 참여 이력은 최대 64명으로 제한한다. 최초 인원은 최대 16명이다. 닫힌 퀘스트를 다시 열지 않는다.
- **처음 선택된 사람만 해당 신의 메인을 진행한다는 규칙은 그대로다.** 탈퇴/제외해도 기존 focus 자격을 지우지 않는다. MAIN은 기존 자격이 있는 후보만, MAIN_ENTRY도 이미 선택된 후보만 검토하므로 재편성으로 새 메인 권한을 만들지 않는다. 첫 메인처럼 적격 충원 후보가 사실상 없는 의뢰는 `minimumParticipants: 1`과 남은 인원 정산을 고려해야 한다. 높은 최소 인원을 설정해도 적격 후보를 자동 생성하지 않는다.
- FTB는 개인 미러 표시만 갱신한다. 이탈자 마커/고정을 해제하고 다른 사람의 실적을 건드리지 않는다. 오프라인 변경은 다음 접속 때 표시를 복구한다. 최종 판정/지급은 MythicTRPG 소유이며 FTB 보상을 복제하지 않는다.

`refundItems: true`는 정확히 소비한 아이템의 이름·components를 기록하고 기존 `RewardClaimService`로 원래 제출자에게 반환한다. 관찰 실적·평가 점수·타인 아이템을 반환하지 않으며 추가 보상/호감도도 만들지 않는다. 반환 표시/중요 이력은 완료 보상과 구분한다. 오프라인은 지급권을 보존하고 다음 접속 또는 `/mythquest rewards`로 수령한다. 한 번에 최대 16스택씩 큐에 넣어 큰 기부량도 다음 틱 검사에서 계속 반환한다.

반환 source는 `mythictrpg:quest_refund/<run UUID>/<player UUID>/<수량 offset>`이다. 반복 처리/정상 저장 복원 시 기존 claim과 반환 cursor로 중복을 막는다. 공간이 모자라면 기존 보상 지급 규칙(남은 아이템 드롭)을 따른다. 아이템 정의가 사라지거나 저장/지급 검증에 실패하면 보류한다. 반환 가능한 기록을 만들 수 없는 아이템은 제출 단계에서 소비하지 않는다. 기존 플레이어 인벤토리와 여러 SavedData 파일의 **비정상 종료·부분 백업 복원 전체를 하나의 원자적 트랜잭션으로 보장하는 기능은 아니다**. 관련 월드 데이터는 함께 백업·복원해야 한다.

## AI 계약·영속성·남은 검증

- Proposal은 `type: quest_roster_request`, `parameters: {"quest_id":"namespace:id"}`만 허용한다. AI가 대상 UUID/제외 사유/반환량/동의를 지정하지 못한다. 게임 capability, 현재 화자의 `[QUEST_ROSTER_REQUESTS]` 목록 및 최종 Validator를 모두 거친다.
- Primary의 정보 질문/회상으로 분류돼도 메뉴 요청만 허용한다. 다른 gameplay Proposal 권한은 늘리지 않고 read-only/Secondary/종료된 방은 차단한다. `EXECUTED`는 **메뉴를 열었다**는 뜻이며 명단 변경 완료가 아니다.
- 확인 대기/실제 반영 결과는 `[QUEST_ROSTER_LAST_RESULT]`로 같은 방·신·플레이어에만 최대 1,200틱 유지한다. 다음 턴에서 이어 말할 근거이지 별도 LLM 자동 호출이나 장기 기억 DB가 아니다.
- `mythictrpg_quests` 저장 버전은 2, 버전 1은 읽을 수 있다. 이전 실행의 roster 미지정은 고정 명단 그대로다. 기존 실행에 설정을 소급 적용하거나 제출품 영수증을 추측하지 않는다. 실행 중 정책을 바꾸면 비교 검증에서 보류되므로 원래 정책을 복원해야 한다. **이전 버전으로 롤백할 때는 업데이트 전 월드 백업이 필요하다.**
- 이번 작업은 기존 활성 퀘스트 JSON을 자동 변경하지 않았다. 새 퀘스트/새 실행에 opt-in 설정을 작성해야 한다. 운영 배포, 실제 클라이언트 HUD/클릭 및 실제 LLM의 요청 생성·말투 검사는 별도로 남는다.

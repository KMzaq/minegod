# 실제 프로젝트 연결 자료

기준: 2026-10-04, HanesTest의 개발 소스와 서버 폴더 파일. 이 자료는 콘텐츠 작성자에게 전달하는 참고 사본이다.

## 신 ID

사용자가 확정한 신규 God ID 규칙은 **소문자 영어 `소속신화_소속_신이름`**이다.

```text
프로필 파일: greek_olympian_demeter.json
게임 God ID: mythictrpg:greek_olympian_demeter
프로필 콘텐츠 ID: mythaiaicontent:greek_olympian_demeter
```

프로필 파일과 게임 God Definition은 서로 다른 종류의 파일이다. 게임은 `data/<namespace>/mythictrpg/gods/<path>.json`에서 `<namespace>:<path>`를 God ID로 만든다. AI 프로필의 `godId`에 그 값을 그대로 넣는다. God Definition의 `faction`은 게임 세력 정보이며, 이름의 ‘소속’ 문자열과 자동으로 같아지는 필드는 아니다.

- [사람이 읽는 God ID 목록](GOD_ID_LIST.md)
- [전체 God ID와 원문 위치 JSON](GOD_ID_INVENTORY.json)
- [퀘스트·진행도·프로필·바인딩 연결 JSON](QUEST_LINK_INVENTORY.json)

현재 게임 개발 소스의 God Definition은 4개다. 서버 폴더에는 그리스 테스트 데이터팩의 정의 135개가 추가로 있다. 총 139개의 서로 다른 파일 기반 ID를 목록으로 제공한다. 활성 데이터팩 목록/실행 중 레지스트리를 조회한 결과는 아니므로 각 JSON에 `runtimeRegistrationVerified: false`를 적었다.

실제 데이터팩의 데메테르 ID는 `mythictrpg:greek_olympian_demeter`다. `greek_olympus_demeter`로 철자를 바꾸면 다른 신이 된다. 기존 개발 테스트 신 `mythictrpg:demeter`, `mythictrpg:fortuna`는 이전 ID 그대로이며, 새 ID의 자동 별칭이 아니다. 포르투나의 새 소속 분류는 아직 정하지 않았다. 작성자는 소속을 확정한 뒤 세 부분 ID를 정하고, 기존 테스트 신을 이전할 경우 게임 정의·참조·저장 상태의 이관도 요청해야 한다.

## 원문 파일을 찾는 방법

`reference/` 안에는 원래 프로젝트 경로를 유지한 사본이 들어 있다.

| 자료 | 사본 경로 |
|---|---|
| 현재 게임 신 정의 4개 | `reference/mythictrpg-main/src/main/resources/data/mythictrpg/mythictrpg/gods/` |
| 그리스 테스트 신 정의 135개 | `reference/server/world/datapacks/mythictrpg-greek-ai-test/data/mythictrpg/mythictrpg/gods/` |
| 현재 개발 AI 프로필 | `reference/mythai-ai-content-registry/src/main/resources/data/mythaiaicontent/mythai_ai/god_profiles/` |
| 현재 퀘스트 후보 목록 | `reference/mythai-ai-content-registry/src/main/resources/data/mythictrpg/mythai_ai/quest_lists/` |
| 실제 FTB 바인딩 | `reference/mythictrpg-main/src/main/resources/data/mythictrpg/mythictrpg/ftb_quests/` |
| 신 보상 등급표 | `reference/mythictrpg-main/src/main/resources/data/mythictrpg/mythictrpg/reward_tables/` |
| 즉석 사이드 퀘스트 템플릿 | `reference/mythictrpg-main/src/main/resources/data/mythictrpg/mythictrpg/generated_quest_templates/` |
| 개발용 FTB 퀘스트북 | `reference/mythictrpg-main/ftbquests-pack/config/ftbquests/quests/` |
| 현재 서버 폴더의 FTB 퀘스트북 | `reference/server/config/ftbquests/quests/` |
| 엄격한 바인딩·보상·참여 목표 파서 | `reference/mythictrpg-main/src/main/java/com/sande/mythictrpg/quest/` |

`test5` 프로필에는 `mythictrpg:test5`가 있지만 이번에 확인한 God Definition에는 없다. 데메테르와 올림포스의 현재 퀘스트 목록은 비어 있다. 이 사본을 복사하는 것만으로 미작성 퀘스트나 새 연결이 생기지는 않는다. 프로필이 참조하는 모든 로어와 서버 콘텐츠 JAR의 전체 데이터까지 이 묶음에 넣은 것은 아니다.

## 퀘스트를 연결하는 세 층

1. AI 후보 목록 `mythai_ai/quest_lists`: NPC가 설명할 제목·내용·목표·보상과 수주 가능 진행 구간.
2. 게임 바인딩 `mythictrpg/ftb_quests`: 실제 완료 방식·NPC·공용 진행도·FTB ID·게임 보상 정책. `questId`는 파일에서 계산한 ID와 같아야 한다.
3. FTB SNBT: 화면에 표시할 실제 퀘스트와 숨김 수주 마커. 두 퀘스트의 ID를 바인딩에 정확히 연결한다.

현재 세 층이 연결된 개발 예시는 `mythictrpg:fortuna_deep_sea_heart`다. 실제 퀘스트 FTB ID는 `21F48990D282287B`, 수주 마커는 `5DD74E73298791E8`이다. 개발 AI 후보와 개발 FTB는 바다의 심장 **2개**, 보상은 불사의 토템 **1개**다. 현재 서버 FTB 파일은 심장 **1개**로 남아 있어 차이를 별도로 기록했다. 작성 초안은 개발본을 기준으로 맞추고, 배포 때 서버 정의도 함께 맞춰야 한다. 이번 작업에서는 원본이나 서버 파일을 수정하지 않았다.

신규 연결 예시는 [게임 연결 양식 안내](../05_게임연결_양식/00_양식_설명.md)를 따른다. 기존 포르투나는 FTB 아이템 보상 버튼을 사용하는 예시다. 새 양식은 게임의 직접 보상을 사용하는 별도 예시이며 FTB 보상을 비워 두었다. 같은 보상을 양쪽에 동시에 넣지 않는다.

## 목표·보상 표현

AI 후보의 `{type, description, parameters}`와 게임의 실제 목표/보상 구조는 다르다. 공통처럼 보여도 JSON 필드를 그대로 복사하지 않는다.

- 후보 작성에서 현재 확인된 목표 예시는 `collect_item`; 보상 예시는 `item`; 진행 조건은 `world_quest_progress_range`다. 후보 노드는 일반 문자열을 읽지만, 새 문자열만 추가해서 실행 기능이 생기는 것은 아니다. 현재 AI 후보 조건 필터는 알 수 없는 조건 유형을 수주 불가로 처리한다.
- `participation`이 없는 기존 고정 퀘스트는 FTB 일반 태스크로 목표를 추적한다. NPC 확인형의 마지막 `custom` 태스크는 게임만 완료한다.
- `participation`이 있는 고정 퀘스트의 실제 게임 목표 `kind`는 `ITEM_SUBMISSION`, `ITEM_DONATION`, `OBSERVATION`, `EVALUATION`이다. 목표는 1~16개, `count`는 정수 1~1,000,000. 평가형 `count`는 1이며 별도 평가 정책이 필요하다.
- 참여형 관찰과 즉석 템플릿이 허용하는 관찰은 `mythictrpg:entity_killed`, `mythictrpg:block_broken`, `mythictrpg:mature_crop_harvested`, `mythictrpg:animal_fed`, `mythictrpg:animal_bred`다. 아이템/블록/엔티티 대상은 실제 게임 등록 ID를 써야 한다.
- 즉석 개인 사이드는 등록된 `generated_quest_templates`를 이용한다. 목표 수량은 1~256이며 참여형 목표 구조와 같지 않다. 제목·요약을 자유롭게 제안해도 목표·보상을 임의 확정하지 않는다.

## 현재 게임 보상 타입

아래는 현재 개발 `RewardEntryCodec` 기준이다. 오래된 가이드의 ‘주시 미지원’ 문구보다 실제 codec과 지급 경로를 우선한다. 개발 지원 여부가 현재 설치 JAR의 동일한 지원을 뜻하지는 않는다.

| `type` | 실행 JSON 필드 | 주요 범위 |
|---|---|---|
| `item` | `itemId`, `count`, 선택 `components` | 실제 등록 아이템, 수량 1~64. `components`는 게임 보상에서만 쓰는 객체 |
| `affinity` | `amount` | +1~+200 |
| `blessing` | `effectId`, `durationTicks`, `amplifier` | 실제 효과, 20~72000틱 또는 영구 -1, 증폭 0~4. 즉시효과를 영구화할 수 없음 |
| `title` | `titleId`, `displayName` | 영구 칭호 해금, 표시명 1~80자 |
| `watch` | `godId`, `displayName` | 해당 등록 신의 개인 주시 획득. 현재 관측/응답 가능 여부와 별개 |
| `currency` | `amount` | 개인 골드, 1~9,000,000,000. 실제 잔액 상한도 검증 |
| `unlock_shop_product` | `shopId`, `productId` | 등록 상품의 서버 공용 해금 |

직접 보상은 바인딩 `rewards`에 `mode: REPLACE` 또는 `ADD`로 넣는다. `ADD`는 실제 신 보상표의 `baseTier` 1~100이 필요하고, `REPLACE`는 `baseTier`를 생략하거나 0으로 둔다. 자동 보상은 최대 32개, 선택지는 사용 시 2~6개이며 선택지마다 보상 1~16개다. 콘텐츠 후보의 보상 노드에는 중첩 `components`를 임의로 넣지 않는다.

영구 가호는 지급 보유권과 현재 효과 상태를 구분한다. 우유로 효과를 지우면 제거 상태를 유지하고 명령 재적용 또는 사망 후 부활로 복구한다. 작성된 가호 보유권은 전투력 계산 입력으로 남는다.

## 완료와 미연결 항목

기본 완료는 `PLAYER_RETURN_TO_NPC`다. 목표 달성은 확인 대기이며, 유효한 현재 주시·응답 가능 상태의 원격 확인 또는 실제 대면/재조우가 필요하다. `AUTO`, `NPC_VISIT_PLAYER`는 콘텐츠에 명시한 예외로 작성한다. 단순 목표 달성으로 신이 자동 방문하지 않는다.

관계·공용 진행도·상점 해금·실제 보상·퀘스트 판정은 게임이 저장한다. 미등록 God ID, 없는 아이템, 미정 FTB ID, 연결되지 않은 로어, 미정 장소/소속은 작성자가 `미정`으로 남겨도 된다. 검토 전에 임의의 실행 성공 상태나 새 기능 type을 만들어 확정하지 않는다.

이 목록과 사본은 파일 점검 결과다. 이번에 모드 빌드·서버 실행·실제 LLM 요청·인게임 완료 확인은 하지 않았다.

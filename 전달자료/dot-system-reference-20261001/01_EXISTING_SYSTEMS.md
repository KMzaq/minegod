# 콘텐츠 기획자를 위한 기존 시스템 설명

2026-10-01 / HanesTest 작업본 기준. 새 콘텐츠를 결정하는 문서가 아니라 기존 구현과 제한을 설명한다. 관련 원문은 [문서 길잡이](00_READ_FIRST.md), 과거 설명의 정정은 [주의사항](02_SOURCE_NOTES.md)을 따른다.

## 1. 게임의 중심과 시스템 경계

목표는 신들과 자연스럽게 대화·상호작용하며 퀘스트, 탐험, 레이드, 장비 교체, 경제와 스토리를 진행하는 소규모 멀티플레이 Minecraft RPG다. 신은 무조건적인 도우미가 아니다. 페르소나, 욕망, 현재 관계·감정, 알려진 힘의 차이, 과거 사건에 따라 거절하거나 요구하고 협력할 수 있다.

현재 모듈은 다음 역할로 나뉜다.

| 모듈 | 소유하는 책임 |
|---|---|
| MythicTRPG | 실제 진행도·플레이어 정보·관계·사건·퀘스트·보상·아이템·전투·NPC 상태와 실행 검증 |
| AI 콘텐츠 레지스트리 | 신 프로필·단계형 지식·예시·정적 관계·퀘스트 후보의 정적 데이터 |
| AI 응답 | 로컬 LLM 호출, 대화 해석·생성, 허용 지식/기억 활용, 행동 Proposal |
| FTB Quests | 퀘스트 UI·표시 및 경로에 따른 목표 추적. MythicTRPG의 완료·보상 원본을 대체하지 않음 |

AI가 “주겠다/완료했다/전쟁이 끝났다”고 말해도 게임 결과가 자동 확정되지 않는다. 게임이 검증·실행한 결과와 제안·확인 대기·실패를 구분한다. 리소스팩 역시 능력이나 게임 규칙을 실행하는 엔진이 아니다.

## 2. 진행도와 데이터 범위 — 가장 중요한 구분

| 항목 | 범위 | 기획상 의미 |
|---|---|---|
| 신/세력 퀘스트 진행 트랙 | 서버 월드 공용, 트랙 ID별 0~100, 없으면 0 | 개인별 데메테르 진행도 사본을 만들지 않는다. 신 트랙과 올림푸스 같은 세력 트랙을 따로 정의할 수 있다. |
| 고정 퀘스트의 수주·참가·제출 | 개인 또는 확정 참가자 명단 | 공용 진행도라고 모든 사람이 자동 수주·완료·보상을 얻는 것은 아니다. |
| 플레이어↔신 호감도 | 플레이어와 신의 쌍별 | 같은 신도 A와 B를 다르게 대한다. |
| 골드 잔액·보상 지급권·칭호/주시 획득 | 플레이어별 | 타인의 지급권을 공유하거나 대신 수령하지 않는다. |
| 잠긴 상점 상품 해금 | 월드 공용 | 한 사람이 해금하면 다른 사람의 상점에도 열린다. |
| 신↔신 동적 관계 | 월드의 방향별 관계 | A→B와 B→A는 다를 수 있다. 동맹·휴전·전쟁은 대칭 규칙이 있다. |
| Story 사건·사실 | 정의별 SERVER / PLAYER / TEAM | 모든 사건이 개인형인 것도, 모두 전역인 것도 아니다. TEAM은 사건 시점 청중을 고정한다. |
| 대화·기억 공개 | 방·화자·실제 청중·원본 근거별 | 비밀방에서 들은 사실을 모두가 아는 사실로 옮기지 않는다. |

퀘스트를 실제로 완료 커밋한 뒤 게임이 지정 트랙을 갱신한다. 예를 들어 공용 신 진행도가 이미 20이 되었다면, 진행도 조건이 0~19인 앞 퀘스트를 신규 플레이어에게 개인 초기화해서 다시 주는 구조로 기획하면 안 된다. 단, 모든 퀘스트가 진행 구간에 묶이는 것은 아니며 작성된 수주 조건에 따른다.

근거: `MythicWorldState.questProgress/applyQuestClearProgress`, [FTB 가이드](reference/mythictrpg-main/docs/FTB_QUESTS_INTEGRATION_GUIDE.md), [상점 가이드](reference/mythictrpg-main/docs/SHOP_ECONOMY_GUIDE.md).

## 3. 퀘스트

### 세 데이터의 연결

신 프로필의 `questListIds`로 콘텐츠 레지스트리의 목록을 참조할 수 있다. 목록은 여러 개이며 공용 세력 목록도 공유할 수 있다. **목록에 문장을 적는 것만으로 실행 퀘스트가 생기는 것은 아니다.** 고정 퀘스트는 AI용 목록 + MythicTRPG 바인딩 + FTB 정의를 같은 논리 ID로 연결한다.

### 서로 다른 실행 경로

| 경로 | 현재 의미 |
|---|---|
| 기존 고정 바인딩(`participation` 없음) | 개인별 수주는 가능하지만 최초 유효 완료가 논리 퀘스트를 전역 완료시킨다. 다른 수주자의 동일 퀘스트는 무효화될 수 있다. FTB 팀 목표 공유 영향을 별도로 고려한다. |
| 참여형 고정 바인딩 | 서버 소유 개인 실적과 고정 참가자 명단으로 SOLO / GROUP / COMPETITIVE / RANKING을 처리한다. FTB는 표시 미러다. |
| AI 즉석 SIDE 퀘스트 | 등록된 템플릿 중 AI가 선택하고 제목/요약을 제안한다. 게임이 조건·목표·보상 범위를 검사한다. 현재 개인형이며 무제한 자유 생성 엔진이 아니다. |

참여형 SOLO는 같은 논리 퀘스트를 여러 사람이 각각 복제 수주하는 모드가 아니다. GROUP은 확정 참가자 각자가 목표와 제출을 끝내야 공동 종료된다. COMPETITIVE는 첫 유효 최종 제출자, RANKING은 서버 점수·종료 조건과 작성된 보상 구간을 사용한다. 동의 전에 수주 성공이나 소비·보상으로 취급하지 않는다.

### 완료 확인 방식

- `AUTO`: 허용 목표 달성 후 자동 완료.
- `PLAYER_RETURN_TO_NPC`: 목표 달성 후 지정 상대에게 돌아와 확인.
- `NPC_VISIT_PLAYER`: 목표 달성 후 적절한 자발적 상호작용에서 확인할 수 있는 계약. **완료 준비 상태에서 물리 NPC 방문을 자동 예약·시작하는 연결은 아직 미완료다.** 이미 있는 일반 집 방문과 동일시하지 않는다.

참여형의 목표에는 아이템 제출·누적 기부·관찰·평가가 있다. 즉석 SIDE는 처치, 블록 파괴, 성숙 작물 수확, 동물 먹이주기, 번식의 기존 5관찰 목표 범위다. 목표 종류·참여 유형·완료 방식·메인/사이드 역할은 별개 축이다.

`MAIN_ENTRY`는 신의 메인 접근 대상을 정하는 입문, `MAIN`은 해당 접근 대상에 대한 메인, `SIDE`는 일반 조건을 따르는 사이드다. 메인 접근 권한을 보상으로 얻는 ‘신의 주시’나 친밀함·자동 후원과 혼동하지 않는다. 늦게 들어온 플레이어에게 어떤 콘텐츠를 줄지는 별도 기획이 필요하다.

보상은 자동 지급과 개인 선택 지급권을 지원하며 중복 지급을 방지한다. FTB 미러와 MythicTRPG에 같은 보상을 이중 등록하지 않는다. [참여 유형](reference/mythictrpg-main/docs/QUEST_PARTICIPATION_GUIDE.md), [즉석 퀘스트](reference/mythictrpg-main/docs/GENERATED_QUESTS_GUIDE.md), [보상](reference/mythictrpg-main/docs/REWARD_SYSTEM_GUIDE.md) 참조.

## 4. 관계·감정·힘·지식

플레이어↔신 affinity 원본은 게임에 있으며 범위는 -1000~1000이다. AI용 관계 지침은 다음 9단계를 지원한다.

`R_EXTREME_HOSTILE → R_HOSTILE → R_DISLIKE → R_WARY → R_NEUTRAL → R_FAVORABLE → R_FRIENDLY → R_TRUSTED → R_DEEP_BOND`

단계별 구체적인 태도는 NPC마다 다르게 작성한다. 수치→태그 경계는 설정 가능하며 문서의 임시 기본 경계를 최종 밸런스로 채택하지 않는다. 별도의 trust/respect/caution이 모두 완성된 게임 수치 저장소로 존재한다고 가정하지 않는다.

신 간 관계는 정적 혈연·배경(`RT_*`)과 현재 방향별 점수·태그를 나눈다. 과거 숙적이 현재 휴전할 수도 있고, 한쪽은 두려워하지만 반대쪽은 무관심할 수도 있다. 친족/연인 같은 유형은 호감도 9단계의 대체물이 아니다.

장기 관계와 현재 감정은 다르다. 대화의 실제 전달 이력에 따른 비권위 현재 감정 연결은 있지만, 대화 밖 모든 활동에 통용되는 공용 감정 원본까지 완성된 것은 아니다. 없는 정보는 미평가이지 중립 확정이 아니다.

신의 사회적 위상, 전투에서의 우위, 친밀함, 두려움, 보호 의무는 별개다. 높은 호감도·가호·주시 획득이 자동 보호 계약이나 강제 개입을 뜻하지 않는다. 아래 전투력 보정 점수가 곧 신과 인간의 서열 판정도 아니다.

프로필·로어는 NPC가 아는 지식 단계와 현재 청중에게 공개 가능한 범위를 구분한다. 관계·사건의 비밀을 모든 NPC의 공용 프롬프트에 넣지 않는다. ## 5. 전투·실체 NPC·레이드

- 실제 신 NPC 정의와 단일 실체 관리가 있다. 같은 신을 다른 장소/레이드에 동시에 복제하지 않는다.
- 현재 외형은 classic/slim 플레이어형과 신별 스킨을 지원한다. 스킨 교체만으로 날개·여러 팔·거대 괴물 모델이 생기지 않는다.
- 작성된 NPC 전투와 AI `player_damage` 액션은 존재한다. 후자는 신별 허용 템플릿과 게임 검증에 따른 타격이며 자유 명령 실행이 아니다.
- 레이드는 공용 월드형과 미리 만든 구역을 배정하는 파티 격리형을 지원한다. 신/전장 슬롯이 사용 중이면 대기한다. 임의 월드 복제형 인스턴스가 아니다.
- 모집·참가·시작·제한 시간·목숨·보상 자격·실보스 사망·복귀·상태 UI가 있다. 체력 단계별 추가 몹을 작성할 수 있다. 임의의 새 특수 공격/기믹은 해당 엔티티 구현이나 추가 개발이 필요하다.
- 엔티티 사망이 신화적 영구 사망·봉인·세력 붕괴를 자동 확정하지 않는다. Story 효과를 따로 작성해야 한다.
- 전장 자동 원상복구와 모든 외부 모드의 월드 변경을 막는 완전한 격리는 없다. 전장 재사용 방식과 보호 범위를 기획/연동에서 고려한다.

현재 확인한 게임 리소스·서버 데이터팩/설정에는 운영용 신 실체·레이드·전장·전투력 정책 JSON이 준비되어 있지 않았다. 런타임이 있다는 것과 실제 플레이할 레이드 콘텐츠가 작성되어 있다는 것을 구분한다. 테스트용 fixture는 운영 콘텐츠가 아니다.

## 6. 장비·보상·가호·전투력 보정

장비 성장은 사용자가 선택한 **더 좋은 장비를 얻어 교체하는 방식**이다. 강화·개조 트리를 기본 전제로 만들지 않는다. 생활활동의 바닐라 두 도구 수리는 장비 강화 시스템이 아니다.

서버 아이템 ID와 Minecraft 1.21.1 data components로 이름·CustomModelData·속성 등을 가진 장비를 보상/상점으로 제공할 수 있다. 리소스팩은 외형을 담당한다. 특수 액티브 스킬은 이미지나 모델 번호만으로 실행되지 않는다. 장비 목록, 수치, 리소스팩 미술은 제작 대상이다.

보상에는 아이템, affinity, 시간제 효과인 가호, 영구 해금 칭호, 개인 골드, 전역 상품 해금, 신별 개인 주시가 있다. 칭호 해금은 별도 표시/장착 UI 완성을 뜻하지 않는다. 주시 획득도 모든 비밀을 무제한 관측하는 권한이 아니다. 영구 가호와 영구 능력치 성장 지급의 독립된 콘텐츠 체계는 미완성이다.

전투력 공급자는 확인된 보상 장비 이력·현재 효과·실제 영구 modifier·공용 진행도의 작성된 권장치를 읽는 **즉석 퀘스트 캐치업 용도**다. 범용 레벨 시스템이나 모든 모드 장비의 자동 전투력 평가기가 아니다. 정책/근거가 없으면 UNAVAILABLE이고 보정하지 않는다. 신들의 전투력 서열표로 재사용하지 않는다.

## 7. 경제·상점

- 골드 잔액은 개인 UUID별로 저장한다. 신규 0, 기술적 상한 9,000,000,000이다. 상한은 권장 밸런스가 아니다.
- BUY/SELL 상점을 데이터팩으로 정의하고, 화면에서 묶음 수량을 선택해 거래한다.
- 현재 상품 재고는 무제한이며 가격은 작성 데이터다. 수요·공급 자동 가격 변동이나 NPC 자유 흥정 엔진으로 설명하지 않는다.
- 구매는 공간/잔액, 판매는 아이템과 components를 게임에서 확인한다. 방어구·보조손을 자동 판매하지 않는다.
- 골드 보상은 개인, 상품 해금은 전역이다.
- 아이템·가격·상품·재화 수급량은 작성자가 정한다. 샘플 광물/물약 상점만으로 최종 경제가 완성된 것은 아니다.

기획 시 구매→판매 차익, 반복 퀘스트/자원 자동화의 재화 수급, 최상위 보상과 상점의 역할 중복을 검토한다. 경매·개인 상점·유한 재고·세금·플레이어 송금 등을 현재 지원한다고 추측하지 않는다. [상점·경제](reference/mythictrpg-main/docs/SHOP_ECONOMY_GUIDE.md) 참조.

## 8. 스토리·건축·생활과 대화

Story 엔진은 조건/신호 기반 사건, 고정·첫 조건 일치·가중 선택·플레이어 선택, 반복 정책, 사실/위장 설명/공개 범위를 지원한다. 선택 화면도 있다. 현재 SERVER/TEAM 사건의 선택도 고정 청중의 **첫 유효 선택**이 확정되는 정책이지 전원 투표가 아니다. 합의/투표형 결정이 필요하면 별도 요구로 표시한다.

집/신전 같은 건물은 기존 영역 등록·평가를 사용할 수 있다. 허용 신과 공용 진행도 조건을 만족하면 기존 실체가 건축물을 고르는 대화/자율 방문이 가능하다. 같은 차원·로드된 도달 가능 범위의 보행이며 자동 소환·순간이동·장거리 여행 완성을 뜻하지 않는다. 신전 봉헌, 영구 축복, 공물에 따른 장기 진행 효과는 별도 미완료다.

생활활동은 주변 시설 인식, 앉기/독서/산책/교류, 실제 자원 사용 작업, 동의 후 무피해 대련 등을 지원한다. 일반 플레이어의 “쓰지 마”는 신이 거절할 수 있고 관리자 금지는 항상 적용한다. 자원 사용에서 플레이어 인벤토리는 제외한다. 임의 외부 모드 기계/특수 사용 동작은 미지원이다. 주변 NPC-only 대화는 짧은 활동 이력까지이며 장기 기억·소문 연결은 남았다.

공개/비밀 대화방과 다인·다신 대화, 채팅/HUD, 정체 식별이 있다. AI가 전체 지식을 알고 있거나 관계가 있다는 이유로 임의 신을 대화에 추가하지 않는다. 새 기억 저장/검색 전체 전환과 일반 플레이 소문·평판의 완전 활성화도 미완료다.

## 9. dot의 기획 결과에 붙일 분류

각 사건·퀘스트·레이드에 다음 중 하나를 표시한다.

1. **기존 기능으로 작성 가능:** 참고한 계약과 필요한 데이터/자산을 명시.
2. **추가 개발 필요:** 새 행동/판정/저장/UI를 구체적으로 명시.
3. **지원 여부 미확인:** 근거가 부족한 부분과 확인할 문서를 명시.

예를 들어 ‘아테나가 승리 소식을 듣고 동맹을 제안한다’는 대사, 전이 정의, 공개 권한, 선택/확인, 실제 관계 변경을 나누어 기획한다. 대사 하나로 동맹·보상·세계 진행도를 모두 실행했다고 쓰지 않는다. 이 예는 기획 방법 설명일 뿐 새 정사가 아니다.

현재의 기능 한계 때문에 아이디어를 모두 버릴 필요는 없다. 다만 추가 개발 부담을 감추지 말고, 기존 기능을 이용한 대안과 비교한다. 등장 신화·필수 인물·배경/진행 스토리와 게임 밸런스는 사용자가 별도로 제공하거나 승인할 내용이다.
